## 1. 背景与问题

1. **最好用的 agent 工作台只服务一家 agent。** Codex 桌面客户端（现为 ChatGPT 桌面 App 中的 Codex 视图）把"并行跑多个会话 → 审批 → 审查 diff → 提交"做成了顺手的闭环，但它只能驱动 Codex。同时使用 Claude Code 的开发者，要么回到终端，要么在两套工具之间来回切换。（R01）
2. **离开电脑后，agent 就停在那里等审批。** 官方的移动端远程功能（Claude Code Remote Control、Codex Remote）都要经过厂商的中继，只有 TLS 加密，厂商能看到会话内容。第三方方案中做了端到端加密的只有少数几家，而且都有配对认证或推送明文方面的缺陷。目前没有一个产品同时做到"多 agent + 扎实的端到端加密"。（R03）
3. **开放协议已经可用，但仍在快速变化。** ACP v1 已经稳定。Claude Code 和 Codex 都有 ACP 适配器，由 ACP 组织维护、Zed 和 JetBrains 主导，并不是 Anthropic 或 OpenAI 的官方产品。两个适配器几乎每天发版，有过破坏性变更。（R02）

## 2. 产品定位

**一句话**：一个开源、自用优先的 macOS agent 工作台。用 Codex 的交互方式驱动 Claude Code 和 Codex，并能在 iPhone 上通过端到端加密的通道随时接管。

**目标用户**

- 首要：作者本人，即同时使用 Claude Code 和 Codex 的开发者。
- 次要：开源社区里有同样需求、愿意自己部署的开发者。

**目标**

| # | 目标 | 衡量方式 |
|---|---|---|
| G1 | 日常开发中替代 Codex App 和终端里的 Claude Code | 作者连续两周的日常开发主要在 cupper 中完成 |
| G2 | 离开电脑时，能在 iPhone 上处理审批和提问、追加指令 | 在 Mac 醒着、cupper 在运行的前提下，离开电脑期间的审批和提问都能在手机上完成 |
| G3 | 除用户自己的设备外，cupper 自身链路上的任何一方（包括中继和推送服务）都看不到会话内容 | 抓包和检查中继，确认只有路由所需的元数据和密文。agent 的模型提供方按各自的条款处理会话内容，不在这个承诺的范围内 |

**不做的事（非目标）**

- 不复刻 ChatGPT 的 Chat、Work、Sites 等非编码功能，只复刻 Codex 编码视图。（R01）
- 不做云端执行、云任务、SSH 远程主机。
- 不做账号、计费，不内置任何 Claude 或 ChatGPT 登录流程。（见第 8 节）
- 首期不做 Windows、Linux、Android、Web 客户端。
- 不做团队协作或多人共享会话。
- 不追求补齐 Codex 自家 harness 的专有能力，例如 Approve for me 的审查 agent、Goal、Memories。某个 agent 本身提供这些能力时再接入。替代方案见 U6。
- 不提供官方托管的中继或推送服务。

## 3. 核心概念

| 概念 | 说明 |
|---|---|
| Agent | 被驱动的编码 agent。首期只支持 Claude Code 和 Codex，使用用户本机已安装、已登录的官方 CLI |
| 电脑 | 运行 cupper 桌面端的一台 Mac，有唯一标识。一台手机将来可以对应多台电脑 |
| 会话宿主 | 电脑上一个与界面分离的后台组件，持有全部会话、历史和操作能力。桌面界面、命令行工具和手机都是它的客户端 |
| 项目 | 本机的一个代码文件夹 |
| 工作区 | 会话实际工作的目录：项目目录本身（本地模式），或为这个会话新建的 Git worktree |
| 会话 | 某个项目下、与某一个 agent 的一段对话。创建时选定 agent 和工作区，之后都不能更换 |
| 回合 | 用户发一条消息，到 agent 停下来为止的这一段工作 |
| 交互请求 | agent 需要用户介入时发起的请求，分两类：**审批**（是否允许某个操作）和**提问**（选择题、表单、计划确认、授权链接）。任何一个客户端都可以处理，先到先得 |
| 会话状态 | 空闲 / 运行中 / 需要处理（有待处理的交互请求）/ 完成未读 / 出错。状态由会话宿主统一计算，所有界面看到的一致（R01） |
| 未读 | 回合完成后、还没有被查看的会话。任何一端查看过，其他端都同步为已读（已确认 U4） |
| 已配对设备 | 经扫码配对、可以远程操作本机会话的 iPhone，可以在桌面端撤销 |

## 4. 关键使用场景

| # | 场景 |
|---|---|
| S1 并行开发 | 在项目 A 里同时开两个会话：用 Claude Code 修一个 bug，用 Codex 补测试。两个会话各自在独立的 worktree 里运行，互不干扰。侧边栏能看出哪个在运行、哪个在等我 |
| S2 审批与提问 | agent 要执行越界命令时，消息流里出现审批卡片，按 Enter 批准、Esc 拒绝，范围选项（如"仅本次""总是允许"）由 agent 提供。agent 需要我做选择或确认计划时，出现提问卡片。窗口不在前台时收到系统通知 |
| S3 审查到提交 | 回合结束后打开审查面板看 diff，在某行写评论让 agent 改；满意后按文件或 hunk 暂存，提交并推送 |
| S4 运行中追加指令 | agent 还在工作时，我补充一句话，排到下一回合（Queue）；agent 支持的话，也可以插进当前回合（Steer） |
| S5 离开工位 | 我在外面，iPhone 收到推送："项目 A / 修 bug 需要审批"。解锁后查看命令详情并批准，然后回到会话列表看进度 |
| S6 手机上追加指令 | 在手机上查看某个会话的实时输出，追加一条消息让它换个思路 |
| S7 首次配对 | 桌面端显示二维码，手机扫码完成配对，之后不需要再配对；手机丢了可以在桌面端撤销 |

### 6.3 安全与隐私

| ID | 需求 | 优先级 |
|---|---|---|
| SEC-1 | 端到端加密：桌面端与手机之间的全部内容，包括会话标题、项目路径、主机名、命令和推送内容，都要加密。中继只能看到路由所需的元数据和密文，具体范围见 SEC-7 | P0（M3） |
| SEC-2 | 配对时双向认证：二维码里放一次性、短时效的秘密，用它认证手机回传的应答，防止中继冒充（R03 发现 Happy #1503 就是这类问题） | P0（M3） |
| SEC-3 | 每台设备一把独立密钥；在桌面端可以查看和撤销已配对设备；撤销后，被撤销的设备无法再连接，也无法解密新内容 | P0（M3） |
| SEC-4 | 桌面在执行来自手机的指令之前，要能确认三点：它来自一台未被撤销的已配对设备；它没有被重放；如果是审批或提问的回答，它针对的正是当前这条请求 | P0（M3） |
| SEC-5 | 客户端拒绝明文降级：一旦启用加密，任何时候都不接受未加密的连接 | P0（M3） |
| SEC-6 | 默认不收集任何遥测数据 | P0 |
| SEC-7 | 文档明确说明加密覆盖的范围：中继能看到哪些元数据（电脑和设备的标识、IP、在线时段、消息大小和频率、推送时间），以及 Apple 推送服务能看到什么 | P0（M3） |
| SEC-8 | 会话宿主只接受经过认证的本地客户端；agent 子进程和集成终端都拿不到这份凭据；宿主不监听任何网络端口。目的是防止 agent 连上宿主替自己批准，或把自己切到完全访问 | P0 |
| SEC-9 | 手机的权限边界（已确认 U3）：只能在 agent 本身的权限范围内操作；不提供远程 shell，不能直接写文件；不能切换到"完全访问 / 跳过审批"；不能选择"总是允许"这类会持久扩大权限的审批选项；只能在已有项目里新建会话 | P0（M3） |
| SEC-10 | 每个对交互请求的处理都绑定到具体的请求和它的内容；请求所属的 agent 进程退出后，请求自动失效 | M1 打数据基础；M3 P0 |
| SEC-11 | 说明静态数据的保护方式：桌面的会话记录以明文存在本机（依赖 FileVault）；iOS 的本地缓存使用系统数据保护；密钥存在钥匙串中 | P0（M3） |

### 6.4 中继

| ID | 需求 | 优先级 |
|---|---|---|
| RL-1 | 中继是一个开源的单体服务，由用户自己部署（Docker 或单个可执行文件）；桌面端和手机都只需要发起出站连接 | P0（M3） |
| RL-3 | 推送由中继直接发出，使用用户自己的 APNs 凭据。前提：用户有付费的 Apple Developer Program 账号，并用它构建 iOS App（已确认 U7） | P0（M3） |
| RL-5 | 中继运维：健康检查；设备凭据会过期、可以吊销；限流；部署文档；与客户端的版本兼容 | P0（M3） |
| RL-2 | 中继缓存最近一段时间的密文（默认 7 天），用于电脑离线时查看历史。M3 的中继不保存任何会话数据，断线续传由桌面补齐（已确认 U1） | P1（M4） |
| RL-4 | 手机与电脑在同一局域网时直连，不经过中继 | P2 |

## 7. 非功能需求

| ID | 需求 |
|---|---|
| NFR-1 平滑演进 | 1. 会话、历史、审批与提问、排队、Git、worktree、终端都由一个与界面分离的会话宿主持有。桌面界面是它的客户端，除宿主协议之外，不读写任何会话数据，也不直接调用 agent、git 或终端。<br>2. 宿主协议从第一版起具备：版本与能力协商；客户端身份，以及对每条命令的授权检查；断线后按位置续传，落后太多时整体重新同步；命令可以安全重试；大内容按需获取。<br>3. 宿主输出语义化的事件和状态，界面只负责排版和本地化。<br>4. M3 接入手机时，新增远程传输、端到端加密、设备与配对、推送、手机权限范围，以及桌面端的配对和设备管理界面；不改写已有的界面、会话逻辑和事件模型。<br>**M1 验收**：一个独立进程的命令行客户端，通过和桌面界面相同的协议完成以下操作，并由自动化测试覆盖：<br>- 订阅会话列表和任意一个会话，看到的内容与桌面一致；<br>- 发送消息、排队、中断、处理审批、回答提问，桌面界面同步更新；<br>- 任何一端处理了审批或提问，另一端自动收起；<br>- 客户端断开期间产生的事件，重连后补齐，不丢也不重复；<br>- 会话宿主被强制结束后重新启动，会话可以继续 |
| NFR-2 断线续传 | 任何客户端断线重连后，都能从断点补齐，不丢消息，也不重复；落后太多时整体重新同步。客户端发出的命令带唯一标识，网络重试不会造成重复执行 |
| NFR-4 数据本地化 | 会话数据只存在用户本机；M4 起，用户自建中继上可能有加密缓存 |
| NFR-5 版本可控 | 锁定经过验证的适配器版本，升级要经过回归验证（R02：适配器几乎每天发版）；明确本机 CLI 的已验证版本范围；不随 App 再分发受 Anthropic 商业条款约束的组件（以 ADR-11 为准） |
| NFR-6 性能 | 冷启动到"可用"不超过 2 秒。"可用"指会话列表和历史可见、可以输入；agent 进程按需启动，不计入这 2 秒。流式输出不卡顿；一千条以上消息的长会话滚动流畅 |
| NFR-7 可降级 | cupper 自己实现排队、运行状态、回合级和会话级的 diff、worktree、会话索引、审批与提问的路由。只能依赖 agent 私有扩展的能力，探测到才启用，不可用时降级，包括：Steer（降级为排队）、子代理展示、Markdown 计划、后台任务状态（R02） |
| NFR-8 宿主生命周期 | 会话宿主单实例运行，由 App 启动；界面崩溃或重载不影响宿主和正在运行的会话；退出 App 时如果有会话在运行，要先提示；App 升级时如果有回合在运行，推迟重启宿主。后台常驻（关窗后会话继续运行、手机仍能操作）为 P1，M3 之前完成（已确认 U5） |
| NFR-9 崩溃恢复 | 会话宿主崩溃后：清理残留的 agent 进程，运行中的回合标记为"已中断"，待处理的交互请求标记为"已失效"，会话可以继续。agent 进程崩溃后：自动重启并恢复会话，消息流中显示提示。任何崩溃都不能损坏已保存的历史 |
| NFR-10 升级与迁移 | 本地数据有版本号，升级时自动迁移，迁移前自动备份；明确说明不支持降级。宿主协议做版本协商，桌面和 iOS 的版本可以相差若干个版本 |
| NFR-11 容量 | 能同时运行至少 6 个会话；历史记录、附件和 worktree 的磁盘占用可见、可清理（P1） |
| NFR-12 诊断 | 本地日志按大小轮转并脱敏；收集 agent 适配器的错误输出（P0）；可以导出诊断包（P1）；不上传任何数据 |
| NFR-13 电源 | 有回合在运行或有待处理的交互请求时，阻止 Mac 空闲睡眠（M1 为 P1，M3 为 P0）；合盖后无法远程操作，写进文档 |

## 8. 合规与约束

- **账号**：cupper 不内置任何 Claude 或 ChatGPT 的登录流程，只调用用户本机已安装、已登录的官方 CLI。用户也可以通过环境变量自行配置 API key。（访谈 #2；R02 S11）
- **商标**：产品名、图标和宣传中不使用 "Claude Code"、"Codex"、OpenAI 或 Anthropic 的商标和品牌素材；README 不写"使用你的 Claude 订阅"之类的说法。
- **UI 复刻边界**：复刻布局、交互和信息架构；视觉素材（图标、插画等）自己制作。
- **不改写 agent 的配置**：cupper 不修改 `~/.claude`、`~/.codex`、项目中的 `.claude/`、`AGENTS.md` 等 agent 配置。唯一的例外是用户选择"总是允许"后，agent 自己写入的权限规则。
- **开源许可证与再分发**：cupper 的许可证，以及哪些第三方组件不能随 App 分发（例如受 Anthropic 商业条款约束的 Claude Agent SDK 和 Claude Code 程序），在阶段 ② 由 ADR-11 决定。
- **iOS 前提**：M3 需要用户有付费的 Apple Developer Program 账号，用它构建 iOS App 并发送推送（已确认 U7）。
- **大范围公开分发之前**：先向 Anthropic 确认第三方客户端调用用户本机 CLI 的政策边界。

## 9. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| ACP 适配器变化快，几乎每天发版，有过破坏性变更 | 功能随时可能失效 | 锁定版本，用录制的 agent 行为做回归测试（NFR-5） |
| 适配器使用的 agent 程序与本机 CLI 版本不一致 | 行为不可预期 | 使用本机 CLI，明确已验证的版本范围，超出范围时提示（AG-5） |
| ACP 缺少 Codex 风格 UI 需要的能力 | 部分功能做不到或体验不一致 | 由会话宿主补齐；按 agent 降级（NFR-7）；Codex 是否改为直连 app-server，由 ADR-07 决定 |
| 适配器的已知缺陷（回放不完整、拒绝审批会结束整个回合、中途退出后不返回等） | 历史、审批和中断的体验受影响 | 历史以 cupper 自己的记录为准；超时兜底；阶段 ② 用原型实测（SP-1） |
| agent 通过本地接口替自己批准，或切换到完全访问 | 审批形同虚设 | 本地接口鉴权（SEC-8） |
| 清理 worktree 时丢失未提交的工作 | 数据丢失 | 有未提交或未推送内容时不删除（GT-5） |
| 没有"帮我批准"后审批变多 | 影响 G1 | 提供 agent 自带的低打扰模式（已确认 U6） |
| Codex 界面持续演进 | 复刻目标在移动 | 以 2026-10 的 Codex 视图（R01 加截图）为基线冻结 |
| 端到端加密方案存在设计或实现漏洞 | 安全承诺失效 | 配对和加密使用成熟协议与库，不自己发明密码学方案；M3 退出前做安全设计评审 |
| iOS 后台限制；Mac 睡眠或合盖 | 手机无法远程操作 | 依靠推送唤醒，回到前台后补齐（NFR-2）；阻止空闲睡眠，并在文档中说明限制（NFR-13） |
| 自建 iOS 需要付费开发者账号 | 用户无法使用推送 | 写入前提条件（第 8 节）；阶段 ② 用 SP-7 核实 |
| Claude 订阅在第三方客户端中使用的政策风险 | 开源分发受限 | 见第 8 节 |
