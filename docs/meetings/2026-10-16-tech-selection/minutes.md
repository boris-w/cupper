## 第一轮形成的共识

| ADR | 共识 |
|---|---|
| ADR-01 | 宿主是独立的无界面进程。M1 由 App 按需拉起，但不随 UI 一起退出；M2 用同一个二进制注册为 LaunchAgent，实现后台常驻。否决进程内模块、随 UI 退出的子进程、App 内嵌的 XPC 服务 |
| ADR-02 | 宿主用 Rust：架构师和移动与安全工程师首选，桌面工程师接受，条件是协议以 schema 为唯一来源。否决 Swift，因为没有官方 ACP SDK |

| ADR-04 | 自有协议；M1 用 JSON，长度前缀分帧；整数主版本加特性标志；宽容读取；命令幂等 |
| ADR-05 | Unix 域套接字；用 `LOCAL_PEERTOKEN` 取审计令牌，校验 UI 的代码签名；不开 TCP 端口；XPC 只作后备 |

## 分歧与裁定

第二轮中，C1、C2、C3、C5 都出现了"互相让步、结果交换立场"的情况，说明双方都认为对方的方案可行。在这种情况下，编排者选更简单、或者 M1 成本更低的那一个。

| # | 分歧 | 第二轮后的状态 | 编排者裁定 |
|---|---|---|---|
| C1 | seq 是否连续 | 三方收敛 | **日志里的 seq 连续。** 合并分两级：<br>- 写入时：宿主按 33–50 ms 合并同一条目的片段；首个片段立即发出；条目完成时或发出其他事件之前，先把缓存的片段刷出去。<br>- 发送时：可以对慢连接合并成区间事件，用 `from` 字段标明覆盖的 seq 区间。<br>客户端检查"`from` 等于上一个 seq 加 1"，不满足就重新订阅。schema 里标出哪些事件类型可以合并，并加一条性质测试：合并后应用的结果与逐条应用相同。保留 `stream/reset` 作为兜底 |
| C2 | schema 来源；iOS 怎样使用协议 | schema 来源三方收敛；iOS 的使用方式两人交换了立场 | **schema 来源**：Rust 类型（serde + schemars）→ 提交到仓库的 JSON Schema → 用 @hey-api/openapi-ts 生成 TS 类型和 zod 校验（不用 strict 模式）。规则如下：<br>- 事件信封保持开放；<br>- 联合类型统一用 `type` 字段作标签；<br>- 枚举和联合类型默认开放，由生成器产出 `Unknown` 兜底；<br>- 带 `fallback{kind, summary}`，给不认识的条目显示占位；<br>- 兼容性检查区分消息方向。<br>**iOS 使用协议的方式留给 ADR-15（M3 前）决定**，在"通过 UniFFI 共用不做 I/O 的客户端 crate"和"生成原生 Swift 类型"之间二选一。M1 只做两件低成本的事，保证两条路都还能走：<br>- 共享的 crate 不做 I/O，并在 CI 里验证能编译到 iOS 模拟器；<br>- 金样例里包含未知值的样例。<br>架构师提议在 M1 加"Swift 生成器解码测试"，并以它作为改用 Protobuf 的条件。这一项推迟：如果 ADR-15 选 UniFFI，就根本不需要 Swift 生成器，而 schema 来源也不会因此改变 |
| C3 | 帧大小上限 | 两人交换了立场；桌面工程师和架构师的最终立场都是 64 KB | **本地和远程统一用一个上限**，单帧不超过 64,000 字节，能放进一条 Noise 消息。帧格式是 `u32 长度 \| u8 帧类型 \| 负载`：0x01 表示 JSON，0x02 表示 blob 分片（原始字节，不做 base64），0x03 预留给二进制编码。新增 `blob/put`。"大字段换成 blob 引用"的阈值对所有连接相同（ADR-06）。移动与安全工程师提出的"48 KiB 经 base64 后放不进一条 Noise 消息"的问题，因为 blob 改走二进制帧而不再存在 |
| C4 | CLI 认证 | 收敛 | **CLI 默认只读，不保存任何凭据。** 任何写操作（不只是审批）都要经用户在场确认：由主进程弹出原生确认框，授权只在这条连接上有效，最长 15 分钟。能确认申请方是适配器的后代就直接拒绝，同一来源的申请要限频。非 UI 的 principal 永远不能切到完全访问，也不能选择 `allow_always`。测试用的 principal 只在编译特性打开时存在。开发构建和自行构建使用退化的认证模式，并在 UI 上提示。**"可信 CLI 凭据"不在 M1 提供**（架构师建议作为默认关闭的可选项保留），交用户决定（U-T4） |
| C5 | Electron 里由谁连接宿主 | 两人交换了立场 | **M1 只由主进程持有一条连接**，这是两个方案里更简单的一个。主进程只按长度前缀切帧，不解析 JSON；大约每 16 ms 批量转发一次；渲染进程跟不上时停止读取。SP-6 增加一个指标：主进程事件循环延迟的 p99 小于 5 ms。达不到时，后备方案是"utilityProcess 宿主桥 + 委托票据 + 父进程绑定"（见 `architect-round2.md` C5） |
| C6 | 宿主放在哪里、怎么升级 | 收敛 | 宿主做成 app-like 的 helper bundle：`Contents/Helpers/CupperHost.app`，设为 LSUIElement，有自己的 identifier，M3 时在这里嵌入描述文件。Node 和适配器按锁定版本装在包外的 `runtime/<名称>/<版本>/` 目录（由 ADR-08 细化）。宿主在运行中不读取包内的任何资源；每次拉起运行时之前先比对 cdhash。安装时机由我们控制：用 electron-updater，关闭 `autoInstallOnAppQuit`，顺序是"通知宿主待升级 → 宿主空闲后退出 → 安装 → 拉起新宿主"。后备方案是把宿主复制到包外的版本目录，包内放一个启动器（见 `desktop-engineer-round2.md` C6）。全部由 SP-4 的升级演练验证 |

## 其他共识（来自两轮的问答）

- **渲染进程的安全**：
  - 渲染进程能调用的命令有白名单。切换到完全访问或跳过审批、选择 `allow_always`、批准 CLI 提权、M3 的配对和撤销设备，都只能走主进程弹出的原生确认框。
  - 批准和回答提问，要求主进程在 1 秒内观察到真实的用户输入（`before-input-event`），同时检查 `navigator.userActivation`。
  - 审批卡片出现后有约 500 ms 的输入保护；Enter 只在焦点位于卡片上时生效。
  - 严格的 CSP；不渲染原始 HTML；Mermaid 在沙箱 iframe 里渲染；链接在外部浏览器打开；禁止页面导航和新开窗口。
  - 深链接按白名单路由，只做导航；不提供 AppleScript 字典，不注册 Services 菜单。
  - M1 的桌面通知上不放"批准"按钮。
- **Electron 加固**：
  - 发布构建关闭 `runAsNode`、`nodeOptions`、`nodeCliInspect` 三个 fuse，打开 ASAR 完整性校验和 `onlyLoadAppFromAsar`；启动参数里出现调试参数就直接退出。
  - 端到端测试用单独的 e2e 构建，开发构建是 "cupper Dev"，两者都用不同的 identifier，发布版的宿主不接受它们。
- **系统通知**：全部由宿主 helper 弹出，UI 只上报"窗口是否在前台"。如果 helper 在系统通知设置里显示的名称和图标不对，就退回"UI 在时由 UI 弹"。
- **多窗口**：共用一条连接；每个窗口分到一个自己的 MessagePort。
- **宿主提供的能力**：会话内搜索（SQLite FTS5，位置用 UTF-16 偏移）；条目摘要（行数、字节数、退出码、耗时、diff 统计、预览）；按内容寻址的 hunk ID，加上基线作为前置条件；交互请求上的 `actionable_by`；索引流里的 `clients` 列表。
- **审批摘要**：由宿主计算并下发，客户端原样回显，客户端不重新计算。
- **冷启动预算**：宿主侧 p95 不超过 400 ms，包括拉起约 150 ms、握手和签名校验约 100 ms、首屏快照约 150 ms。
- **iOS（M3）**：用 SwiftUI 原生；审批和提问卡片永远不放进 WebView；通知扩展（NSE）只链接推送解密。
- **密码学（M3）**：原语白名单（X25519、Ed25519、ChaCha20-Poly1305、AES-GCM、SHA-2、HMAC、HKDF、HPKE，P-256 只用于签名）；只调用库，不手写原语；用外部测试向量校验，再用一份独立的实现做交叉验证；`crypto/` 目录的改动必须人工审查。是否把这几条写进 `CLAUDE.md`，到 M3 开工前（ADR-12）再决定。
