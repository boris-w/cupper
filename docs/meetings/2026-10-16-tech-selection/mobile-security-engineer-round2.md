# 技术选型讨论会第二轮：移动与安全工程师回应

- 日期：2026-10-16
- 角色：移动与安全工程师
- 依据：本目录下的 `architect.md`、`desktop-engineer.md`，以及我第一轮的发言
- 说明：本轮没有发起任何外部请求。事实沿用第一轮的核实结果；新增的判断标为"推"，需要 SP-4 或 SP-8 验证。

**总体立场**
- C1：给出一种兼容写法——日志里的 seq 保持连续，下发时可以用"区间事件"合并。
- C2：接受 JSON Schema 路线，不再坚持 Protobuf；接受 iOS 共用 `cupper-client`，但各附了条件。
- C3：接受"握手协商、本地默认 1 MiB"，但 48 KiB 的 blob 块在 base64 下放不进一条 Noise 消息，要改。
- C4：接受架构师的方案，撤回"钥匙串凭据加挑战-应答"。

## C1 seq 语义

**最终立场**：采用编排者提出的思路，但把"只看单调性"加强为"区间事件 + 精确的缺口检测"。

1. **日志层**：同一条流的 seq 连续（接受架构师的意见）。
   - 桌面工程师提出宿主在 30–50 ms 的时间窗内合并 delta。这一步放在**落盘之前**，所以日志本身存的就是合并后的结果，所有客户端看到的一样。
2. **下发层**：对慢连接（手机），网关可以把一段**连续的、属于同一条目的文本 delta** 合并成一个区间事件。
   - 区间事件带 `seq_from`（区间第一个 seq）和 `seq`（区间最后一个 seq）。
   - 合并窗口可以按连接设置，在 `initialize` 的 `limits` 里协商，比如 `coalesce_ms`，手机取 200–300 ms。
3. **客户端规则**：收到事件时，检查 `(seq_from ?? seq) == last_seq + 1`；不满足就按游标重新订阅。
   - 这样架构师在 `cupper-client` 里设计的缺口检测仍然是精确的，比我第一轮"只看单调性"的写法更严格。我放弃第一轮的写法。
4. **schema 里标出哪些事件类型可以合并**（例如 `x-cupper-mergeable`）。
   - 合并只能发生在一段连续的 seq 内部，中间夹着其他事件就不能跨过去合并。
   - 加一条性质测试：合并后再应用，结果必须和逐条应用完全一样。
5. `stream/reset` 保留，作为发送队列溢出时的兜底。

**理由**：第一轮的估算显示，合并 delta 能把字节数降到约 1/6，帧数降到 1/8。这个收益对手机是必须的。这种写法拿到了这部分收益，同时没有削弱续传的正确性。

## C2 schema 来源，以及 iOS 共用 `cupper-client`

**最终立场**：接受"Rust 类型（serde + schemars）→ 提交到仓库的 JSON Schema → TS 和 Swift"这条路线，不再坚持 Protobuf。理由是：宿主已经定为 Rust，这条路线有 ACP 和 Codex app-server 两个先例，而且 CI 已经有"生成产物和仓库一致"以及"与上个发布版本做兼容性比对"两项检查。

**逐条对照我的四个条件：**

| 条件 | 架构师的路线是否满足 | 缺什么、怎么补 |
|---|---|---|
| ① Swift 能生成类型 | iOS 如果通过 UniFFI 使用 `cupper-client`，Swift 拿到的是 UniFFI 生成的客户端模型，**根本不需要"JSON Schema → Swift"这条链** | 只有放弃 UniFFI、改走 Codable 时，才需要生成器。到时候先在 SP 里实测 quicktype 对 serde 带标签枚举（`oneOf` 加常量判别字段）的支持；不理想就手写一层判别字段分发，其余字段由生成器产出（推）。两条路在 ADR-15 二选一，不同时维护 |
| ② 未知值兜底 | 部分满足：架构师的握手部分已经写了"宽容读取" | 1. schema 里给每个枚举和联合类型标注是开放还是封闭（例如 `x-cupper-open`）。<br>2. Rust 端为开放类型实现兜底变体，例如 `Unknown{type, raw}`，可以用 `#[serde(other)]` 或自定义反序列化（推）。<br>3. TS 端生成 zod 时也要有兜底，因为宿主升级被推迟时，UI 和宿主的版本可能短暂不一致。<br>4. `protocol/fixtures/` 里加入"未知枚举值、未知事件类型、未知字段"的样例，Rust、TS（以及 Swift，如果走 Codable）都必须解出 Unknown，而不是报错。<br>5. 兼容性比对要**区分方向**：宿主发给客户端的消息，删除字段或把必填改成可选都算破坏性变更；客户端发给宿主的消息，新增必填字段算破坏性变更。封闭枚举新增成员也算破坏性变更。新的交互请求类型必须用 `features` 门控，也就是第一轮说的"必须理解"语义，由宿主强制执行 |
| ③ 二进制 | 不满足：M1 只有 JSON，二进制只能 base64 | 帧头现在就预留"帧类型"，例如 0 表示 JSON、1 表示二进制 blob 块。M1 不实现二进制，M3 在握手里协商。blob 块大小见 C3 |
| ④ 多语言 | 满足：以 Rust 为源，生成 TS，Swift 走 UniFFI 或 Codable | — |

**补充一条**：架构师在前置条件里写的 `request_digest` 是"对请求内容做规范化后的哈希"。我坚持**由宿主计算并下发，客户端原样回显**。原因是 Electron 端用 TS 写客户端，CLI 和 iOS 用 Rust 写客户端，跨语言做 JSON 规范化很难完全一致，一旦不一致就会出现"摘要对不上"，或者"绑定的不是用户看到的内容"。

**对 iOS 共用 `cupper-client` 的看法：同意。** 它的好处是：宽容读取、缺口检测、重同步、命令重试、Noise 都只实现一份，安全评审也只审一份。附五个条件：

1. **共享的 crate 不做 I/O（sans-IO）**：`cupper-protocol`、`cupper-client`、`cupper-crypto` 不内置 tokio，只做"输入字节，输出字节和事件"。宿主和 CLI 在外面用 tokio 包一层。
2. **平台相关的部分留在 Swift**：iOS 的 WebSocket 用 URLSession 或 Network.framework，钥匙串、推送、前后台切换也都在 Swift 里做。理由是：iOS 的系统代理和 VPN、Wi-Fi 与蜂窝网络的切换、自建中继的证书信任，都应该交给系统处理（推）。App 被挂起后再恢复时，由 Swift 显式调用 `suspend()` 和 `resume()`，触发重连。
3. **UniFFI 的边界划在客户端模型这一层**（会话列表、条目、交互请求的投影），而不是每条线上消息都穿过一次 FFI。事件通过回调接口推给 Swift；要实测每秒 30–60 次更新进 SwiftUI 时的线程切换和 Swift 6 严格并发的表现。
4. **NSE 只链接推送解密**（`cupper-crypto` 的一个子集，或者直接用 CryptoKit 的 HPKE），不链接 `cupper-client`，以免撞上 NSE 的内存限制（推测约 24 MB）。
5. **M1 就在 CI 里加一个冒烟检查**：`cupper-protocol` 和 `cupper-client` 要能编译到 `aarch64-apple-ios-sim`。这代替我第一轮要求的"M1 加 Swift 解码测试"，成本更低，又能防止这两个 crate 混入 iOS 上用不了的依赖。用户自己构建 iOS App 需要 Rust 工具链，这个门槛由一键构建脚本和"可选的预编译 xcframework 加校验和"来缓解。

## C3 帧大小上限

**最终立场**：接受"握手时协商，本地默认 1 MiB"，不再要求统一用 64 KB。坚持以下几点：

1. **远程连接协商出的上限，必须能放进一条 Noise 消息。** Noise 单条消息最多 65535 字节，扣掉 16 字节的 tag，明文最多 65519 字节。
2. **48 KiB 的块放不下**：M1 只有 JSON，blob 要转成 base64。48 KiB（49152 字节）转成 base64 是 65536 字节，单这一项就超过了 65519。所以只要还走 JSON，块大小要不超过 **45 KiB**（46080 字节，base64 后是 61440 字节，给信封留出约 4 KB）；M3 协商出二进制帧以后，再放宽到 48 KiB。
3. **事件的形状不能随连接变化。** "大字段换成 blob 引用"的阈值要写进事件模型（ADR-06），对所有连接一视同仁；不能出现"本地看到全文，手机看到引用"的情况，否则两端的内容和审批摘要就不一致了。按连接变化的只能是批量的大小：网关按每条连接协商出的上限来切分 `stream/events` 批次。
4. **E2EE 层不做通用分片。** 一帧对应一条 Noise 消息。如果某一帧超过了连接的上限，宿主返回 `too_large`，并且把它当作程序缺陷处理。CI 加一条性质测试：所有夹具和录制的会话，按远程上限序列化之后，每一帧都不超过上限。

## C4 CLI 认证

**最终立场：采用架构师的方案**：CLI 默认只读；需要写操作时调用 `auth/elevate`，由用户在 UI 上确认；授权绑定到这一条连接；不保存任何凭据；宿主再做尽力而为的血缘检查。**我撤回"凭据存钥匙串加挑战-应答"。**

- **它对"agent 直接执行 cupper-cli"没有额外价值。** 架构师说得对：钥匙串 ACL 信任的是 cupper-cli 这个程序本身，谁执行它都一样。我第一轮真正挡住这条路的，其实是"审批要用户在场"，而架构师的方案里每次提权都要用户确认，已经覆盖了这一点。
- **它对"冒充宿主"也没有额外价值。** 架构师的方案里根本没有可以偷走、可以重复使用的秘密，而且客户端本来就要校验宿主的签名。
- **它剩下的价值只有方便**：可以不经 UI 弹窗就提权，比如 M2 后台模式下 UI 没开的时候。但代价是多了一个能被窃取、能被重放的秘密。真需要时，以后可以在宿主的 helper app 里用 Touch ID 来做用户在场确认，现在不做。

**在架构师方案的基础上补充五点：**

1. **确认框由主进程弹出原生对话框**，不放在渲染进程里，否则渲染进程一旦被 XSS，就能替用户点"允许"（见下面的问题 2）。对话框的内容由主进程直接从宿主获取。
2. **授权有上限**：即使连接一直不断，超过一定时间（例如 15 分钟）也要失效；`interaction.respond` 这类审批权限必须明确申请，并在确认框里醒目标出。
3. **血缘检查对能确认的情况硬性拒绝**：只要能确认申请方是某个适配器进程的后代，就直接拒绝，不弹确认框。这样也能防止 agent 反复申请、靠刷屏让用户顺手点"允许"。同一来源的提权请求要限频。
4. **CLI 永远不能切到完全访问，也不能选 `allow_always`**，和 SEC-9 对手机的限制一致，策略里统一处理"非 UI 的 principal"。我不认为生产版本的 CLI 应该完全禁止写操作，因为 NFR-1 和日常使用都需要它。
5. **只在测试中使用的 principal 不应出现在 release 构建里，要在编译期去掉。**

## 回答桌面工程师

**(1) iOS 用 SwiftUI 原生，还是在 WKWebView 里复用桌面的渲染组件？**
- 用 SwiftUI 原生。审批和提问卡片、所有能触发命令的界面，**永远不放进 WebView**。
- MB-3 的消息流用原生方式排版。只读 diff（MB-8，P1）将来如果用原生做成本太高，可以考虑在 WKWebView 里只读展示，到时候再决定。
- 所以现在不需要给渲染组件加 WebKit 的 CI。

**(2) 针对"渲染进程 XSS 后替自己批准"，除了 CSP、清洗、内容摘要，还要求什么？**
先说明一点：内容摘要挡不住 XSS，因为被控制的渲染进程同样能拿到摘要并原样回显。摘要防的是"批准了一条已经变了的请求"。我要求的额外防线有四条：
- **渲染进程能调用的命令要有白名单。** preload 或宿主桥不能提供一个可以发任意命令的 `host.command` 通道。切到完全访问或跳过审批、选择 `allow_always`、批准 CLI 提权、M3 的配对和撤销设备，都不在渲染进程的 API 里，只能走主进程的原生确认框，确认框的内容由主进程直接从宿主获取。
- **普通审批要求真实的用户操作。** preload 在转发 `interaction/respond` 之前，检查 `navigator.userActivation.isActive`。脚本合成的点击和按键不会产生用户激活，所以纯脚本层面的 XSS 绕不过去（推，需要在 SP-4 或 SP-6 实测；如果渲染进程本身被内存漏洞攻破，这条防线无效）。
- **审批卡片出现后有输入保护延迟（约 500 ms）**，Enter 键只在焦点位于卡片上时才表示批准。这样既能防止"正在输入框里打字、卡片突然弹出、一个回车就批准了"，也能拦住即时的自动点击。
- **宿主侧记录审计**：每次审批记录处理者、从卡片显示到批准的间隔。间隔异常短的，在 UI 上标出来。

**(3) 桌面通知上能不能带"批准"按钮？**
- **M1 不带。** 通知上只放"打开"和"拒绝"。理由是通知只能显示截断后的摘要，用户可能在没看全命令的情况下就批准了，这违背了"批准要绑定到用户看到的内容"。
- **以后如果要加**，限定在以下条件：只对"仅本次"这一个选项开放；只在请求内容能在通知里**完整显示、不被截断**时才出现；要求设备已解锁（推，Electron 能否设置这一项要实测，可能需要原生代码）；由主进程处理按钮事件，并带上摘要。
- iPhone 锁屏通知上的批准（M3）采用同一套规则，另外还要加上设备密钥的签名。
