# M1a 退出的性能闸门不在作者机器上跑

- 日期：2026-11-02
- 参与：用户、编排者
- 形式：会话中的决定

## 背景

M1a 退出候选 ec459fd 在 GitHub 上的四项都通过了：
- `ci` 的 8 个检查（41413977102）；
- nfr1 连跑 20 次（41414667873）；
- 降速变体 5 次（41414671830）；
- nightly（41414675363）。

按计划 1.8 和 T099 的任务书，还剩一项：在作者机器上跑 `cargo xtask ci nightly`，约 45–60 分钟，期间用户离开机器。这一项产出 PERF 闸门的 5 个编号（PERF-host-cold-start、PERF-index-snapshot、PERF-host-memory、PERF-snapshot、PERF-bridge-gate）和 IT-sys-peer-current。

编排者向用户说明了这项放在本机的原因：
- 托管 runner 是共享虚拟机，速度波动大。当天就见到单个用例从 16 秒跳到 40 秒左右（T208），不适合作性能参考机（T197）。
- IT-sys-peer-current 按定义是作者真机上的结果。

编排者也列了替代办法：改用 GitHub 的大型 runner 并重新标定阈值，或者把 PERF 降为只记录、不卡闸门。

## 决定

- **D1**：压测不在用户的电脑上做，先放一放。用户原话："嗯 压测不在我的电脑上做，先放一放吧"。
- **D2**（编排者据 D1 定）：
  - T099 照常完成其余各项。
  - PERF 的 5 个编号和 IT-sys-peer-current 在记录里列为缺口，写明原因（D1）和可选的替代办法，交 M1a 同步会由用户决定。
  - 以后不安排在用户机器上跑 PERF 或本机 nightly。
