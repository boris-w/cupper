# 设计评审：安全工程师

## 总体结论

**修改后可以进入 gate/design。** 本地认证主干站得住：固定令牌加 nonce、编译期写入的签名要求、CLI 默认只读加用户确认、`allow_always` 和完全访问只能走原生确认框。这三条阻断都不需要推翻 ADR，只需细化 ADR-05、ADR-08、ADR-10：
- 宿主自动执行的 git 会运行仓库配置指定的程序；
- SDK 模式下没有工作区信任环节，恶意仓库的 hooks 会直接运行；
- 风险等级为 `elevated` 的权限模式没有纳入审批授权的范围。

其中前两条是 agent 拿不到套接字也能走通的路径：它绕过宿主，借宿主或 CLI 在沙箱外执行代码。所以这两条比握手本身更要紧。

## 对待定问题的意见

| 问题 | 意见 |
|---|---|
| Q1 连接模型 | **同意**用 control 连接加"每个窗口一条数据连接"。安全上的前提：<br>- 角色由主进程在 initialize 时确定，之后不可变；<br>- 宿主拒绝重复的 initialize；<br>- 主进程转发出方向消息时重新序列化，只放行 0x01 和 0x02 帧（第 4 条）。<br>如果以后退到 utilityProcess 方案，委托票据要绑定到具体的窗口连接和角色 |
| Q4 codex-acp 随包 | **同意随包。** Apache-2.0 允许分发，还少了一次联网安装带来的攻击面。条件：<br>- CI 按 npm 的 SRI 校验上游文件；<br>- 清单记录 sha-256，拉起前核对；<br>- 附带 22 个内联依赖的许可证声明；<br>- 与第 2 条一起实测 codex-acp 会不会自动信任 cwd |
| Q11 threadStatus 与回合边界 | **同意**：有 prompt 在途时，以 prompt 的响应为准。安全上要保证一点：`threadStatus` 变为 idle 不会让还挂着的交互请求失效或被收起（K12 的场景），只有撤回、中断、适配器退出才会 |
| Q14 晚到的工具输出 | **同意**不把它放进新回合，**但不建议把内容丢掉**。用户需要知道命令在取消之后还在产生副作用。建议：<br>- 把晚到的输出附在原来那个已取消的工具条目上，默认折叠，标"取消后仍在运行"；<br>- 原始帧照常保留；<br>- Codex 的回合一被中断，就立即提示"命令可能仍在运行"（K3 是已知行为），不要等晚到的输出出现才提示 |
| Q3 Node 公证 | 建议**直接采用后备方案**：把重签的 `node` 作为普通 Mach-O 放进 `CupperHost.app/Contents/Helpers/`，随 App 一起公证。这样公证覆盖到 Node，也不必另写 tar.xz 的解析。安装时复制出来，照样核对 cdhash |
| Q5 bundle 前缀 | 同意在 gate/design 时确定。从安全角度：要选项目自己控制的域名，因为它会写进签名要求、钥匙串 ACL 和 TCC 授权，以后改动的代价最大 |

| Q22 退化模式 | **同意接受**，不要把密钥存进钥匙串或文件。附加条件：<br>- 退化模式只由编译特性决定，不允许运行时回退；<br>- 自行构建的版本使用开发构建的身份和独立的数据目录，不与发布版共用 `cupper/`；<br>- 发布产物检查见第 12 条 |

## 认可的部分

- 固定令牌、nonce 回显、每次读取都比对令牌（含 pidversion），把 SP-4b 发现的 G2–G4 都堵上了；任何校验错误都按拒绝处理，并分四类记录。
- 签名要求在编译期写入，加了 Developer ID 的标记 OID 和动态状态字检查；UI 和 CLI 都反向校验宿主。
- CLI 默认只读、不发放可信凭据；授权绑定到连接和固定令牌，有效期最长 15 分钟。
- 协议常量 `SCOPE` 加表驱动的矩阵测试；`allow_always` 一律算 privileged，并按工具区分是否持久，判断不出来就当作持久；不认识的权限模式按完全访问处理。
- SEC-10 的数据基础：摘要回显、`actionable_by`、请求所属的适配器实例，以及适配器退出或宿主重启后请求失效。
- 运行时安装：清单在编译期内嵌；拉起前核对 cdhash 和 sha-256；不运行包脚本；本机打包的产物哈希固定、可在 CI 预先算出。
- 进程卫生：环境变量白名单、去掉 `CUPPER_*`、argv 和环境变量里不放任何秘密、dev 密钥只经 stdin 传递。
- 渲染进程永远拿不到套接字；CSP 加 Trusted Types；原生确认框的内容由主进程经 control 连接从宿主获取，默认按钮是取消。
- 选用 electron-builder 的理由是安装时机由我们控制，这个理由成立；`_auth/status_update` 只保留类型（K16）。

## 核实记录

- **Security 框架源码**（[apple-oss-distributions/Security，`OSX/libsecurity_codesigning/lib/Code.cpp`](https://github.com/apple-oss-distributions/Security/blob/main/OSX/libsecurity_codesigning/lib/Code.cpp)）：`SecCode::checkValidity` 调用了 `validateNonResourceComponents`，没有调用 `validateResources`。结论：宿主每次连接做的校验不覆盖包内资源（第 17 条）。
- **Electron**：[GHSA-vmqv-hx8q-j7mg / CVE-2025-55305](https://github.com/electron/electron/security/advisories/GHSA-vmqv-hx8q-j7mg) 在 35.7.5、36.8.1、37.3.1、38.0.0-beta.6 修复，只影响同时开了两个完整性 fuse 的应用。修复提交"fix: ensure snapshot is valid"（#48102、#48104，经[镜像页](https://ayakael.net/mirrors/electron/commit/3f92511cdecc39f46b0e86cce40a0c691e301c9d)查看）在 `EnableEmbeddedAsarIntegrityValidation` 打开时校验 V8 快照的 SHA-256。背景见 [Trail of Bits 2025-09-03 的文章](https://blog.trailofbits.com/2025/09/03/subverting-code-integrity-checks-to-locally-backdoor-signal-1password-slack-and-more/)。**部分核实**：没有看到 macOS 专门的代码路径，从提交内容看不分平台。
- **Claude Code 官方文档**：[Permissions：What runs before you trust a folder](https://code.claude.com/docs/en/permissions) 写明，SDK 会话不显示信任对话框；仓库里的 hooks、`env`、`apiKeyHelper` 照常使用；settingSources 含 project 时，`.mcp.json` 的服务器不经询问直接连接。[Security](https://code.claude.com/docs/en/security) 页写明 `-p` 会话两种提示都不显示。**未核实**：claude-agent-acp 实际使用的 settingSources，以及能否经 `_meta` 传入 SDK 选项。
- **Codex**：[官方配置文档](https://developers.openai.com/codex/config-advanced)（经搜索摘要）说项目 `.codex/` 配置只在信任后加载。SP-4b 实测 `codex exec` 会自动写入信任项。**未核实**：app-server 和 codex-acp 会不会自动信任 cwd。
- **Claude 沙箱禁写 `.git/hooks`、`.git/config`、`.husky`**：来源只有 [claudeissues.com 上转载的 issue](https://claudeissues.com/issue/66288-bug-sandbox-git-internals-write-protection-resolves-paths-against-the-worktree-r)，属于二手资料，**未在 sandbox-runtime 源码核实**。官方文档提到 `.git`、`.claude` 属于受保护路径。
- **git**：[githooks](https://git-scm.com/docs/githooks) 写明 post-checkout 在 `git worktree add` 之后也运行（除非 `--no-checkout`），hooks 目录可以由 `core.hooksPath` 改到别处，`core.fsmonitor` 会调用钩子程序。
- **electron-updater**：读了 `MacUpdater.ts`，版本是 tag `electron-updater@6.8.3` 和 master（6.8.10 没有直接读）。代理服务器在下载完成后的 `updateDownloaded()` 里创建，监听 `127.0.0.1:0`；根路径用随机的 64 字节口令做 Basic 认证；zip 放在不需要认证的随机路径下；只在 `handleUpdateDownloaded` 或下一次下载完成时关闭。`autoInstallOnAppQuit=false` 时，`checkForUpdates` 只在 `quitAndInstall` 里调用。
- **Squirrel.Mac**：读了 `SQRLCodeSignature.m`。校验用的要求取自 `SecCodeCopySelf` 的 designated requirement；`SecStaticCodeCheckValidityWithErrors` 的标志是 `kSecCSCheckNestedCode | kSecCSStrictValidate | kSecCSCheckAllArchitectures`。"资源也被校验"是根据默认标志推断的。
- **GitHub**：[Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use) 写明，自托管 runner 几乎不应该用于公开仓库。
- **仓库内的录制**：`spikes/SP-1-adapter-behavior/recordings/`。Claude 的模式取值有 default、acceptEdits、plan、auto、bypassPermissions；Codex 有 read-only、workspace-write、agent（Auto review）、agent-full-access，录制里 Codex 的当前值是 `agent`。SP-1 声明的 `fs`、`terminal` 都是 false。
- **未核实，凭已有知识**：
  - `nodeCliInspect` fuse 同时屏蔽 SIGUSR1 打开调试器；
  - Electron 会响应 `--remote-debugging-port`；
  - 用不带控制缓冲区的 `read()` 读套接字时，XNU 会丢弃并关闭 SCM_RIGHTS 传来的 fd；
  - Claude Code 和 Codex 拉起工具命令时会不会 setsid（Codex 的 PTY 执行很可能会）；
  - husky 默认把 `core.hooksPath` 设为 `.husky/_`。

整个评审只读，没有创建、修改任何文件，也没有在仓库里运行构建。外发请求只有公开文档和源码的读取，不含任何个人信息。
