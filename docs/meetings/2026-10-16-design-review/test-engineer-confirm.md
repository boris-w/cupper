## 阻断项能否关闭

**测试 #1：附条件关闭。** Clock 接口、纯核心的 `step(input, now)`、`AcpTransport`、`test/clock_advance`，再加上 `disallowed-methods`，已经覆盖了我提的问题。写线程 2 ms 攒批不归 Clock 管，可以接受。方案本身不用改，修订稿只需补写三点规格：

1. **写明 `test/clock_advance` 的返回时机。** 推进时钟后，要等到期的定时器全部触发、由此产生的 Action 都执行并落盘，宿主才返回。否则推进时钟时，actor 可能还在处理上一批输入，定时器和消息的先后顺序仍是随机的。进程内的 B 层回放也一样：当前帧引起的动作全部处理完，才推进到下一帧的 `t`。等外部进程（假 agent）的地方，仍用事件做屏障。
2. **补全禁用清单。** 除现有几项外，再加：
   - `Instant::elapsed`、`SystemTime::elapsed`；
   - `tokio::time::Instant::now`；
   - `std::thread::sleep`。

   UUIDv7 也要经 Clock 或可注入的 ID 生成器来生成。否则用 ManualClock 时，ID 里的时间和事件的 `ts` 对不上。
3. **测试里不要完全关掉攒批，改成"攒够数量或队列为空就刷出"。** 组提交会把不同 actor 的操作放进同一个事务。其中一个操作失败时，同批的其他操作怎么处理（需要 savepoint），只有开着攒批才测得到。存储层单元测试和"高负载下反复 `kill -9`"的崩溃测试，都要在开着攒批时跑。

**#13 键盘输入**

这个测法能覆盖 AP-1 的规则和链路。本轮在 Electron 34.5.8 上复测：

- `sendInputEvent` 发出的 Enter 会触发 `before-input-event`；
- 页面收到的 keydown 是 `isTrusted: true`。

所以按键白名单、"每次输入只能用一次"、冷却、"Esc 只能用于拒绝"这些规则，以及"主进程 → 卡片 → 宿主"整条链路，在 e2e 里走的都是生产代码。主进程里的 `blur()` 和 `focus()` 也能触发窗口事件，冷却用例可以测。

剩下的差距只有一点：操作系统的实体按键会不会触发 `before-input-event`。这一点自动化补不了：Playwright 和 `sendInputEvent` 都不经过系统的按键事件；用 CGEvent 发系统级按键需要辅助功能授权，CI 上大概率拿不到（未核实）。所以除了 Q26 的复测，只能靠实体键盘人工确认。我接受，但有两个条件：

1. 人工确认写进人工验证清单，每次升级 Electron 大版本都做一遍，检查三件事：Enter 批准、Esc 拒绝、用输入法选词时不触发。只做一次不够。
2. 加一个自动用例，断言 e2e 中 inputGuard 记录的输入证据来自 `before-input-event`。这样 Electron 升级改变了这个行为时，CI 会先报出来。

另外，同一实验显示，`input-event` 的键盘事件在运行时其实带了 `key`、`code`、`isComposing`、`isAutoRepeat`，只是类型定义里没有。建议 Q26 复测时一并确认，留作后备方案。

**#18 外发检查与 Seatbelt**

本轮实测：用 `sandbox-exec`（只拒绝出站网络）包住 Electron 34.5.8 启动，Chromium 的子进程在初始化自己的沙箱时报 "sandbox initialization failed: Operation not permitted"，GPU 进程、网络服务和渲染进程都崩溃了。

所以 Seatbelt 只能用在宿主集成测试里：测试直接拉起宿主进程，可以在外面套一层。整个 App 的外发检查要改用 nettop 采样或其他办法。Q27 需要按这个结果修正。

**#19 晚到输出（方案 (b)）**

方案可行，但金样例的写法和 #5 自相矛盾：

- A 层是逐帧的纯函数，不知道回合和取消，断言不了"t1 里有 `abandoned` 加 `may_still_run`、t2 里有一个 `late_tool_output`"这种回合结构；
- B 层按 #5 只用宿主自己驱动产生的录制，而 codex s07 是 SP-1 客户端录的，不能用于 B 层。

建议改成三层分别断言：

- A 层只断言晚到的帧被提取成带原 `toolCallId` 的 ToolUpdate；
- 回合结构由"宿主集成测试 + 假 agent（codex 形态的 `late_tool`）"断言；
- B 层等 M1b 用宿主重新录到 codex 的取消场景后再补。

另外补两项：

- 一条不变式，作为性质测试和金样例检查：回合快照写入之后，日志里不再出现指向这个回合的事件；
- TS 和 Rust 视图里的 `late_by_ref`，纳入每晚的差分测试。

## 对其他统一方案的意见

**(d1) 兼容套件只在本机运行**

可行。补三个条件：

1. 报告要有 JSON schema。CI 校验已提交的报告，并从报告重新生成"已验证范围"，与清单比对，不一致就失败。这样"不手填"才有检查兜底。
2. `xtask compat` 的框架在 CI 里用假 agent 跑一遍，不调用真实 CLI。否则这段只在本机偶尔运行的代码会慢慢坏掉，没人发现。
3. 报告里记下三项：cupper 的提交、运行模式（隔离配置还是真实配置）、模型。

**(d3) 注入点表、stdin 传 JSON、`CUPPER_E2E_DIR`**

可行。补两个条件：

1. **门控与读取超时**：
   - 读取 `CUPPER_E2E_DIR`、解析 stdin JSON 里的 `harness_key` 和 `test_config`，都要在编译期门控；
   - d2 的"不带特性的测试"加一条：发布特性的宿主收到带 `harness_key` 的 stdin 时，拒绝 harness 认证，并忽略 `test_config`；
   - 宿主读 stdin 要有超时，防止拉起方忘了关 stdin、启动一直卡住。
2. **原生对话框的替换**：
   - 替换函数要记录调用参数，测试断言确认框里显示的操作描述，以证明用户确认的是正确的操作；
   - 主进程代码要在调用时才经 `dialog.showMessageBox` 取函数，不能在模块加载时解构保存，否则 `electronApp.evaluate` 的替换不生效。这一条写进 5.1.7 的代码约束。

**epoch 机制（安全 #12 的补充）**

可以测，前提是两个输入都能注入：

- 启动会话的 UUID，由 test-config 覆盖；
- "上次是否正常退出"，从 meta 读取。

用例：

1. **纯函数决策表**：正常退出或异常退出 × 同一次开机或已重启。只有"异常退出并且重启过"时 epoch 才加 1。`kill -9` 不加，因为进程崩溃时 WAL 不会丢数据。
2. **模拟断电丢数据**：
   - 客户端停在 seq N；
   - 停掉宿主，把 `host.db` 和 WAL 换成 seq M（M < N）时的副本，改掉启动 UUID，并标成异常退出；
   - 重启宿主后，客户端带着旧 epoch 和 N 订阅，必须走快照；
   - 之后的新事件会从 M+1 起重用 seq，Rust 的 Mirror 和 TS 的 host-client 都要整体重置，不能报"seq 重复"。
3. **游标超前**：epoch 相同但 `after_seq` 大于 head 时，按 `cursor_ahead` 走快照。
4. **误判**：`kill -9` 之后用户正常重启电脑，也会被判成断电，只多一次全量快照。用例记下这个行为。

**M1a 退出标准"连续 20 次全绿"**

同意。补充口径：

- 在退出候选的同一个提交上跑；
- 按 CI 平时的并行度运行；
- 不允许重试、跳过或隔离用例；
- 中途失败一次，查明根因后计数清零。

**U-R4、U-R5**

- **U-R4**：同意首选隔离配置，报告里记下用了哪种模式。Claude 的凭据如果存在钥匙串里，隔离 `CLAUDE_CONFIG_DIR` 后可能仍然读得到（未核实），可以和 Q30 一起确认。
- **U-R5**：同意。注意 SP-1 的 TS 客户端产出的录制只能进 A 层。

**建议级 #22–#26**

处理方式全部同意。
