## 对再确认点的表态

### (b) `late_tool_output`：同意

反向索引在实际使用中几乎总能命中。历史按从新到旧加载，视图淘汰的是旧回合；晚到条目所在的回合总比原回合新，所以原回合在内存时，晚到条目一定也在。

有三点在实现时处理即可，不需要再议：

1. `late_tool_output` 与 `notice`、`error` 一样，画在回合折叠之外。否则当前回合结束收起后，用户就看不到"取消后仍在运行"。
2. 它不并入当前回合的活动组，也不参与 #8 的判定（见下一条）。
3. 建立反向索引时，要让原条目所在的行重新渲染。也就是说，按条目订阅的 store 要支持"因为别的条目而变化"。

### #8 由宿主判定"最终回答"：同意，规则要补边界

1. **判定时只把 `tool_call`（和组内的 `thought`）算作"非消息条目"。** `late_tool_output`、`notice`、`error`、`plan`、交互请求都不算。否则晚到输出一旦排在最终回答之后，这个回合就没有最终回答了。
2. **写明始终显示在折叠之外的条目**：
   - 最终回答；
   - `plan`；
   - `error`、`notice`、`late_tool_output`；
   - 未处理的交互卡片；
   - Steer 插进来的用户消息（用户自己说的话不应收进"用时"里）。
3. **回合以工具调用结束、后面没有文字时**，`final_item_ids` 为空，界面只显示折叠标题。这可以接受，写明即可。Claude 的一次回答常拆成多个 `message_id`，`final_item_ids` 是列表，正好覆盖这种情况。

### (a) 审查用的 diff 放进单独源的 iframe：可以作为主方案，同意后备方案

代价与风险如下，都应列入 Q29 的验证或写进 5.7.5：

1. **进程与内存。** `app://cupper` 和 `app://cupper-review` 的主机不同，开启站点隔离时很可能成为进程外 iframe（未核实），也就多一个渲染进程，再加一份 React、pierre 和 Shiki。首次打开审查面板有冷启动成本。
   - 建议首次打开后常驻（隐藏而不销毁），并在空闲时预加载。
   - SP-6 的 5,000 行 diff 场景要计入 iframe 的冷启动时间和内存。
2. **焦点与快捷键。** 焦点在 iframe 里时，主文档的 keydown 监听收不到按键。
   - 全局快捷键一律注册为菜单加速键，经 `onCommand` 送达；
   - iframe 只处理自己的键（Esc 关闭评论框、⌘Enter 提交），其余按键通过消息转给父文档。
3. **真实输入可能被"借用"。** 要核实 `before-input-event` 和 `input-event` 对子框架里的按键和点击是否触发。如果触发，用户在 iframe 里写评论时按的 Enter 会被 inputGuard 记成一次真实输入，主文档可以借它去批准审批。inputGuard 应只记录主框架获得焦点时的输入（用哪个 API 判断当前聚焦的 frame，未核实）。
4. **主题、语言与字号的同步。** 初始化消息要传主题覆盖、语言、文案和缩放比例；设计 token 打成一份 CSS，两个入口共用。如果用了随包的字体，跨源加载需要 CORS（`corsEnabled` 特权加上相应的响应头）。
5. **行内评论与 hunk 操作。**
   - iframe 只做无状态的视图：评论草稿、文件展开状态、当前滚动到的文件都由主文档持有并下发，iframe 重载也不会丢草稿；
   - 消息协议要有版本号，两个方向都用 zod 校验；
   - 暂存和还原按钮在 iframe 里，只发出 `hunk_id`，由父文档按 `diff_token` 校验（与回应一致）。
6. **剪贴板。** 跨源 iframe 使用异步剪贴板需要 `allow="clipboard-write"`：按 Permissions Policy 的默认值，这项能力只给同源（未在 Electron 上实测）。权限处理器也要放行审查源。
7. **滚动联动。** 文件列表在主文档、diff 在 iframe 里。点击文件、从消息流的编辑条目跳转，都要通过消息让 iframe 滚动；iframe 占满面板高度，避免出现两层滚动条。
8. **复刻度。** 原样使用 pierre，视觉和交互最接近 Codex，这是主方案最大的好处。后备方案要自己写虚拟滚动和 hunk 交互，复刻度和工期都更差，只在 Q29 验证不通过时启用。

### 主文档放行 `style-src 'unsafe-inline'`：桌面侧同意

- 原始 HTML 已经关闭，脚本注入被 Trusted Types 和 `script-src` 挡住，所以内联样式只能由已经在运行的脚本插入。
- 这样也省掉了按次生成 nonce 的整套管道。

最终以安全工程师的确认为准。

## 对其他统一方案的意见

### (c) 真实输入规则

都能实现，成本低。补两点：

- **窗口激活后的 1 s 冷却会让一个常见动作失败**：点通知回到窗口、立刻按 Enter 批准。渲染进程收到 `user_activation_required` 时，应在卡片上提示"请再按一次"，不要弹出错误 toast。`window.onFocusChange` 可以带上获得焦点的时间，让卡片等冷却结束后再接受 Enter。
- `sendInputEvent` 的方案可以。`page.click()` 是否真的产生 `input-event`，也一并列入 Q26 复测。

### (e) M1a 界面元素与测量闸门

M1a 新增的界面元素清单，我同意。测量闸门有三点要改：

1. **负载要按订阅上限来定义。** 一个窗口最多订阅索引流加 4 条会话流（当前会话加最近 3 个），而回应写的是"6 条流各每秒 200 个片段"，超出了这个上限。用它做判定，可能为一个实际碰不到的负载触发后备方案，而后备方案要修改 ADR-05 和 5.8.1。
   - 建议判定负载为：索引流、4 条会话流、一个 5 MB 的 blob、一次 5,000 个事件的重新同步。
   - 负载按线路上的帧数和字节数给出，也就是经过宿主 40 ms 写入合并之后，每条流每秒多少帧、多少 KB。
   - 6 条流的结果只作为压力报告，不参与判定。
2. **消费端必须是真实的渲染进程**，例如一个隐藏窗口经 MessagePort 接收并确认，不能在主进程里打桩，因为 MessagePort 的序列化开销落在主进程上。
3. 窗口可见和被遮挡两种状态各测一次。

### 订阅策略（当前会话加最近 3 个）

同意。补两点：

- 从通知、或从"下一个需要处理的会话"跳转过去的会话，通常不在 LRU 里，会走缓存未命中的路径。150 ms 的预算正好覆盖这种情况，SP-6 的"切换会话"场景要包含这条路径。
- 会话被淘汰时退订并丢弃视图，但保留它的草稿和滚动位置。这两样属于界面状态，不在视图里。
