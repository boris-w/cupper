## 各议题结论

### 1. 平滑演进

- 架构师支持"会话宿主"方向，同时比较了三个替代方案并逐一否决：UI 直接持有 ACP、宿主对外讲 ACP、宿主对外讲 Codex app-server 协议。
- 架构师的核心观点：NFR-1 只写了目标，没写出约束。真正不可逆的是宿主与客户端之间的契约，共 10 项：访问边界、协议语义、事件日志、状态计算、交互请求对象、授权钩子、领域模型、瘦客户端、南向解耦、迁移机制。
- **编排者：采纳。** NFR-1 改写为架构师建议的文本，M1 验收要求一个独立进程的第二客户端，用同一套协议完成全部手机端需要的操作。宿主的具体进程形态（App 拉起的子进程，还是登录项常驻）留给 ADR-01，但"与界面分离"写进 PRD。
- 架构师认为设备密钥可以推迟到 M3，M1 只需落下授权钩子和 host_id，这一点与 R03 A4 的看法不同。**编排者：采纳架构师的意见。**

### 2. 架构骨架

- 架构师给出了组件清单、组件图、8 个接口、宿主协议的消息类别、关键数据流（流式输出、审批先到先得、断线续传、推送），以及"PRD 能力 → 组件"的映射表。
- **编排者：作为阶段 ② 技术设计的起点。** PRD 只吸收其中的产品级约束（NFR-1、NFR-2、SEC-8），不写组件细节。

### 3. 可行性与范围

架构师指出 PRD 与调研之间有 10 处不一致，另有 15 条需求做不到、代价过高或有隐藏前提。**编排者全部采纳**，其中改动较大的有：

| 事项 | 结论 |
|---|---|
| AG-1 与 NFR-5 的冲突：适配器默认用自带的 agent 程序，随包分发还涉及 Anthropic SDK 的再分发许可 | agent 程序用本机 CLI；适配器由 cupper 锁定版本，但不随包再分发受 Anthropic 商业条款约束的组件；Node 运行时的来源由 ADR-08 决定，由 SP-2 实测 |
| Steer 只能靠 agent 私有扩展 | 排队由宿主实现，是主路径；Steer 探测到才启用，失败时转为排队 |
| ACP 没有"本会话"这种审批范围 | 选项和文案以 agent 给出的为准；会持久生效的选项要在界面上标明 |
| 保密承诺过宽 | G3 限定在 cupper 自身的链路上；SEC-1 改为"路由元数据加密文" |
| worktree 提到 P0 | 架构师同意，但 P0 只做"最小 worktree"（新建有名字的分支，安全清理）；setup 脚本、复制被忽略的文件、Handoff 放 P1 |
| 集成终端（UI-1） | 架构师建议降到 P1，P0 改为"在外部终端或编辑器中打开"。**待用户确认**（见 U2） |
| 生成提交信息 | 降到 P1；提交和推送保留 P0 |
| M1 内部分两步 | 采纳：M1a 先做宿主骨架加 Claude，M1b 再做 Codex、Git 和 worktree |
| M3 的中继改为无状态，密文缓存和离线历史移到 M4 | 编排者赞同，可以大幅缩小 M3 的密码学范围。**待用户确认**（见 U1，涉及原问题 9） |
| 推送方案 | 统一为"桌面按设备加密、通知扩展解密、失败时显示通用文案"（R03 的 N-2） |
| 自建 iOS 的前提 | 推送需要付费的 Apple Developer Program 账号，写进 PRD 的前提条件。**待用户确认**（见 U7） |

架构师还提出一个产品侧的观察：用户目前在 Codex 里用的是"帮我批准"（Approve for me），cupper 没有对应的能力，审批次数可能明显上升，影响 G1。**编排者：认同这个风险，列为待用户确认事项（U6）。**

### 4. 遗漏

**编排者采纳以下新增需求**：

| 类别 | 新增需求 |
|---|---|
| 会话与交互 | PS-8 重启后会话可以继续；AP-5 结构化提问 |
| 非功能 | NFR-8 宿主生命周期；NFR-9 崩溃恢复；NFR-10 升级与迁移；NFR-11 容量；NFR-12 诊断；NFR-13 电源 |
| 安全 | SEC-8 本地接口鉴权；SEC-9 手机权限边界；SEC-10 交互请求绑定；SEC-11 静态数据说明 |
| 移动端 | MB-11 多台 Mac；MB-12 推送防打扰 |
| 中继 | RL-5 中继运维 |
| 合规 | "cupper 不改写 agent 配置文件"原则 |

对优先级的一处调整：NFR-12 诊断，架构师建议整体定为 P0。编排者把"本地日志、收集适配器 stderr"定为 P0，"导出诊断包"定为 P1。

### 5. 阶段 ② 的输入

- **ADR 清单**：M1 前 11 份（ADR-01 至 ADR-11），M3 前 4 份（ADR-12 至 ADR-15）。
- **原型实测**：SP-1 至 SP-9。其中 M1 前做 SP-1、SP-2、SP-4、SP-5，SP-3 和 SP-6 视情况而定；SP-7、SP-8、SP-9 在 M3 前做。
- 最关键的两项是 SP-1（两个适配器的行为实测）和 SP-4（宿主骨架走通）。
- **编排者：采纳**，作为阶段 ② 的工作计划初稿，在 PRD 新增的 §11 中列出。

### 6. 对 PRD 的修改建议

架构师的汇总表共约 50 条，标为"高"的全部采纳，"中"和"低"的除上文说明的调整外也都采纳。逐条的处理结果体现在 PRD v0.2 的修订记录中。

## 决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 确认"会话宿主"方向；NFR-1 改写为契约式要求，M1 用一个独立进程的第二客户端做验收 | 防止 M3 返工，这也是用户要求的"平滑" |
| D2 | agent 程序使用本机 CLI；适配器锁定版本；不随包再分发受 Anthropic 商业条款约束的组件 | 解决 AG-1 与 NFR-5 的冲突，同时满足合规 |
| D3 | 排队是主路径，Steer 尽力而为；审批选项以 agent 为准 | 与 ACP 和适配器的事实一致 |
| D4 | 新增 AP-5、PS-8、NFR-8 至 NFR-13、SEC-8 至 SEC-11 等需求 | 补上遗漏 |
| D5 | P0 只做最小 worktree；生成提交信息降到 P1；M1 分为 M1a 和 M1b | 控制 M1 的成本 |
| D6 | 推送统一采用"按设备加密、NSE 解密" | 消除 PRD 内部的不一致 |
| D7 | ADR 清单和原型实测清单作为阶段 ② 的工作计划初稿 | 为技术设计做准备 |
