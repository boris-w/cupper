## 本机执行方案的新问题

1. **本机的 `xtask ci security-macos14` 跑在作者的 macOS 26 上，不代表 macOS 14。** 摘要要记下系统版本，trace-ids 不能把它记成 macOS 14 的覆盖。IT-sys-peer 在 macOS 14、15 上的结果，应当保持"缺口"状态。
2. **逐个编号的结果没有进仓库。** 入库的只有作业级的通过数和失败数，trace-ids 读的原始报告在 `.private/`。到里程碑退出时，"待完成为空"无法从仓库复核。建议摘要里加一份逐编号的结果清单（编号、套件、结果、提交）。编号本身不含个人信息。
3. **同一台机器上的资源争用。** 3–4 个子 agent 和编排者可能同时跑 `xtask ci pr`，其中有 e2e 冒烟、截图和连跑 10 次，互相抢 CPU 会造成计时类的误报。作者在 T099 以外操作机器，也会影响焦点和冷却类用例。建议：
   - e2e、`ui`、性能、nfr1 这几类作业加一把机器级的锁，串行运行；
   - "Playwright 并行度同 CI 设定"在 T090 里写成具体数字。现在没有 CI 设定可以参照。
4. **截图元数据里"系统版本对不上就失败"写得太死。** macOS 的小版本会自动更新，一更新，所有分支的 `xtask ci ui` 会同时失败。字体已经随夹具附带，建议：
   - Chromium（Electron）版本严格比对，macOS 只比大版本；
   - 小版本变化时给出提示，有像素差异才重新生成基线。
5. **"干净 worktree"要写清楚含义。** 它指 git 状态干净，构建缓存可以共享；但 e2e 的 App 和 `CupperHost.app` 必须由当前提交构建，摘要记下产物的哈希，防止测到别的 worktree 留下的旧产物。另外，性能趋势的"历史中位数"需要入库的历史数据（脱敏后的数值序列），否则每一波跑一次的 nightly 没有可比的基线。
