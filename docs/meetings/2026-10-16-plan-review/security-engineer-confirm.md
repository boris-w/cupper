## 部分接受的三条

- **#11（E2E-SEC-no-key-client）：接受。** 我第一轮的原意就是"拿不到 desktop_ui"。按 5.8.2，同 uid 的客户端本来就可以只读接入。补一条断言：客户端出示 `auth: dev_key`、但证明错误或缺失时，必须得到 `unauthenticated` 并被断开，不能悄悄降级成只读的 cli。否则"证明失败"与"本来就是只读客户端"在用例里分不开。
- **P-14：接受。** T102 先用"备份 + 差异报告"。三点要求：
  - 备份覆盖 `~/.codex/config.toml` 和 `hooks.json`，存放在仓库之外，权限 0600；
  - 差异报告单独列出新增的 `[projects]` 信任项；
  - spike 只在临时仓库里运行，不读写 `auth.json`。
- **#10 / P-19：同意采纳。** 这个写法没有绕过的漏洞，对 e2e 的 harness 认证也没有影响。有四处需要改：
  1. **不要在启动时按 ppid 去查父进程的启动时间**：如果父进程刚好已经退出，查到的就是别的进程。改用 `proc_pidinfo` 的 `PROC_PIDUNIQIDENTIFIERINFO`：宿主读自己的 `p_puniqueid`，这是 fork 时就写进来的父进程唯一 ID，没有竞态；校验时取对端的 `p_uniqueid` 比对。字段名凭记忆，由 T021 实测确认。实测不可行时，再退回"pid + 启动时间"。
  2. **启动时如果 ppid 已经是 1**（父进程已退出），`dev-auth` 构建的宿主直接以错误码退出，不再等待任何 `dev_key` 连接。
  3. **范围只限 `dev_key`**：`harness` 认证不受影响。实现时核对 T030、T033、T073 的集成测试，确认 dev_key 都由拉起宿主的那个测试进程自己出示；目前的设计里没有例外。`pnpm dev` 重启 Electron 时一并重启宿主，这一点设计里已有。
  4. **建议**：父进程退出后，宿主不会再有合法的控制方，挂着的审批没人能处理。建议进入"孤立"状态：不再开始新回合，等运行中的回合结束后有序退出。不这样做，就要等新 UI 走"重启宿主"。

  这条的实际价值有限：只有在密钥经崩溃转储、日志等意外途径泄露时才起作用。但改动小，也不会让人误以为认证变强了，所以值得做。

## 更正与 CLI 校验宿主的问题

**更正：确认。** 退化模式下，CLI 按 uid 以只读身份接入；需要写入时提权，由 UI 的原生确认框批准，这条路在退化模式下照常工作。我第一轮对 P-6 说的"退化模式下 CLI 连不上宿主，所以隐藏 `install_cli`"出自同一个错误前提，撤回。相应要改：
- 7.3 中 K7 不通过的那一行；
- Q35 的说明。

Q35 的收益改写为：NFR-8 成立，并且 UI 和 CLI 都能按签名身份校验宿主。

**问题：非发布构建的 CLI 无法确认对面是真宿主。这个缺口是真实存在的。**
- **攻击路径**：
  - 有两种办法占住套接字：宿主空闲 10 分钟退出后，路径空着，谁都能绑定；或者同用户进程主动删掉套接字文件、再绑定自己的。
  - UI 有双向证明，能识破假宿主；CLI 识破不了，会把 `send`、`new`、提问的回答这些内容交给假宿主，也会把假宿主伪造的会话、审批和输出当真。
  - 最严重的是劫持提权：假宿主一边作为只读客户端连上真宿主，一边把用户的 `cupper elevate` 转发过去。真 UI 弹出确认框，用户正在等这个框，会点批准，但授权落在了假宿主的连接上。退化模式下真 CLI 也是 ad-hoc 签名，确认框里的签名信息分不出两者。
- **风险**：前提是同用户、在沙箱外有明确恶意的进程，这属于边界说明里"挡不住"的一类。但劫持提权恰好抵消了"用户确认"这条主防线，而补上它的成本很低，所以应该补。
- **建议（选方案一，不选方案二、三）**：
  - 自用构建的 CLI 在**编译期写入宿主的 cdhash**。由 `xtask host-bundle` 先签宿主、拿到 cdhash，再编译和签名 CLI。CLI 与宿主是两个独立的 Mach-O，不存在 UI 与宿主之间那种互相依赖的问题。
  - 连接时，CLI 用审计令牌取对端运行中的 cdhash 比对，并且每次读取都比对令牌（与发布版相同）；不一致就拒绝连接。
  - 攻击者如果想通过，只能运行真的宿主程序，而真宿主照样执行真实的策略，最多换一个数据目录来展示假数据。改磁盘上的宿主文件也没用，因为期望值在 CLI 里。
  - 开发构建由 cargo 直接编译，没法保证构建顺序：CLI 运行时按同目录宿主文件的 cdhash 比对，这是弱校验，并在输出里标"宿主未经签名校验"。
  - Q35 通过后，改为本机签名要求，cdhash 校验可以一并保留。
  - 不选方案二（默认只读、不发送写入）：它会让自用构建里的 CLI 写入功能整体不可用。不选方案三（UI 发一次性配对凭据）：凭据不绑定信道，照样会被中继，而且违背"不提供可信 CLI 凭据"（U-T4）。
- **落点**：
  - T005：构建顺序和嵌入；
  - T045：CLI 校验宿主，加 UNIT 用例；
  - T092：新增 E2E-SEC-cli-fake-host（假宿主占住套接字时 CLI 拒绝连接）；
  - 可选，T038：确认框醒目标出"申请方不是本 App 自带的命令行工具（路径或 cdhash 不符）"；
  - 5.8.1 的"UI 和 CLI 校验宿主"一段，按构建种类分别写清。
- **在此之前**：`install_cli` 仍可以提供，自用前须知里写明"CLI 暂不校验宿主"。
