# 计划评审：安全工程师

## 总体结论：修改后可以进入 gate/plan

我没有提阻断意见。关键的安全措施在依赖关系上都排在第一次经宿主运行真实 agent（T066）之前：项目信任、git 安全档位、档位规则、进程卫生、环境变量规则、运行时校验。安全 e2e 也都有明确的归属任务：T092、T093、T131、T161。

主要问题集中在 M1b 的"自用构建"上：作者从 T160 起就在真实项目上日常使用，但它的身份、加固和使用须知都没写清楚。另外，Q35 的验证漏掉了最关键的一项。第 1–7 条要在对应任务派发前改。

## 对两个问题的回答

### 1. 长期使用自用构建、没有 Developer ID 时，Q35 两种方案的差异

**两种方案共同的关键：签名私钥能被谁使用。** 宿主认 UI，靠的是"签名满足要求串"。而攻击者可以复制这个要求串里的所有内容：identifier 是签名时自己填的，Team ID 或证书哈希就是作者自己的身份，hardened runtime 等运行时标志也能照样设上。至于把 cdhash 写死在要求串里，这条路走不通：宿主嵌在 UI 的包里，两者的哈希互相依赖，宿主编译时还算不出 UI 的 cdhash。

所以，Q35 能否带来实质的安全提升，只取决于一件事：私钥能不能被同用户的进程静默使用。SP-4b 实测过，本机两个身份调用 `codesign` 都没有弹窗。在这种情况下，"本机签名构建"比退化模式更差：攻击者可以签一个假 UI 悄悄接入宿主，不用杀宿主，用户也察觉不到。

**两种方案的差异：**

| 方面 | 钥匙串里的自建证书 | 免费 Apple ID 的 Apple Development 证书 |
|---|---|---|
| 签名要求串 | 不是 Apple 签发的证书，只能固定证书哈希（`certificate leaf = H"…"`）。只认这一张证书；换证书就要把所有组件重新编译 | 写成"Apple 证书链 + 个人团队的 Team ID + 开发证书的标记 OID"（具体 OID 由 T105 导出 designated requirement 确定）。同一个 Apple ID 在别的 Mac 上由 Xcode 生成的证书也满足这个要求 |
| hardened runtime 下的库校验 | 自签名证书没有 Team ID，Electron 自己的 framework 大概率过不了库校验（AMFI 会报 "mapped file has no Team ID"，凭记忆，未核实），只能加 `disable-library-validation`。代价是：磁盘上被替换的 `cupper_native.node` 或 framework 照样能被加载，而宿主的动态校验看不出来 | 有 Team ID，库校验正常工作，不需要这项例外。运行时的完整性更好 |
| `get-task-allow` | 不受影响 | 如果按 Xcode 的调试配置签名，会带上 `get-task-allow`，宿主的状态字检查会拒绝。所以必须用 `codesign` 显式签名，并确认不带它 |
| 私钥存放 | 可以一开始就生成在一个专用的钥匙串里 | Xcode 把私钥生成在登录钥匙串里，而且常被设为"始终允许" codesign 使用。需要迁出，或者收紧访问控制；Xcode 可能还会自动重建这个身份 |
| 生命周期与个人信息 | 有效期自己定，不依赖网络和账号 | 依赖 Apple ID；证书到期或被撤销后要重新签名、重新编译。个人 Team ID 与 Apple ID 绑定，会出现在审计日志和诊断信息里，属于个人信息 |

**我的倾向：**
- 如果私钥能放进一个专用、加锁的钥匙串，选 Apple Development 证书。
- 如果做不到（例如 Xcode 会自动重建身份），选自建证书，接受 `disable-library-validation` 的代价。
- 无论选哪种，都必须满足私钥隔离，才能算 K7 通过。

**T105 的验证方案还缺这些：**

1. **私钥隔离（列为通过条件）。** 签名身份放在一个只装它的专用钥匙串里：有独立的密码，不在默认的搜索列表里，签名完就锁上，访问控制设为每次都确认，不设"始终允许"。实测：同用户的另一个进程在没有用户输入的情况下，用这个身份签名必须失败。构建脚本每次签名时交互式解锁。
2. **负面矩阵。** 以下对象都要被拒绝：用另一张同名自签名证书签的程序；ad-hoc 副本；四个 Electron helper；node；开发构建和 e2e 构建。另外，用同一身份签、但带 `get-task-allow` 或没开 runtime 的程序也要被拒绝。
3. **两种方案下的签名事实。** 实测各自需不需要 `disable-library-validation`，并导出完整的 entitlements 和动态状态字。
4. **证书到期、撤销和更换。** 实测这时宿主还认不认旧构建，重新编译的步骤要写进说明。
5. **Team ID 和证书摘要的去向。** 确认它们在 `--build-info`、审计日志、诊断包、录制里出现时都经过脱敏；本机构建配置放在仓库之外（加进 `.gitignore`），CI 永远不会把它编进产物。
6. **已有的三项保留：** 签名后能否运行、UI 被杀后新 UI 能否接上旧宿主、CLI 能否以只读身份接入并走完提权流程。

**如果 Q35 不通过、长期停在退化模式，M1b 必须补上：**
- 第 1 条：自用构建单独一套身份和数据目录；只在自用构建上处理真实项目，不用开发构建。
- 第 2 条：自用构建打开 hardened runtime（需要时加 `disable-library-validation`），不带 `get-task-allow` 和 `allow-dyld-environment-variables`；fuse 和 entitlements 在 T160 就校验。
- 第 3 条：使用前须知里写明退化认证的实际含义：沙箱外的同用户进程只要能杀掉宿主、再以注入的方式重新启动 App，就能接管；所以要开启 agent 自带的沙箱。
- 不提供任何把密钥存进文件或钥匙串的"便利"做法（Q22 已定）。CI 断言宿主里没有从文件读密钥的代码。
- 建议补上第 9、10 条：发信号前核对 pid；退化模式下的证明绑定父进程。

### 2. 第一次真实运行之前，安全措施是否都已就位

- **T003、T102 不经过 cupper 的宿主。** 它们用 SP-1 的 TS 客户端直接驱动适配器，所以宿主侧的项目信任、git 档位、档位规则与它们无关，也不需要。它们的风险在 CLI 自己身上：项目配置、持久规则、改写配置。这些靠第 8 条和 P-14 约束；在空的临时仓库里运行，也就没有项目配置可加载。
- **T066（Claude）和 T113（Codex）经过宿主。** 从依赖关系看，下列措施都已合并在前：
  - 项目信任：T035 和 T044，经 T064 在前；
  - 档位规则与 `config_unconfirmed`：T031 和 T044；
  - git：T060 是唯一的 git 入口，T034 依赖它，所以从第一次调用 git 起就是安全档位。T061 不是 T066 的前置；如果它还没合并，回合快照记为 `skipped`，不会调用 git，同样安全；
  - 进程卫生、可信 PATH、环境变量规则：T020、T054、T055；
  - 运行时的哈希校验：T056；
  - Codex 在未信任项目上拒绝启动：T111，在 T113 之前。

  真实输入和原生确认（T077）与这两次运行无关：这时没有 UI，兼容套件走 test_harness。但正因为 test_harness 绕过了档位规则和原生确认，兼容套件必须自我约束（第 4 条）。录制入库前还要过本机的敏感词清单（第 5 条）。
- **第一次在作者的真实项目上运行，是 T160 之后的日常使用和 T179 的 S1–S4 检查。** 那时宿主侧和桌面侧的措施都已实现。但有三件事排在使用之后，或者根本没写：
  - 自用构建的加固校验在 T161（第 2 条）；
  - 使用须知在 T157（第 3 条）；
  - 自用构建与开发构建共用数据目录（第 1 条）。

  这三条改完，"措施先于使用"就成立了。
