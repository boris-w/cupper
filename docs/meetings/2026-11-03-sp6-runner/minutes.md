# SP-6 渲染压测改在 GitHub runner 上跑

- 日期：2026-11-03
- 参与：用户、编排者
- 形式：会话中的提问（选项）

## 背景

按计划，M1b 的 SP-6 渲染压测在作者机器上跑：
- T103 跑场景 1–4、7、8，判定以作者机器为准（设计 5.9.7）；
- T108 跑场景 5、6：8 小时浸泡，以及流式输出期间用拼音输入；
- T104（场景 9，Q29 审查文档）也在作者机器上测量。

2026-11-02 用户决定压测不在自己的电脑上做（`docs/meetings/2026-11-02-perf-local/`），M1a 同步会随后定了 PERF 只记录、不卡闸门（`docs/meetings/2026-11-02-m1a-sync/` D1）。SP-6 原来的安排和这两个决定冲突，派 T103 之前需要用户选。

编排者给了三个选项：
1. 改到 GitHub runner（推荐）：只记录，K8 只看有没有数量级的问题；托管 runner 单个作业最长 6 小时，浸泡缩短到约 5 小时；场景 6 是几分钟的手动操作，不算压测，仍请用户做。
2. 挑用户不用电脑的时段，在用户的 Mac 上跑。
3. 降级：runner 上只记录，取消浸泡，只保留场景 6。

## 决定

- **D1**：用户选 1，改到 GitHub runner。
- **D2**（编排者据 D1 定）：
  - T103（场景 1–4、7、8）和 T104（场景 9）的测量都在 `macos-15` runner 上跑，只记录。
  - T108 的浸泡在 runner 上跑约 5 小时；场景 6 由用户在自己的机器上手动做，约 15 分钟。
  - K8 只看有没有数量级的问题，比如冷启动或内存超出预算好几倍、流重置频发。只有这种情况才按 ADR-03 的改变条件讨论；单项不达标照常进 M1b 的任务。
  - 已知 runner 比作者机器慢得多：T220 在 6 路洪流下只测到 4 帧/s，T078 在作者机器上是 102–107。判读时要考虑这一点。
  - 场景 8（遮挡）在 CI 虚拟机上能否检测到遮挡还没核实。检测不到时按"环境不合格"记录，不计结果。

## 落实

- 计划 v1.3.86 改写 T103、T104、T108 三行，以及第 3 节的注、用户操作表第 15、16 行。
- 设计 5.9.7 改写"环境"、场景 5 和场景 8；5.9.6 的浸泡一行随之改写。
