# Cupper Local 自用前须知

- 适用于：Cupper Local，作者在自己的 Mac 上构建、日常使用的"自用构建"（设计 5.7.9）。安装和更新见 [selfuse-install.md](selfuse-install.md)。
- 来源：计划 T160 的注、设计 5.7.9、5.8.1、5.8.7、ADR-05。完整的安全边界说明由 T157 在 M1b 末尾写成，Codex 部分也在那时补上。
- 第一次用 Cupper Local 处理真实项目之前读一遍。之后真实项目只用 Cupper Local；开发构建（cupper Dev）和测试只用临时目录或 `cupper-dev/`（计划 1.10）。

## 1. "弱认证"是什么意思

发布版的界面和会话宿主靠 Developer ID 签名互相认人。Cupper Local 没有 Developer ID，改用退化认证：界面每次拉起宿主时，经 stdin 交给它一把只存在两边内存里的一次性密钥，双方用它互相证明身份。界面工具栏上的"弱认证"标记说的就是这个。它有两个后果：

- **界面一崩，会话跟着停。** 界面崩溃或被强制退出后，新打开的界面拿不到那把密钥，连不上还在运行的旧宿主。旧宿主此时成了"孤立"状态：不再开始新回合，运行中的回合结束后自己退出。如果新界面提示"需要重启宿主"，确认后旧宿主被结束，运行中的回合会中断。"界面崩溃不影响会话"（NFR-8）在 Cupper Local 上不成立。
- **沙箱外的恶意程序可以接管。** 以你的身份、在沙箱外运行的程序，只要能结束宿主，再用注入的方式重新启动 Cupper Local，就能冒充界面接管宿主，替你批准请求、切到完全访问。这样的程序本来就能读写你的全部文件，弱认证只是又给了它一条路；挡住它的办法只有一个：不在沙箱外运行你不信任的东西。

命令行 `cupper` 不受影响：它按用户身份只读接入，任何写操作都要先 `elevate`，由 Cupper Local 弹出原生确认框，你批准后才生效。Cupper Local 的命令行只认编译时写进去的那个宿主（按 cdhash 核对），冒充宿主的程序骗不了它，也就劫持不了你的提权。

## 2. 不要因为 agent 的操作给 Cupper Local 授权

agent、它运行的命令、它的 MCP 服务器和 hooks 触发的系统授权提示，都会显示成"Cupper Local 想要……"，授权也记在 Cupper Local 名下，之后 agent 就一直带着这项权限。

- **辅助功能、自动化（"想要控制……"）、屏幕录制：一律拒绝。** Cupper Local 自己从来不需要它们。辅助功能最危险：有了它，agent 能合成点击，替你点掉 Cupper Local 的确认框。
- **摄像头、麦克风、蓝牙：同样拒绝。** Electron 自带的 Info.plist 写了这几项的用途说明，所以这类提示也可能出现。
- 已经误给的，到"系统设置 › 隐私与安全性"里对应的项目下关掉 Cupper Local。
- 文件夹访问（"想访问'文稿'文件夹中的文件"）只在添加位于这些位置的项目时允许，见第 5 节。

## 3. 开启 agent 自带的沙箱

- **Claude Code**：开启它的沙箱，并且不要配置 `allowUnixSockets`。沙箱开着时，agent 运行的命令连不上 Cupper Local 的宿主，也就没法冒充命令行去申请写权限。
- 沙箱管不到的东西（你批准在沙箱外运行的命令、MCP 服务器、hooks）能以只读身份连上宿主；写操作和审批仍然要你在 Cupper Local 里确认。看到不是你自己发起的提权确认框，拒绝。
- **Codex**：Cupper Local 目前还没有接入 Codex。接入时这里补上 Codex 的设置（工作区模式不要打开网络访问，否则所有 Unix 套接字都会放行），由 T157 完成。

## 4. 在 Cupper 里提交会运行仓库的 hooks

Cupper 自己在后台调用 git（快照、比较、状态）时，不运行仓库配置里的任何程序：hooks、fsmonitor、过滤器、diff 驱动都不执行。但是你在 Cupper 的审查面板里点"提交""推送"时（M1b 陆续上线），和在终端里执行一样，会运行仓库的 hooks、提交签名和凭据助手，而且是在 agent 沙箱之外、以你的身份运行。

agent 改过的仓库可能改了 `.git/hooks/` 或 `core.hooksPath`。提交之前看一眼；Cupper 发现本会话期间仓库的 hooks 或配置变过时，会在确认里提示。

## 5. 剩余风险

两项风险来自 ad-hoc 签名，根本的解决办法都是本机签名身份（待定问题 Q35，T105 正在验证；通过后由 T162 改用签名校验，身份和数据目录不变）。

- **关掉了库校验（`disable-library-validation`）。** ad-hoc 签名的 App 开着 hardened runtime 时，不关库校验就加载不了自己的 Electron 框架和原生扩展。代价是：能改写 `Cupper Local.app` 里文件的同用户程序，可以把包里的库换成自己的再 ad-hoc 重签，Cupper Local 照样加载，等于在 Cupper Local 里运行任意代码。hardened runtime 仍然开着，`DYLD_INSERT_LIBRARIES` 这类环境变量注入不起作用。
- **每次手动替换 App，都要重新确认系统授权。** ad-hoc 签名没有稳定的签名身份，macOS 按每次构建的程序记授权，换成新版本后，之前给的文件夹访问等授权会再问一次（以后有系统通知时，通知授权也一样）。替换后接连弹出的授权框容易让人顺手点"允许"：只允许你确实要用的项目文件夹，其余按第 2 节拒绝。

## 6. 为什么关掉了 cookie 加密

Electron 的 cookie 加密（fuse `enableCookieEncryption`）把密钥存在钥匙串里，钥匙串按签名身份决定谁能读。ad-hoc 签名的 App 每换一个版本身份就变，每次打开新版本都会弹钥匙串密码框。Cupper Local 的界面不用 cookie：它不加载任何远程内容，内容安全策略禁止一切网络连接（`connect-src 'none'`），所以关掉没有损失，也免得你习惯在钥匙串密码框里随手输密码。这是编排者的裁定（设计 5.7.9 自用构建一列）；其余 fuse 与发布构建相同。

## 7. 出问题时

- 界面和宿主的日志在 `~/Library/Logs/cupper-local/`（`main.log`、`host.log`），数据在 `~/Library/Application Support/cupper-local/`。日志里家目录写成 `~`，命令输出和文件内容默认只记类型和长度。
- 宿主提示"数据来自更新的版本"：不支持降级，换回新版本；迁移前的数据库备份在数据目录的 `backups/` 下。
