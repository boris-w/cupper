# ADR-05 本地传输与本地客户端认证

- 状态：提议
- 日期：2026-10-16
- 来源：`docs/meetings/2026-10-16-tech-selection/`（`minutes.md` C4、C5；`architect.md` ADR-05；`mobile-security-engineer.md` 第 4 节；三份第二轮回应）

## 背景

SEC-8 要求：宿主只接受经过认证的本地客户端；agent 子进程和集成终端都拿不到凭据；宿主不监听网络端口。

威胁的主体是 agent 本身，或者 agent 拉起的子进程。它们和宿主是同一个系统用户，可能被提示注入驱动，目的是替自己批准、切换到完全访问，或者选择"总是允许"。

另外：
- NFR-8 要求 UI 崩溃后能重新连上宿主；
- NFR-1 要求命令行工具也是协议客户端。

## 可选方案

1. Unix 域套接字 + 校验对端代码签名 + 命令行提权时由用户确认
2. XPC Mach 服务 + 签名要求
3. 继承的 socketpair
4. localhost TCP + token 文件
5. Unix 域套接字 + 钥匙串或文件里的共享密钥

方案 4 违反 SEC-8。方案 5 挡不住 agent，因为 agent 可以直接执行在钥匙串 ACL 里的 cupper-cli。方案 3 不支持 UI 重连，也不能给命令行用。方案 2 会让 M1 就必须用 LaunchAgent，而且 Rust 没有可用的 XPC 库。

## 决策

**采用方案 1。**

**传输**
- 套接字是数据目录下的 `run/host.sock`，所在目录权限为 0700。路径超过 `sun_path` 的 104 字节限制时，改放到更短的临时目录。
- 分帧方式见 ADR-04。

**principal 与认证**

| principal | 认证方式 | 权限 |
|---|---|---|
| `desktop_ui` | 宿主用 `LOCAL_PEERTOKEN` 取对端的审计令牌，再用 `SecCodeCopyGuestWithAttributes` 和 `SecCodeCheckValidity` 校验签名要求：Apple 签发的证书链、UI 的 identifier、Team ID；还要求开启 hardened runtime、不带 `get-task-allow`。只接受主进程的连接，所有 helper 进程一律拒绝 | 全部 |
| `cli` | 对端用户 ID 相同（`LOCAL_PEERCRED`） | 只读：订阅和查询 |
| `cli`（已提权） | 调用 `auth/elevate` 后，由主进程弹出原生确认框，用户批准。确认框显示可执行文件、签名、PID、父进程链和申请的范围。授权只在这条连接上有效，最长 15 分钟 | 只限申请的范围。任何写操作都需要提权，不只是审批类操作。审批类权限要单独申请，在确认框里醒目标出 |
| `test_harness` | 只在编译特性 `test-harness` 打开的 debug 或测试构建里存在。测试工具通过继承的 fd 传入一次性密钥，只能配合临时数据目录和临时套接字使用 | 全部；release 二进制里没有这段代码 |
| `remote_device`（预留，M3） | 由远程桥在进程内完成认证后接入 | 按 SEC-9 |

**规则**
- UI 也要校验宿主的签名，防止有进程冒充宿主。
- 非 UI 的 principal 永远不能切换到完全访问，也不能选择 `allow_always`。
- 宿主做血缘检查：能确认申请方是某个适配器进程的后代时，直接拒绝，不弹确认框。这项检查是尽力而为的，经过双重 fork 的进程查不出来。同一来源的提权请求要限频。
- 开发构建和自行构建（没有 Team ID）时，使用退化的认证模式：UI 拉起宿主时，经 stdin 的启动载荷传入一次性密钥，双方用绑定信道的双向证明互相认证（设计评审修订，见文末）。UI 用语义码提示"本地鉴权较弱"：首次启动时说明一次，之后在标题栏放一个小标记，在设置页常驻显示。
- **不提供"可信 CLI 凭据"**，也就是命令行不经确认就能执行写操作的方式（2026-10-16 用户确认，U-T4）。
- 每次连接都记审计日志。设置页的"连接与设备"列出当前连接的客户端，数据来自宿主索引流里的 `clients`。

**agent 子进程的隔离**
- 环境变量用白名单，去掉所有 `CUPPER_*` 变量。
- 用 `POSIX_SPAWN_CLOEXEC_DEFAULT` 拉起子进程，标准输入输出显式建管道。
- 每个适配器单独一个进程组。

**写进文档的边界**

SEC-8 能做到：
- agent 的沙箱开着时，操作系统层面就挡住它连接宿主；
- 关掉了"借一条命令替自己批准"这条低成本的路；
- 冒充宿主、偷凭据会留下痕迹。

SEC-8 挡不住的：agent 处于完全访问模式，或者在沙箱之外执行任意代码时，它可以直接修改 agent 自己的权限配置，也可以改 cupper 的数据目录。建议用户开启 agent 自带的沙箱。

## 后果

- **好处**：没有可以被偷走的静态凭据；不依赖宿主的进程形态和实现语言；M3 的 principal 模型可以直接沿用。
- **代价**：
  - 签名校验需要 Developer ID 签名的构建才能发挥完整强度；
  - 要写几十行 Security 框架的调用代码；
  - 命令行做写操作前多一步确认。
- **需要 SP-4 验证**：
  - 审计令牌加签名校验能可靠地认出主进程，并且拒绝以下对象：helper 进程、关闭 fuse 后的 `ELECTRON_RUN_AS_NODE`、node、cupper-cli；
  - 在 Claude Code 和 Codex 的各种权限模式下，agent 能否连上这个套接字；
  - 血缘检查能挡住哪些逃逸方式；
  - UI 校验宿主的流程；
  - 冒充宿主抢占套接字路径的情形。
- **改变条件**：如果用审计令牌校验签名不可靠，就改用 XPC 加 LaunchAgent（M1 起），命令行和测试仍然走套接字。

## SP-4b 实测修订（2026-10-16）

依据：`docs/tasks/SP-4b-local-security/report.md`。实测结论：方案 1 成立，不需要换成 XPC。

1. **固定令牌握手（必须做）。** `LOCAL_PEERTOKEN` 返回的是**最近一次在这个套接字上做 I/O 的进程**的当前映像，并不是 connect 时的身份。所以只在连接开始时校验一次是不安全的：
   - 对端可以先写数据，再 exec 成正版二进制，从而骗过校验；
   - fork 出来、共享同一个 fd 的进程，可以借用已经校验过的连接。

   做法：
   - accept 时取令牌并校验；
   - 宿主发一个 nonce，对端的第一条消息必须回显它；
   - 之后每条消息都比对令牌（包括 pidversion），和 accept 时不一致就立即断开。

   实测证实这样能挡住上面两种攻击。
2. **发布构建的签名要求**：在 Apple 证书链、identifier、Team ID 之外，再加上 Developer ID 的标记 OID（`certificate 1[field.1.2.840.113635.100.6.2.6] exists and certificate leaf[field.1.2.840.113635.100.6.1.13] exists`）。签名标志用动态状态字 `kSecCodeInfoStatus` 检查：必须有 `CS_RUNTIME`，不能有 `CS_GET_TASK_ALLOW` 和 `CS_DEBUGGED`。每次校验的耗时中位数约 0.9 ms。
3. **错误处理**：任何错误都按拒绝处理。错误码归为四类：对端已退出（ENOTCONN）、对端已 exec（-67065）、磁盘上的代码已变（ENOENT 或 -67034，多半是正在升级）、其他。每类都记日志，并给 UI 一个语义码。
4. **退化模式**：
   - 只写 identifier 的要求没有用，任何签名方式都能通过；
   - 在开发机上，同一用户下不在沙箱里的进程可以用开发者本人的签名身份签任意代码，"带 Team ID 的要求"可以被伪造。

   所以开发构建和自行构建**必须**用继承 fd 传一次性密钥，并明确提示"本地鉴权较弱"。
5. **fd 卫生**：UI 连接宿主的 fd 必须设置 CLOEXEC；宿主拒绝通过 SCM_RIGHTS 传递 fd（这一项有待在实现中验证）。
6. **不在 argv 和环境变量里放任何秘密**：同一用户的进程能看到 cupper 进程的命令行参数和环境变量。这一点纠正了讨论会上"看不到环境变量"的说法。
7. **"沙箱能挡住连接"要加前提条件**：
   - Claude Code 开启沙箱、使用默认权限时，连接全部被挡（实测）。前提是没有配置 `allowUnixSockets`（按文档）。
   - Codex 的只读和工作区模式在**没开网络访问**时全部被挡；一旦开启 `network_access`，所有 Unix 套接字都会被放行（实测）。
   - 用户批准的沙箱外命令、MCP 和 hooks 不受沙箱限制，这时靠第二层：只读权限，写操作需要确认。
8. **血缘检查**：
   - 用进程组加会话 ID，能挡住 nohup、双重 fork、disown，挡不住 setsid；
   - 经 launchd、`open`、已经在运行的长期进程（例如 tmux）中转的，全部挡不住。

   血缘检查只作为辅助信号，主要防线仍然是"写操作必须由用户确认"。私有 SPI `responsibility_*` 暂不采用，留给 SP-10 评估。

## SP-4a 实测修订（2026-10-16）

- 套接字路径过长时会退回到短路径目录。这个目录在使用前也要检查属主和 0700 权限，防止被其他用户抢先创建（spike 已实现）。
- 校验对端 uid 用 tokio 的 `peer_cred()`，不需要 `unsafe`。
- `test_harness` 的一次性密钥通过继承的 stdin 传入，实测可行。
- 适配器隔离已经有自动化测试覆盖：继承的 fd 只有 0、1、2，环境变量按白名单传入。

## 设计评审修订（2026-10-16）

来源：设计评审会（`docs/meetings/2026-10-16-design-review/minutes.md`）、用户决定（`docs/meetings/2026-10-16-gate-design-decisions/minutes.md`）、详细设计 v0.7 的 5.13.2。本节是细化，不推翻上文；上文中被替换的写法已就地改正并注明。

- **principal、角色与 scope**：principal 增加角色（control、window），scope 增加 `privileged`、`ui_local`、`test`，完整的权限矩阵见详细设计 5.8.3。
- **审批档位纳入 scope 规则**（纪要 D10）：权限模式分 normal、elevated、full_access 三档；放宽到 elevated 需要 approve，full_access 只能经原生确认；会话的默认档位视为由创建者设定，不符时进入 `config_unconfirmed` 并暂停发送；回合进行中发现越权时，先把档位改回原值，改不回就中断当前回合；手机不能放宽到 elevated（U-R2，M3）。
- **项目信任**（U-R1）：SEC-8 之外的又一道边界。添加项目时经原生确认信任项目配置；未信任的项目，Claude 以 `settingSources: ["user"]` 启动，Codex 拒绝启动；扫描覆盖工作区到 git 根目录的每一级，跟随符号链接，摘要按链接目标的完整内容计算，工作区外的目标醒目标出；每次发送 prompt 前重新扫描（5.2.6，Q34）。
- **提权**：非 UI 的申请全局同一时间只允许 1 个未决，被拒后有静默期；确认框把宿主核实的信息与申请方自述分开显示；血缘检查只认适配器的会话（适配器以 SETSID 拉起）、进程组和祖先链（5.8.4）。
- **环境变量**：传给适配器的环境变量有禁用清单（`NODE_*`、`DYLD_*`、`ELECTRON_*`、`CUPPER_*`、适配器的控制变量等）；`CLAUDE_CONFIG_DIR`、`CODEX_HOME` 由宿主从登录 shell 读取、校验后自己设置（纪要 D14）。
- **退化模式**（纪要 D11、Q22）：一次性密钥经 stdin 的启动载荷传入；证明绑定信道，防止被中继；退化模式只由编译特性决定，运行时不能回退；自行构建使用开发构建的身份和独立的数据目录；发布版 UI 和 CLI 拒绝 `weak_auth` 的宿主。
- UI 校验宿主之后，每次读取都比对令牌。
- **安全边界说明**写明：授予 Cupper 的系统权限会被 agent 继承；合成的输入能操作确认框。
