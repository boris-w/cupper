# ADR-09 适配器进程拓扑

- 状态：已采纳（2026-10-16，`gate/design`）
- 日期：2026-10-16
- 来源：SP-1 实测的第 12 个场景和资源数据（`docs/tasks/SP-1-adapter-behavior/report.md`）

## 背景

有两种拓扑可选：每个会话各起一个适配器进程，或者每种 agent 只起一个适配器进程、由多个会话共用。

SP-1 的实测结果：
- **Claude**：每个会话本来就有一个 CLI 进程，约 220–290 MB，另外加上用户配置的 MCP。`session/close` 之后全部释放。
- **Codex**：一个 app-server 服务所有线程，约 80–150 MB。但每个线程各自拉起一套用户 MCP，本机约 400–480 MB，而且 `session/close` 之后不释放。
- 每个适配器进程本身约 60–120 MB（node）。

## 决策

**每台 Mac 上，每种 agent 只运行一个适配器进程，所有会话共用。**

- **进程组与清理**：适配器在独立的进程组里启动（ADR-05）。关闭时依次执行：
  1. 对所有会话调用 `session/close`；
  2. 关闭 stdin；
  3. 等待进程组退出；
  4. 超时后对整个进程组发 SIGTERM，仍不退出再发 SIGKILL。

  Claude 适配器退出时不等子进程，所以必须对整个进程组做兜底清理。
- **Claude 的会话**：会话不用时及时调用 `session/close`，释放对应的 CLI 进程。
- **新会话页（AG-4）**：不常驻预先建好的会话，而是缓存每种 agent 最近一次的能力描述（模式、模型、推理强度、斜杠命令都来自 `session/new` 的响应）。用户真正发出第一条消息时才建会话。
- **Codex 的资源回收**：宿主监控适配器进程树的常驻内存。空闲时或超过阈值时，回收（重启）适配器，会话通过 `session/resume` 恢复，代价很小。
- **容量提示**（NFR-11）：只算 agent 本身，6 个会话时 Claude 约 1.6 GB，Codex 约 0.3 GB。用户每配置一套 MCP，每个会话还要再加几百 MB。设置页要显示 agent 进程的资源占用，并提供回收入口。

## 后果

- **好处**：省掉每个会话一份 node 开销；Codex 本来就是共享 app-server 的设计。
- **代价**：
  - 适配器一崩溃，同一种 agent 的所有会话都会受影响。因为两边都能自动重启并 resume，影响可以接受（NFR-9）；
  - 宿主需要实现资源监控和回收。

## 设计评审修订（2026-10-16）

来源：设计评审会（`docs/meetings/2026-10-16-design-review/minutes.md`）、用户决定（`docs/meetings/2026-10-16-gate-design-decisions/minutes.md`）、详细设计 v0.7 的 5.13.2。本节是细化，不推翻上文；上文中被替换的写法已就地改正并注明。

- **多会话并发 prompt**（Q8）：Claude 在 M1a 写驱动层之前实测，Codex 在 M1b 之前实测（U-R5）；通过条件是两个会话同时各发 3 个 prompt、全部在 5 分钟内返回、输出没有串到另一个会话、重复 3 轮；不通过时该 agent 的 prompt 全局串行，或只对它退回每个会话一个适配器进程。宿主侧另有"6 个会话共用一个假适配器"的集成测试。
- **回收**：Codex 适配器常驻内存超过 2 GiB 或空闲 30 分钟时回收；能力探测前把探测目录重建为空目录，探测后回收 Codex 适配器。
- 适配器崩溃后按退避策略重启；适配器以 `POSIX_SPAWN_SETSID` 拉起，自成一个会话。
