## 逐项意见

1. **inputGuard 是纯逻辑，时钟由调用方传入**：九条规则里本任务负责的部分各有用例。几处边界处理都对：
   - 单独的修饰键不改变状态，⌘Enter 里先到的 ⌘ 不会清掉输入；
   - 焦点不在主框架时，按键和点击整个忽略、也不算打字；
   - 激活冷却只针对键盘。
2. **"命令"取幂等方式为 `command` 的方法**：读请求和通知不消耗输入。理由成立：渲染进程在后台不断发读请求，否则 Enter 和 `respond` 之间输入会被读请求用掉。"一次输入只能用一次"防的是一次输入授权两条命令，读请求不需要授权，所以不削弱这条防线。已把这句写进设计 5.7.8 第 4 条（main 上 9f67656）。
3. **重发表**：
   - 按 `command_id` 记下参数哈希（去掉 `input`）和当时用的证据，收到宿主的任何回应就删除；
   - 只有上次转发后宿主没有回应时，同参数的重发才沿用原证据；
   - 宿主的命令账本按 `command_id` 去重，所以即使宿主其实已经执行、只是回应没送到，重发也不会执行第二次。
   - 一个文档实例一个桥，文档变了表自然是空的。
   - 与第 9 条一致。
4. **入方向认出回应**：用 `FrameDecoder` 跟帧边界，只在重发表非空时解析 JSON。
   - 16 ms 攒批和 8 MB 暂停读取不变，UNIT-bridge-flow 照常通过；
   - 解析失败只换一个新解码器，不影响转发，有用例。
   - 每个入方向字节多一次复制，留给 T078 的测量闸门评估（记交接）。
5. **主框架判断用 `frameTreeNodeId`**：不依赖是否同一个对象，比直接比较对象更稳。
6. **Q26 的五项结论**：现有 e2e 测法成立。已关闭设计 Q26（main 上 9f67656）。复测脚本和结果放在任务目录，脚本里没有本机路径。
