## 逐项意见

1. **回放核心**：不经 SDK，逐行读写 stdio；与下一个 `send` 帧比对时方法与字段相同、JSON-RPC id 重映射（适配器发起的请求保留录制 id、宿主应答时须一致）、`cwd`/`path` 按占位比较并在发出的帧里换回宿主路径、各层 `_meta` 忽略、其余（含 prompt 与应答的选项）精确比较。比对失败写出帧号和字段路径并以 71 退出，信息足够定位。
2. **时间压缩到 1/100**，从宿主最近一条消息到达时重新计起；`instance_exited` 按录制的退出码退出；`--segment-file` 三次启动的用例覆盖了按段回放。
3. **persona 自动比对**：能力、configOptions、默认模式、命令列表、权限选项 ID，claude 与 codex 都比；临时改错一个选项 ID 验证过会失败；另有断言防止空比对。命令列表按"原样出现、顺序一致"比，因为录制机器装了插件；模型的当前值不比（取决于录制账号）。理由都成立。
4. **SP-1 录制做宿主端到端**：设计 5.9.2 原写"SP-1 录制只用于 A 层"，任务书却要求用它做端到端，是编排者没对齐设计。执行者没有放宽比对规则，而是在测试里把 `initialize` 换成宿主的、删去 SP-1 特有的两次 `set_config_option` 连同响应，其余帧原样逐帧比对。编排者认可，并在设计 5.9.2 补了这条例外（`e84ca5f`）：检验回放机制本身可以这样用，B 层金样例仍只用宿主自己驱动的录制。副作用是宿主的 `initialize` 再变时这个用例会带着字段名失败，多了一道守卫。
5. **不做 `--replay-speed`**：没有使用方，1/100 写成常量，符合"没人用的代码不进 main"。
