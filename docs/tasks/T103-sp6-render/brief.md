# T103 SP-6 渲染压力测试：场景 1–4、7、8

- 派发日期：2026-11-13
- 执行者：子 agent（前端与 e2e；T260 的执行者）
- 分支：`spike/T103-sp6-render`
- 依赖：T107（Electron 45，合并后开工）、T143（已合并）。T155 依赖本任务，把场景 2、3、4、7、8 改写成每晚的性能回归；T152、T159 参考本任务的结论

## 背景

设计 5.9.7 的 SP-6 在 M1b 打磨界面之前测渲染：主进程的连接方案已在 M1a 定下，SP-6 只管渲染。2026-11-03 起改在 GitHub 的 `macos-15` runner 上跑，只记录、不卡闸门（`docs/meetings/2026-11-03-sp6-runner/`）。runner 是共享虚拟机，比作者机器慢得多（T220 在 6 路洪流下只测到 4 帧/s，T078 在作者机器上是 102–107），K8 只看有没有数量级的问题。

## 范围

**做**（计划 T103 一行；设计 5.9.7 场景 1–4、7、8，5.9.6 的预算）：
1. 在 `spikes/T103-sp6-render/` 写测量脚本，测**打包后的 e2e 构建**（fuses 与发布构建一致），经 `spike-run` workflow 在 runner 上跑。能直接用 `tools/e2e` 的夹具、`test/seed`、假 agent 的 `flood_rate` 的就直接用，不要复制一份走样的。
2. 夹具：按 SP-1 录制里的分布生成（每回合条目数、各类条目比例、文本长度），另加"单个回合 2,000 个条目"的极端用例，用 `test/seed` 灌入。
3. 逐场景测量（表见 5.9.7）：
   - 场景 1：冷启动、热启动各 30 次，到 `cupper:ready` 的 p50、p95（定义见 5.9.6）；
   - 场景 2：`flood_rate 200 120 <长度>`，期间在输入框打字：帧时间、输入延迟（预算 p95 ≤ 50 ms）、CPU、输出到屏幕的延迟；
   - 场景 3：4 个订阅中的会话同时流式输出，同时拉一个 5 MB 的 blob，并触发一次 5,000 个事件的重新同步；另跑 6 条流作为压力报告：渲染帧时间、是否发生流重置；
   - 场景 4：1,000 和 5,000 条消息的会话、单回合 2,000 个条目的会话，从顶滚到底、再向前翻页：首次渲染时间、滚动帧时间、内存、翻页时锚点位移 ≤ 1 px；
   - 场景 7：切换到 LRU 里的会话、不在 LRU 里的会话、"下一个需要处理的会话"：到首屏可见的时间。"从通知跳过去"由 T155 补测，本任务不做；
   - 场景 8：主进程放一个同样大小、不透明、置顶的窗口完全遮住 App；测量前在渲染进程断言 `document.visibilityState === 'hidden'`，不满足就记"环境不合格"、不计结果；持续流式输出 10 分钟再移开：不应出现 `stream/reset`，记切回后的首帧时间。
4. **报告** `report-sp6.md`（本目录）：每个场景的数据、trace（或取 trace 的方法与位置）、和 5.9.6 预算的对照；K8 的判读（只看数量级）；不达标项按 5.9.7 的"判定与后续"给建议（进 M1b 的哪个任务，或 T159）。runner 的运行链接写进报告。
5. 交接事项里留给 T103 的两条一并看，结论写进报告：
   - runner 上 3 份并行负载下宿主的会话流每轮停顿几秒（最长 12.4 s），推断与 `host.db` 带 `checkpoint_fullfsync` 的 WAL 检查点有关，未验证（T206）；
   - 洪流下渲染进程很慢，屏幕上几 MB 不换行的文字可能被 streamdown 整块反复渲染（推测），6 路洪流时测量前只有 4–36 帧/s（T220）。

**不做**：场景 5、6（T108）、场景 9（T104 已做）；把场景改写成 nightly 的性能回归（T155）；任何产品代码的优化（发现的问题写进报告，由编排者立任务）。
