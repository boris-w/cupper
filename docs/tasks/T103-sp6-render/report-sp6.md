## 1. 环境与方法

- **机器**：GitHub 托管的 `macos-15` runner，Apple M1（虚拟机），3 核，7 GiB 内存，macOS 15.8.2。共享虚拟机，比作者机器慢得多：T078 在作者机器上测到 102–107 帧/s，T220 在 runner 上只有 4–36 帧/s。
- **被测对象**：打包后的 e2e 构建（fuses 与发布构建一致），Electron 45.2.3。由 `spike-run` 现场构建，构建方式与 e2e-repeat 相同。
- **测量脚本**：`spikes/T103-sp6-render/`，是一组 Playwright 用例，直接用 `tools/e2e` 的夹具。
  - 灌数据：`test/seed` 的 `sp1` 配比。按 SP-1 的 48 份录制：43% 消息约 67 字、42% 工具调用、15% 思考约 44 字。单回合 2,000 个条目用 `large_turn_items`。
  - 定速负载：假 agent 的 `flood_rate`。
- **共用的测量方法**：
  - 帧时间：渲染进程里相邻 `requestAnimationFrame` 回调的间隔。
  - 统计：各项按最近秩算 p50、p95、最大值。
  - 时间：一律用墙上时钟。渲染进程用 `performance.timeOrigin + now`，可以和主进程、宿主的时间直接相减。

## 2. 结果与预算对照

### 场景 1：冷启动（30 次）

| 指标 | f00af90a（43414975876） | 674da26d（43412878272） | 预算 |
|---|---|---|---|
| 到 ready，p50 / p95 / 最大 | 3.1 s / 29.7 s / 31.1 s | 2.0 s / 35.6 s / 48.2 s | p95 ≤ 2 s |
| 第一次启动（含系统对新二进制的检查） | 3.65 s | 5.0 s | 单独计 |
| 打开 1,000 条的会话到首屏，p50 / p95 / 最大 | 490 / 677 / 696 ms | 434 / 632 / 697 ms | （切换会话 p95 ≤ 150 ms） |

- 数据集：一个真实会话，加上 `test/seed` 灌入的 200 个会话，其中一个 20 回合 × 50 个条目，共 1,000 个；其余各 2 回合 × 10 个。
- 冷启动：App 和宿主都停下，由 App 拉起宿主。不清系统的文件缓存。
- **大多数启动在 1.5–4 s 之间，少数会卡几十秒**：
  - 43414975876 里 30 次中有 8 次超过 8 s（8.6、10.0、9.9、12.3、17.9、19.6、29.7、31.1 s）；
  - 43412878272 里有 3 次（21.7、35.6、48.2 s）；
  - 越往后的启动越慢一些。
- **慢在哪一段**：每次启动都从日志里分出三段。
  - 慢的那几次，前三段和快的一样：主进程起来 ≤ 1.7 s，宿主起来（宿主日志的第一行）≤ 1.8 s，主进程的控制连接就绪 ≤ 2.4 s。
  - 多出来的几十秒全在控制连接就绪之后、渲染进程 ready 之前，也就是窗口这一侧：页面加载、窗口的数据连接和握手、订阅索引流并应用快照（200 个会话）、输入框可用。
  - 只查到这一段为止。要再往下分，需要渲染进程里的分段标记。

### 场景 2：单会话洪流 + 打字（43409302612）

- 负载：`flood_rate 200 120 67`，即每秒 200 个片段、每段为 SP-1 消息的长度。洪流期间每 200 ms 用 `sendInputEvent` 打一个字。

| 指标 | 结果 | 预算 |
|---|---|---|
| 帧时间 p50 / p95 / 最大 | 33 / 281 / 581 ms（n = 1,159） | p95 ≤ 16.7 ms |
| 输入延迟 p50 / p95 / 最大 | 80 / 326 / 488 ms（486 个键全部上屏） | p95 ≤ 50 ms |
| 输出到屏幕的延迟 p50 / p95 / 最大 | 505 / 1,250 / 1,547 ms（n = 1,826） | p95 ≤ 100 ms |
| 渲染进程内存（峰值） | 591 MB | （长会话预算 ≤ 600 MB） |
| 宿主 CPU p50 / p95；内存 | 4.7% / 5.5%；38 MB | — |

- 洪流结束时，屏幕上的消息有 1,336,784 字，宿主写了 1,358,224 字。
- 输出延迟从宿主事件的 `ts` 起算，**不含宿主写入前最多 40 ms 的合并等待**。
- 渲染进程每帧读一次正在输出的那条消息的长度，读取本身也占一些时间。
- CPU 用的是 Electron 的 `percentCPUUsage`：
  - 渲染进程忙的那个 p95 约 36；
  - 主进程约 0.6，GPU 约 1–2。
  - 这几个数偏低，口径可能是按全部核心归一的，要核实后再用。两个渲染进程（主文档、常驻的审查文档）混在一起统计。

### 场景 3：4 路流 + 5 MB blob + 5,000 个事件的重新同步（43414734406）

- 负载：每路每秒 100 个 500 字的片段（桥接闸门的判定负载，T078）。第 5 s 拉取 5 MB 的 blob，第 10 s 重新同步约 5,000 个事件。量 20 s。

| 指标 | 4 路 | 6 路（压力报告） | 预算 |
|---|---|---|---|
| 渲染帧时间 p50 / p95 / 最大 | 154 / 333 / 400 ms | 103 / 315 / 367 ms | p95 ≤ 16.7 ms |
| 流重置 | 0 | 0 | 不应发生 |
| 5 MB blob | 384 ms | 398 ms | — |
| 重新同步 5,001 个事件 | 565 ms | 411 ms | — |

- 前两轮的帧时间 p95 分别是 402 / 349 ms、413 / 332 ms，三轮一致。
- 也就是每秒约 3–10 帧，与 T220 的 4–36 帧/s 是同一个量级。

### 场景 4：长会话（43414734406）

| 会话 | 首屏 | 向前翻页 | 锚点位移（≤ 1 px） | 滚动帧时间 p50 / p95 / 最大 | 渲染进程内存（打开后 → 滚动后） |
|---|---|---|---|---|---|
| 1,000 个条目（20 回合） | 311 ms | 无（窗口里已是全部历史） | — | 16.7 / 33.3 / 136 ms（38 帧） | 170 → 176 MB |
| 5,000 个条目（100 回合） | 236 ms | 60 页（脚本的上限，历史还没到头） | 38 页为 0，**22 页为 26 px** | 16.7 / 18.7 / 39 ms（119 帧） | 182 → 248 MB |
| 单回合 2,000 个条目 | 384 ms | 无 | — | 16.7 / 33.3 / 33 ms（18 帧） | 255 → 254 MB |

- 滚动是在翻页之后，从顶部按每帧 120 px 滚到底，滚的是已经载入的部分。
- 结束了的回合会收起，所以 1,000 和 2,000 那两个会话的列表不长。
- 每次滚动前先发一个 wheel 事件。这是因为只有用户能让列表离开底部：滚动必须发生在用户的 wheel 之后 500 ms 内（T245），程序直接改 `scrollTop` 会被列表复原。

### 场景 7：切换会话（43410584669）

| 指标 | 结果（各 30 次） | 预算 |
|---|---|---|
| 不在 LRU 里的会话，p50 / p95 / 最大 | 206 / 407 / 435 ms | p95 ≤ 150 ms |
| LRU 里的会话，p50 / p95 / 最大 | 37 / 46 / 50 ms | ≤ 1 帧 |

- 计时从会话链接在主进程里发出（与点击通知的路径相同），到第一帧出现之前不在屏幕上的行。这包含主进程转发给渲染进程的那一步，几毫秒。
- 8 个灌入的会话（各 5 回合 × 50 个条目）轮流访问，每个都超出窗口保留的 4 个，所以不在 LRU 里。两个会话来回切，则都在 LRU 里。
- "下一个需要处理的会话"测不了，见第 3 节。"从通知跳过去"由 T155 补测。

### 场景 8：遮挡（43409310647）

- **环境不合格**：App 以 Chromium 自己的遮挡处理启动。主进程放上同样大小、不透明、置顶的窗口后，`document.visibilityState` 仍是 `visible`。按设计不计结果，那 10 分钟的洪流没有跑。
- 这与 T078 的记录一致：在 Playwright 下，页面被遮住时还是 `visible`。

## 3. 与设计 5.9.6、5.9.7 的偏差

1. **产品里没有 `cupper:ready` 标记。** ready 改为：索引视图已完整，并且新会话页的输入框可用，两者同时成立的第一帧（按 rAF 轮询）。起点是调 `_electron.launch` 之前的时刻。
2. **App 启动后总是停在新会话页，不恢复当前会话**，而 5.9.6 的冷启动定义里有"当前会话已渲染"。所以"打开 1,000 条的会话"单独计时。后续由编排者定。
3. **热启动在 e2e 构建上测不了。**
   - 退化模式下，`dev_key` 只接受拉起宿主的那个进程；父进程退出后宿主孤立并有序退出（设计 5.8.1）。
   - 新启动的 App 接不上原来的宿主，第一次热启动等满 120 s 失败（43410584669）。
   - 要等 Q35（签名认证），或者在发布构建上才能测。
4. **"下一个需要处理的会话"没有处理方**：菜单里有 `next_needs_action`（Command+Alt+A），ui-core 的命令处理里没有它，所以测不了。去向由编排者定。
5. **输出到屏幕的延迟不含宿主写入前最多 40 ms 的合并等待**：假 agent 的片段里没有时间戳。
6. **场景 8 环境不合格。**
7. **场景 4**：滚动的是已经载入的部分；5,000 条的会话翻到第 60 页时，脚本的上限先到了。
8. **负载**：场景 2 的片段长度取 67（SP-1 消息的长度）。场景 3 用桥接闸门的负载（每秒 100 个 500 字的片段），方便与 T078、T220 对照。

## 4. K8 判读与后续建议

K8 只看数量级。runner 比作者机器慢一个数量级左右（帧率 3–10 对 102–107），所以下面的结论都要在参考硬件上复核。

| 项 | runner 上 | 判读 | 建议 |
|---|---|---|---|
| 冷启动 p95 | 30–36 s，预算的 15 倍以上（p50 2–3 s） | **尾部有数量级的问题**。原因在窗口这一侧 | 按 5.9.7：先在应用里定位。M1b 任务给渲染进程加分段标记（`cupper:ready`、窗口数据连接就绪、索引快照已应用），找出卡住的那一步，再决定是否按 ADR-03 讨论 |
| 帧时间（4 路流、单路洪流） | p95 280–410 ms，约 20 倍 | runner 慢一个数量级，扣掉后仍超预算，但不能凭 runner 定量 | 进 M1b：T159 或打磨任务里剖析流式渲染 |
| 输入延迟 | p95 326 ms，6.5 倍 | 同上 | 同上 |
| 输出到屏幕的延迟 | p95 1.25 s，12 倍 | 同上 | 同上 |
| 切换到不在 LRU 的会话 | p95 407 ms，2.7 倍 | 不到一个数量级 | 进 M1b：切换的首屏路径 |
| 切换到 LRU 里的会话 | p95 46 ms，约 3 帧 | 不到一个数量级 | 同上 |
| 长会话内存 | ≤ 255 MB | 达标 | — |
| 长会话滚动 | p95 18.7–33.3 ms | 接近预算 | 参考硬件上复核 |
| **翻页时锚点位移** | **22/60 页位移 26 px** | 与机器快慢无关的正确性问题 | 进 M1b |
| 流重置 | 0 | 达标 | — |
| 遮挡 | 环境不合格 | — | T155 或真机上补测 |

**翻页锚点位移 26 px**（推测，未验证）：
- 位置在 `packages/ui-core/src/stream/StreamList.tsx` 的 `useLayoutEffect`，以及 `ScrollKeeper.restore`。
- 历史插进前面后，锚点只复原一次，复原后就释放。复原用的是 `virtualizer.measurementsCache[index].start`，新插入的行此时还按 `estimateSize: () => 44` 估算。
- 这些行实测完以后锚点的位置还会再变，但已经没有人去校正了。
- 每次都正好 26 px，说明是某一行的估算值和实测值之差。要加日志才能确认是哪一行。

## 5. 交接事项里留给 T103 的两条

- **T206（会话流秒级停顿与 `checkpoint_fullfsync`）**：这次单份负载下没有复现。
  - 场景 3 的 20 s 里，每路流相邻事件的间隔 p95 约 60 ms，最长 114 ms（4 路）、100 ms（6 路），没有超过 1 s 的。
  - 同一段时间 `fs_usage` 记了宿主的 fsync：4 路 147 次、6 路 226 次，其中 `F_FULLFSYNC` 21 次、34 次，单次最长 13 ms、26 ms。
  - 所以在这个负载下，检查点的 fullfsync 不会造成秒级停顿。T206 的停顿出现在 3 份 e2e 并行时；可用 e2e-repeat 一次 3 份并开 `fs_usage` 验证。
  - 原始记录在 43414734406 的 `results/3-streams-*-fsyncs.txt`。
- **T220（几 MB 不换行的文字被 streamdown 整块反复渲染）**：场景 2 的数据与这个推测相符，但没有剖析证实。
  - 一条 1.3 MB 不换行的消息流式增长 100 s，帧时间 p95 281 ms，输出延迟 p95 1.25 s，渲染进程内存涨到 591 MB；结束时屏幕上还差约 2 万字。
  - 建议在参考硬件上录 trace，看每帧的 JS 时间是不是随消息长度增长；如果是，就进 M1b 的流式渲染任务（按段渲染，或只重渲最后一段）。
