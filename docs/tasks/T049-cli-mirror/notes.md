## 实现时的取舍

- **纯核心和异步胶水分开**：`Mirror<V>` 不做 I/O、不 await，只返回"要不要重新订阅、带什么参数"。`mirror::subscribe(client, mirror)` 和 `mirror::fold(client, mirror, incoming)` 两个异步函数把它接到 `Client` 上。没有改 `client.rs`，避免和并行的 T039 冲突。
- **构造**：只有 `Mirror::index()` 和 `Mirror::session(id)`，视图类型和流配不错。
- **各状态下收到的消息**：
  - `Subscribed`：只要是本流的就处理，每个结果都重新开始一轮。`replay` 只有在 `epoch` 和 `at_seq` 都等于游标时才保留视图和游标；对不上（包括没有游标），就整体重置并不带游标重新订阅。其他 mode 不论原因（含不认识的），都丢弃视图和游标，进入 `Loading`。
  - 订阅失败（`Err(RpcError)`）原样交还调用方，Mirror 停在 `Waiting`。
  - 快照页：只在 `Loading` 时接收。`Waiting` 时是旧订阅的页；`Live` 时不该出现。两种情况都忽略。
  - 快照页里解码不出来的 op（连 `type` 都没有）跳过，和不认识的类型一样不改变视图；`apply` 报 `ViewError` 就整体重置。
  - 事件：`Waiting` 时忽略；`Loading` 时出现属于违反协议（事件只跟在最后一页后面），整体重置；`Live` 时逐个检查连续性后再 `apply`。信封解码失败（拿不到 seq）按 `ViewError` 处理，不带游标重新订阅，这样快照绕过了这条事件，不会反复要到同一条坏事件。
  - `stream/reset`：`Waiting` 时忽略（新订阅的结果还在路上），否则保留游标和视图，带游标重新订阅。
- **重置时立刻清空视图**：`ViewError` 和对不上的 `replay` 都同时清掉视图和游标，`view()` 在新快照到齐之前是空的，不展示半途出错的视图。缺口和 `stream/reset` 保留视图，因为视图仍对应游标。
- `lib.rs` 除了加 `pub mod mirror;`，还把模块文档里"mirror 由 T049 提供"那句改成指向 `mirror` 的链接，共改 3 行。

## 范围外发现

- **宿主写完就关闭连接时，客户端会丢掉最后读到的数据**（T045 的 `client.rs`）。读循环每次读到数据都先查对端令牌，对端那头已经关闭时，`LOCAL_PEERTOKEN` 返回 `ENOTCONN`，于是这批数据被丢弃，关闭原因记为 `Refused(PeerExited)`，而不是 `Eof`。从安全角度看这样做是对的：认不出是谁写的数据就不处理。实际影响很小：宿主发 `host/shutdown` 之后有 2 s 的关闭宽限（T030 的裁定）。本任务经过 `Client` 的用例因此让假宿主等客户端先挂断。T046 写命令行时，如果要报告"宿主已退出"，需要把 `Refused(PeerExited)` 和 `Eof` 当作同一种情况处理。
- 经过 `Client` 的用例里有一个很小的进程内假宿主，与 `client.rs` 测试里的 `FakeHost` 用途相同。为避免和 T039 改 `client.rs` 冲突，这次没有把两者合并成共用的测试辅助，T039 合并后可以再合并。
