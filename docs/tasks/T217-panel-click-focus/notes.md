# T217 笔记

## 实测（Electron 44.9.0，隐藏窗口，CDP 模拟）

一个最小页面：侧边栏按钮，消息流（一段文字和一个按钮），输入框区域。把输入框整块换成面板，面板里依次是标题、"关闭"按钮、可滚动的 `<pre>`、选项列表（`tabindex=-1`）、"跳过"和"提交"。页面焦点用 `Emulation.setFocusEmulationEnabled` 开关，鼠标和按键用 `Input.dispatchMouseEvent`、`Input.dispatchKeyEvent`。脚本放在仓库外，没有提交。

| 情形 | 结果 |
|---|---|
| 页面失去焦点（如同窗口退到后台） | 输入框收到 `blur`、`focusout`，但仍是 `document.activeElement`；页面恢复焦点时它再收到 `focus` |
| 有焦点的输入框被移出 DOM | Chromium 同步派发 `blur`；焦点落到 body |
| 接上一行，面板插在原位后按 Tab | 第一下就到面板里第一个可聚焦元素（"关闭"） |
| 点面板标题（面板根元素不可聚焦） | 焦点到 body；随后按 Tab 进"关闭" |
| 点面板底部空白 | 焦点到 body；随后按 Tab 进"跳过" |
| 点选项行 | 焦点到列表（最近的可聚焦祖先） |
| 点按钮 | 焦点到按钮 |
| 点消息流里的文字 | 焦点到 body；随后按 Tab 进消息流里的按钮，不进面板 |
| 对 mousedown 调用 `preventDefault` | 焦点留在原处 |

React 19 在 commit 期间关闭事件分发（`react-dom` 的 `_enabled`）：输入框被面板替换时，Chromium 派发的那次 `blur` 不会进到 `onBlur`。

## 自动接管失败的条件（修之前）

- 窗口在后台时请求到达：窗口失焦时输入框已经收到 blur，`activity.focused` 为 false，面板是 manual。按 `man-keyboard.md` 的写法（先点输入框，再去终端发请求，再切回来），请求都在后台到达。3b 很可能属于这种情况。
- 激活窗口的那次点击不送进页面（`acceptFirstMouse` 为 false）：靠点输入框来切回窗口时，输入框只有在窗口退到后台之前就有焦点，才会拿回焦点。
- 反方向：面板关掉、输入框重新挂载后，`activity.focused` 还是旧值 true（上一条的 blur 被 React 丢掉了），之后来的请求会把焦点从侧边栏等处抢走。
- 点过输入框之后又点了页面别处：manual，按设计。点在消息流上时，Tab 从点击处往后找，第一下落在消息流里，第二下才进面板。

## 取舍

- 点面板之后焦点放到选项列表上，而不是给面板根元素加 `tabindex`：根元素可聚焦虽然靠浏览器默认就能拿到焦点，但 jsdom 不模拟这个默认行为，单元测试就测不到。放在 click 阶段处理：这时浏览器的默认动作（按钮、输入框、选项行拿焦点）已经发生，只在焦点还在面板外时补上。
- 就绪前按下的鼠标调用 `preventDefault`，面板上的任何位置都一样。代价是待命期内不能在面板上选中文字、点进输入框，与 RP-1"待命期内的点击一律吞掉"一致。
- RP-3 的"焦点在输入框里"改为输入框卸载时读 DOM：不看窗口是否在前台。按编排者 2026-11-02 的裁定，见汇报。
