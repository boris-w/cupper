## 背景

NFR-1（多端同步）是 M1a 退出标准的核心，验收全部自动化，五个用例写在设计 5.9.4。T090、T167 建好了 e2e 设施和辅助函数；T167 还修掉了两处让真实 App 拿不到数据的缺陷，`@smoke` 现在从渲染进程一侧守住数据链路。本任务**只新增用例文件**，严格按 5.9.4 的表写。

## 范围

**做**（计划 T091 一行；设计 5.9.4 的 NFR-1 表）：
1. **E2E-NFR1-1**：订阅会话列表和任意一个会话，内容与桌面一致。
   - UI 和 CLI 同时订阅，等两端都到达同一个 `head_seq`；
   - 经测试钩子导出 UI 的 `host-client` 视图，与 CLI 的 `Mirror` 视图比较；
   - 只比窗口内的内容，排除 `notification.intent`；视图的序列化格式以 schema 为准；
   - 视图导出加在渲染进程入口的 e2e 分支里（`__cupperTest`，T167 的交接）。`flavors.test.ts` 会照样检查它不进非 e2e 构建。
2. **E2E-NFR1-2**：CLI 依次发送、排队、中断、处理审批、回答提问，Playwright 断言 UI 上的相应变化（新回合、排队消息、"你在 … 后停止了"、请求面板与记录行的状态）。至少一个用例走真实用户的路径：CLI 以 `cli` 身份 `elevate`，原生确认框由替换函数批准，之后再发送。
3. **E2E-NFR1-3**：任何一端处理了审批或提问，另一端自动收起。
   - 两个方向各一个用例：UI 批准后 CLI 看到 `resolved`；CLI 批准后 UI 的面板收起，并显示"已在 cupper-cli 处理"；
   - "两端同时回答"：等面板的 `data-ready` 之后，两端同时回答，只有一个生效，另一个得到 `already_resolved`。
4. **E2E-NFR1-4**：断开期间的事件重连后补齐，不丢不重。三种断开：
   - 断开 CLI；
   - 重载渲染进程（走快照）；
   - 经主进程的测试钩子只断开这个窗口的数据连接、不重载（走按游标续传）。
   
   断开期间用 `flood` 产生大量事件，含区间事件；`Mirror` 检查 `from` 连续，`host-client` 的缺口、重置、重复计数为 0。
5. **E2E-NFR1-5**：宿主被强制结束后重新启动，会话可以继续。
   - 运行中和等待审批时各 `kill -9` 一次宿主，时机用事件做屏障（等某个条目或交互请求出现）；
   - UI 自动重新拉起宿主；
   - 回合为"已中断"、请求为"已失效"、残留进程被清理；
   - 下一条消息经 `session/resume` 成功。
6. **顺带确认**：消息流"插入历史后视口不跳"（T082 的交接）。在真实窗口里看一次，能自动断言就加进 NFR1-4 的重载用例，不能就在汇报里写确认方式。

**不做**：安全 e2e（T092）；交互与项目 e2e（T093）。
