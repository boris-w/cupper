## 逐项意见

1. **视图导出只在测试构建里**：界面的 `__cupperTest.views()` 在渲染进程入口的 e2e 分支，`flavors.test.ts` 照样守住；CLI 的 `cupper view` 只在 test-harness 构建。`HostProvider` 改为创建 client 时就调 `onClient`，以便赶在界面订阅之前拿到 client。
2. **NFR1-1 比完整视图**：两端都从快照订阅、界面没有加载历史，拿到的是同一个窗口；`notification.intent` 本来不进视图。
3. **NFR1-3 两端同时回答不预设谁赢**：断言宿主只写一次 `interaction.resolved`、输的一方得到 `conflict/already_resolved`，写法正确。
4. **NFR1-4 三种断开**都在持续 `flood`（含合并成区间的 delta）下进行，结束时两端视图相同，CLI 的 `resubscribed` 为 0，界面的缺口、重置、重复计数为 0。
5. **NFR1-5 按现状断言**：新宿主只在会话收到第一条命令时载入，用例先发下一条消息再断言补写和界面显示。见"记下的点"第 1 条。

## 就地修的三处缺陷（计划 1.2 的上限内，单独提交）

1. **`fix(cli)`**：`approve`、`reject`、`answer` 遇到视图里已处理的请求时在本地报错，改为照常发给宿主，由宿主回 `conflict/already_resolved`，与界面一致。由 NFR1-3 的同时回答查出。
2. **`fix(ui-core)` `data-queue-id`**：设计 5.9.4 规定的 DOM 标记，排队列表原来没有设置。
3. **`fix(ui-core)` 加载历史时的锚点**（T082 引入）：`loadEarlier` 锚住的是"加载更早的历史"控件本身，每次都往下跳整整一页。改为锚住控件之后屏幕上的第一行。T082 交接的"插入历史后视口不跳"因此第一次在真实窗口里得到确认，也说明 jsdom 里的单元测试覆盖不到布局。

## 记下的点

1. **宿主重启后窗口显示过时的状态**（执行者请编排者决定）：新宿主载入会话之前，被杀的回合在界面上仍是运行中、请求面板还在，直到这个会话收到下一条命令。裁定：订阅会话流也触发按需载入，让补写马上进流；并进还没派出的 T175（计划 v1.3.43），设计 5.2.13 补这条规则。T175 合并后，NFR1-5 可以改成不发命令也能断言补写，记交接。
2. **插入历史后的残余偏差**：大约每 10 次有 1 次下移 26 px，原因是视口按估计行高放回、新行实测高度不同、差额没补。用例只断言移动小于 40 px，守住整页跳动的修复。交给消息流的后续任务（T146）：等新插入的行测量完再恢复，或测量后按差额补一次。
3. **"经 `session/resume`"没有直接断言**：假 agent 不对外暴露收到的是 `session/resume` 还是 `session/new`。T063 的 K 清单若需要，可以让假 agent 记一笔可观察的记录，记交接。
4. **T167 夹具的一处注释写错**（`processes()` 说宿主不是 App 的子进程），行为没有问题，下次改夹具时一并修正，记交接给 T092。
