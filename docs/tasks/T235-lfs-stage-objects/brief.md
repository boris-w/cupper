# T235 暂存 LFS 指针时把对象放进用户仓库

- 派发日期：2026-11-04
- 执行者：子 agent（Rust 工程师，宿主 Git 服务）
- 分支：`fix/T235-lfs-stage-objects`
- 依赖：T229（发现者，评审时开出）

## 背景

T229 用锁定的 git-lfs 3.8.0 实测仓库档的写操作时看到，经 `git/stage` 暂存的 LFS 指针，对象只在 cupper 私有的 GIT_DIR 里（`<数据目录>/git/<仓库>/ws/<工作区>/lfs/objects/`）：快照档的 clean 过滤器把对象写在那里；仓库档只 `apply --cached` 了指针，用户仓库的 `.git/lfs/objects` 里没有这个对象。

用户提交时，如果工作区文件仍与暂存内容相同，git 刷新 index 时会重新跑 clean，对象就进了用户仓库，所以 T229 的用例看不出问题。但只要用户在经 cupper 暂存之后、提交之前又改了这个文件：
- 提交里的指针对应的对象在用户仓库里不存在，推送时 git-lfs 报找不到对象；
- 别的克隆检出这个提交时拿不到内容；
- 之后清除快照对象（T127）时，cupper 那份也会被删掉，对象就彻底丢了。

## 范围

**做**：
1. **先确认现象**：在 T229 的 LFS 用例基础上复现：
   - 暂存；
   - 改工作区文件；
   - 用户自己 `git commit`；
   - 用户仓库 `git lfs fsck --objects` 报缺对象，或者 `git lfs push --dry-run` 报找不到。
   复现不了就报给 `main`，说明原因。
2. **修复**：经仓库档暂存（以及取消暂存、还原，如果会引用新对象）LFS 指针之前，把补丁里新指针引用的对象放进用户仓库的 LFS 存储。做法和取舍由你提出，例如：
   - 从 cupper 的私有存储复制，按 oid 校验 sha256，原子改名；
   - 或者用宿主的 git-lfs 在仓库档里写对象。
   用户仓库的 LFS 存储位置按 git-lfs 的规则取（`lfs.storage`、worktree 共用的公共目录）。查清后用 SendMessage 报原因、修法、预计行数，等回复再改产品代码。
3. **用例 IT-git-lfs-stage-objects**（已登记）：
   - 暂存后，用户仓库里有对象；
   - 改工作区文件后再提交，`git lfs fsck --objects` 通过；
   - 对象内容与 oid 一致；
   - 没有 git-lfs 时跳过，照 T229 的写法。
4. 写进 5.2.10 的部分，在汇报的"设计偏差/补充"一节列出，由编排者在合并时改。

**不做**：T127 的清除快照对象（那边要注意的事项已写进交接事项）；与 LFS 无关的 Git 服务改动。
