## 做了什么

`cargo xtask size` 做完了：它统计任务分支自己的增删，对照任务书里的停止线报告余量或超出量。用它试跑了五个已合并的任务，三个与汇报完全一致，两个有小差异，差异能逐处解释（见"验证方式"）。CI 通过。

**用法**：`cargo xtask size [--task <ID>] [--json] [--rev <commit> --main <commit>]`，实现在 `crates/xtask/src/size.rs`。

- **怎么定基准**：
  - 取 `merge-base 版本 main`。编排者合进分支的 main 已经在基准里，所以不算任务的改动。
  - 本地 `main` 比合进来的那个旧时，改用第一父链上合并提交的第二父里最新的一个。
  - 默认统计到工作区，未提交的改动也算，新文件要先 `git add`。
- **`--rev`、`--main`**：统计过去的状态，例如某个任务合并前的最后一个提交，配上它合入时的 main。
- **排除清单**：写成常量，并在输出末尾列出。包括：
  - lock 文件；
  - 生成物：`packages/protocol/src/gen/`、`protocol/schema/`、`views.json`、runtime 的清单、锁和许可证；
  - `docs/`、`testdata/`、截图基线；
  - 二进制文件。
- **停止线的解析**：
  - 优先认任务书模板里固定格式的那一行 `- 停止线：<n>；硬停止线：<n>`，有多行时取最后一行。
  - 没有这一行时，读标题含"规模"或"裁定"的节里的自然语言：后出现的数覆盖先出现的，所以补充裁定会覆盖原值；"上限""停止线""超过"后面的数算停止线，"硬停止线""硬线"后面的数算硬线，可以带"约"和千分位。
  - 找不到时提示"没有找到停止线"。
- **输出**：
  - 一行摘要：增、删、净增，离停止线还剩多少或超出多少；到了 90% 或越线时用 `!!` 标出；
  - 按目录的明细，以及排除清单；
  - `--json` 给出同样的内容，`status` 取值为 `ok`、`near_stop_line`、`over_stop_line`、`over_hard_stop`、`no_stop_line`。
- **单元测试**（3 条）：
  - 排除清单与按目录归并；
  - 停止线的解析：规模节、裁定覆盖、固定格式一行压过后来的自然语言、"注意"节里的"不超过 100 行"不算、找不到；
  - 合进 main 的合并不算：用临时仓库，并包括本地 main 比合进来的那个旧的情形。
- **流程文档**：
  - 任务书模板新增"## 规模"一节，写着固定格式的停止线一行，并说明"每次提交后跑一次 `cargo xtask size`，推算或实际越线就停下汇报"；
  - `docs/00-process.md` 任务生命周期的第 2 步也写了同样的要求。

## 关键取舍

- **规模**：新增 289 行、删除 3 行（不含文档），由工具自己统计。
  - 开工前估约 185 行。写完第一版时它统计出 286 行，越过了硬停止线 240，我随即停下汇报。
  - 超出的来源：rustfmt 把参数数组展开成多行；`--rev`/`--main` 约 20 行；"统计到工作区"。
  - 裁定改为上限约 300、硬停止线 330（计划 v1.3.50）。用 main 上带裁定的任务书统计，工具报"离停止线 300 还剩 11"，并以 `!!` 标出。
- **统计净差异，而不是逐提交累加**：逐提交累加会把写了又删的行算两次，与以往汇报的口径不一致。合进来的 main 已经在基准里，不需要再按提交去排除。
- **编排者的冲突处理算在任务头上**：解决冲突时改动的行落在任务分支上，工具把它们算作任务的改动，下面 T090 的差异就是这样来的。
- **不做 CI 里的强制拦截**：照任务书，只报告。
