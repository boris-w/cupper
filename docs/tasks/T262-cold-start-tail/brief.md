# T262 冷启动的尾部：渲染进程分段标记与定位

- 派发日期：2026-11-13
- 执行者：子 agent（前端与 e2e；T103 的执行者）
- 分支：`perf/T262-cold-start-tail`
- 依赖：T103（已合并）。T155 依赖本任务的 `cupper:ready`

## 背景

T103 在 runner 上测到冷启动到可用 p50 2–3 s、p95 30–36 s（预算 p95 ≤ 2 s，NFR-6）。慢的几次，主进程、宿主和控制连接都在 2.4 s 内就绪，多出来的几十秒全在控制连接就绪之后、渲染进程可用之前，即窗口这一侧。T103 报告第 2、4 节（`docs/tasks/T103-sp6-render/report-sp6.md`）。

## 范围

**做**（计划 T262 一行；设计 5.9.6"冷启动到可用"、5.9.7"判定与后续"）：
1. 在渲染进程按 5.9.6 加 `performance.mark`，至少三个：窗口的数据连接就绪（握手完成）、索引快照已应用、`cupper:ready`（索引快照已应用且输入框可用）。"当前会话已渲染"要等 Q45 定了启动时是否恢复会话，本任务不加。标记的名字和含义写进设计 5.9.6 由编排者合并时补，你在汇报里给出清单。
2. 用 T103 的场景 1（`spikes/T103-sp6-render/startup.spec.ts`）读这些标记，按段记下每次冷启动的时间，在 runner 上跑，找出慢的那几次卡在哪一段、为什么。必要时在该段内再细分。
3. 原因在应用代码里（例如等错了事件、重试退避、某个请求超时后才继续）就修；要改连接模型或架构的，先停下报给 `main`。
4. runner 上场景 1 修前修后各跑一次（30 次冷启动），给出 p50、p95、最大值和分段对照。

**不做**：启动时恢复上次的会话（Q45）；热启动（等 Q35）；流式渲染的优化（T159）；把场景改写成 nightly（T155）。
