## 逐项意见

1. **根因查得透**：用一个只记录、不改判定的探针量出，中继 0.1 ms 内就关好了，是测试里阻塞的读没被唤醒。再拆开对照：阻塞读遇上对端 `shutdown` 会漏，poll、kqueue、对端关 fd 都不会漏。最后用 xnu 两个版本的源码解释了这个竞争。数据和推断分开写，认可。
2. **产品问题也找出来了**：中继自己的两个阻塞读也会漏掉宿主的半关闭，要等宿主关 fd 才交出 EOF。在 0.04%–0.15% 的情况下，窗口要晚几毫秒到几十毫秒才知道连接断了。修法是读之前先 `poll`，只多一次系统调用。主进程那一端用的是 libuv（kqueue），不用改。
3. **`wait_readable` 放在 `cupper-sys`**，符合"`unsafe` 只能在 cupper-sys"的约束；`recv_closing_fds` 的语义不变。
4. **回归用例是概率性的**：竞争在内核里，做不成确定性的复现。用 20000 次换取修复前几乎必然失败，本机对未修的中继也确实失败了，注释写明了依据。可以接受。

## 记下的点

- 设计已补两句：5.7.2 的 `hostConnection` 一行，以及 5.9 的测试原则。
- **仓库里别处的阻塞读**：其他测试或 testkit 里，凡是用阻塞读等 Unix 套接字的 EOF、对端又用 `shutdown` 结束的，都可能撞上同一个竞争。这次没有排查，写进交接事项，以后碰到同类偶发失败时先查这一点。
