## 逐项意见

1. **第一处，根因在测试**：回合结束和失败原因分属两条流，谁先写进库没有保证。改成等索引里 runtime 本身到 `ready` 或 `failed`，再读失败原因。产品的最终状态是对的，界面本来就分别订阅这两条流，不算产品问题，认可。
2. **第二处，根因在宿主**：`host/exit` 有可能在自己的应答入队之前就开始有序退出，违反了设计 5.2.13 的裁定，客户端看到的是连接断开，而不是"已受理"。
   - 用 `reply_queued` 显式等应答入队，只改 host/exit 一处；
   - 新用例扮演网关，不靠时序，把旧顺序改回去时每次都失败。修得干净。
3. **没有扩大范围**：执行者没有顺手把"所有在路上的应答都在关闭前送出"一起做了，理由写得清楚：会改变所有请求在退出时的行为，手动时钟下还可能挂住退出。

## 记下的点

- **NFR9 崩溃用例**：另开 T206（T099 依赖它）。
- **跨流的读取**：用例读跨流的状态，要等对象本身，不能借另一条流的事件当时序。编排者已把这一条写进设计 5.9.1 的规则；现有用例里有没有类似的写法，留到以后碰到时再改。
- **退出时其他请求的应答**：`host/exit` 以外、和退出撞上的请求，应答仍可能被丢弃。它们能按 `command_id` 重试拿到结果。要不要在关闭连接时等所有在路上的应答，留给以后改宿主生命周期的任务，到时由设计来定。已写进交接事项。
