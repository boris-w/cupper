## 实现上的决定

- **裁判的输入**：
  - `Turn(TurnSignal)`；
  - `Driver(DriverEvent)`：全部驱动事件；
  - `Asked`：交互代理写请求之前；
  - `Resolved`：每次解决请求之后；
  - 定时器。
  - 不直接解析 `DriverEvent::Ask`。交互代理的 `AskRequest` 类型由 T042 维护，裁判只需要"来了一个请求"这件事。
- **裁判的输出**：`Start`、`End`、`Hold(bool)` 和定时器。`Action::turn_input()` 把前三个换成回合机的 `AutonomousStarted`、`AutonomousEnded`、`HoldQueue`，T043 直接调用即可。
- **什么算输出，什么算活动**：
  - **输出**：更新、请求。没有回合时开自发回合；回合正在收尾时，先保持队列，等回合结束后再开；自发回合进行中时，重新计 10 s。
  - **活动**：thread 变为 active、上游重试。不开回合；自发回合进行中时重新计 10 s；静默保护期间重新计 30 s。
  - 标题、配置、命令列表、用量都是元数据，不算活动。
- **运行中的工具**：
  - 工具开始，或者收到非结束状态的更新，记为运行中；收到 `completed` 或 `failed` 时去掉。
  - Settle 时整张表清空：那个回合的工具都被放弃了。之后再有晚到输出，会重新记为运行中，所以晚到条目结束之前，自发回合不会因为静默而结束。
- **thread 的状态**：只有 Codex 会报告。适配器退出后，状态回到未知，10 s 重新计时。这一条是性质测试找出来的：thread 运行中时静默到点，接着适配器退出，回合就一直不结束。
- **不需要的放开**：
  - 第一版在用户回合开始时也放开队列。
  - 变异检验显示这一处是多余的：这个回合进行期间本来就不会出队，结束时裁判会放开。所以删掉了。
  - "用户在空闲时发起回合会解除保护"由回合结束时的放开实现，性质测试检查这一条。

## 组合测试核心（`Session`）

T043 可以照着它接线：
- 驱动事件先给裁判，再给回合机；如果是更新，最后给合并器。
- 回合机这一步的每个动作，按顺序处理：
  - 事件写进日志；
  - `Complete` 不写，由合并器写 `turn.completed`；
  - 其他动作交给端口；
  - 能转成 `TurnSignal` 的，立即交给合并器。
- 回合机这一步结束后，再把这些信号交给裁判；裁判发出的动作，作为回合机的输入回送，可以递归。
- 请求先给裁判（`Asked`），再给合并器（`Interject`，刷出文本并结束活动组），之后才由交互代理写出。
- 交互代理在 Settle 时解决这个回合的全部请求，每解决一个，就给裁判送一次 `Resolved`。

## 性质测试

- **随机操作**：
  - 发送、中断；
  - attach 成功或失败、完成快照、prompt 返回（成功或失败）；
  - agent 的输出：消息、思考、工具开始、工具输出、工具结束；
  - 带 `cost` 的用量、thread 的状态、请求与解决、适配器退出；
  - 推进时间，分三档：0–100 ms、5–12 s、25–35 s。
- **收尾**：每次运行最后把所有东西都答完，推进时间，直到会话空闲、队列为空。
- **PROP-autonomous-dequeue-guard**：
  - 静默结束之后，排队的回合要等到结束时刻和最后一次活动都过去 30 s 才开始；
  - 回合收尾期间到达的输出，先进入自发回合，再轮到排队消息；
  - 空闲且有未暂停的排队消息时，只有静默结束后的 30 s 内才允许不出队，其他情况必须立刻出队；
  - 没有工具运行、没有待处理请求、thread 也不在运行时，自发回合在最后一次输出、活动或解决请求之后 10 s 内结束；
  - 收到 `cost`、thread 变为 idle、thread 为 idle 时工具结束，这三种情况下，空闲的自发回合当场结束；
  - 静默结束时 thread 不在运行；
  - 裁判不会在工具运行或请求待处理时结束回合。
- **PROP-turn-snapshot-immutable**：
  - `turn.completed` 之后，没有任何事件指向这个回合：条目事件、快照记录、第二个 `turn.completed` 都不会出现；
  - 已结束的条目不再变化；
  - 条目只在正在进行的回合里开始，并且在它 Settle 之前；
  - 回合的条目都在 `turn.completed` 之前结束；
  - 晚到条目指向一个在已完成回合里被放弃的工具调用，每个调用在每个回合里只有一个。
- **每次运行都检查**：
  - 同一时刻只有一个回合；
  - 空闲时 agent 产生的输出（包括请求）会立即开一个回合（K9，T014 的裁定）。

### 变异检验

手工改坏 18 处，逐个运行。

**性质测试抓到的 15 处**（都是由负责那条规则的检查抓到的）：

| 变异 | 抓到它的检查 |
|---|---|
| 静默结束后不设 30 s 保护 | 30 s 安静 |
| 静默结束时不保持队列 | 30 s 安静 |
| 收尾期间的输出不保持队列 | 先进入自发回合 |
| 收尾期间有输出，回合结束后不开自发回合 | 队列必须出队 |
| 回合结束时不放开 | 队列必须出队 |
| Settle 时不清空运行中的工具 | agent 已完成就当场结束 |
| thread 在运行也按静默结束 | 静默结束时 thread 不在运行 |
| 结束时不看运行中的工具 | 工具运行时不结束 |
| 不计请求 | 请求待处理时不结束 |
| 静默改成 20 s | 10 s 内结束 |
| 忽略 `cost` | 当场结束 |
| 回合机忽略 `HoldQueue` | 先进入自发回合 |
| 合并器在收尾期间不暂存更新 | 条目在 Settle 之前开始 |
| 晚到输出写回原条目 | 已结束的条目不再变化 |
| 每次晚到更新都新建条目 | 每个调用每个回合只有一个 |

**其余 3 处**：
- 静默保护期间有活动，却不重新计 30 s：性质测试很少能构造出"保护期间有活动、之后又在 30 s 内出队"的序列。裁判的场景测试直接断言了"上游重试会重新计时"，它抓到了。
- 用户回合开始时不放开：这是等价变异，于是删掉了这处多余的放开（见上文）。删掉之后，再把"回合结束时放开"也改坏，这个变异被性质测试抓到。
