## 开工前读到的现状

- SP-4a 的 `measure.rs` 有两条：冷启动（spawn 到索引快照，20 个会话、30 次）和内存（空闲、6 个会话）。原型只作参考，不依赖。
- `xtask ci perf` 已登记为持机器锁的作业，`run: None`，在 `nightly` 组合里。
- PERF-snapshot（T186）是库里的 `#[ignore]` 用例，只往 stderr 打印中位数（每种情况 5 个样本）。
- 设计 5.9.6 的口径：
  - 每项至少 30 个样本，报 p50、p95、最大值；
  - CI 机器只看趋势，阈值是历史中位数的 1.5 倍；
  - 绝对预算只在参考硬件上判定：宿主冷启动 p95 ≤ 400 ms，索引快照（200 个会话）≤ 50 ms，宿主内存（6 个活跃会话）≤ 64 MiB。
- CI 摘要已有一个只写机型泛称的 `facts::machine`（例如 "MacBook Pro (Apple M5 Pro)"），历史数据沿用它。

## 方案

- **测量值怎么交出来**：PERF 用例不往 stdout 打印给人看的行（`--nocapture` 会打乱 libtest 的输出），而是经宿主库里一个只在 `test-harness` 构建中存在的 `perf::record`，把原始样本写到环境变量 `CUPPER_PERF_OUT` 指向的 JSONL 文件。PERF-snapshot 改为同样调用它。
- **`ci perf` 作业**：
  - 用 release 构建跑 `tests/perf.rs` 的三个 `#[ignore]` 用例，单线程；再跑 PERF-snapshot；
  - 读样本，算 n、p50、p95、max；
  - 与 `testdata/perf/history.jsonl` 里同一指标、同一机型的历史 p50 中位数比较，超过 1.5 倍判为退化；
  - 每次运行追加一行到历史，字段为日期、提交、版本、机型泛称、指标、单位、n、p50、p95、max。
- **三个用例**：
  - PERF-host-cold-start：经 `test/seed` 灌 200 个会话（其中一个有 1,000 条的回合），30 次"拉起宿主到拿到完整的索引快照"；
  - PERF-index-snapshot：同一份数据，宿主运行中 30 次"连接、订阅索引到最后一页"；
  - PERF-host-memory：6 个会话同时跑带输出的回合，期间和之后按 100 ms 采样宿主 RSS，至少 30 个样本。
- **顺带评估**：`flood_mixed` 分别测"只有假 agent"和"经宿主"两种情况；指纹遍历用一个合成的 10 万文件工作区计时。都是一次性测量，结论写进汇报。

## 顺带评估（一次性测量，release 构建，持机器锁；测量代码没有提交）

### `flood_mixed` 的速度（T062 的交接）

| 情况 | 时间 | 会话流的事件数 |
|---|---|---|
| 只有假 agent，`flood_mixed 2000 10` | 53 ms | — |
| 只有假 agent，`flood 2000 10` | 49 ms | — |
| 只有假 agent，`flood_mixed 6000 200` | 136 ms | — |
| 经宿主，`flood_mixed 2000 10` | 5,202 ms | 6,011 |
| 经宿主，`flood_mixed 500 10` | 1,325 ms | 1,509 |
| 经宿主，`flood 2000 10` | 93 ms | 14 |
| 经宿主，`flood 4000 10` | 179 ms | 16 |

结论：时间花在宿主。假 agent 发 2,000 个交替条目只用 53 ms。经宿主时：
- 每个条目约 2.6 ms，即每个事件约 0.87 ms；
- 每个条目是 `item.started`、`item.delta`、`item.completed` 三个事件，写入时合并只能合并同一条目的连续 delta，所以这些事件逐个提交；
- 同样 2,000 块文本进同一个条目，只有 14 个事件、93 ms。

是否达标：设计 5.9.6 没有"条目吞吐"的预算，有关的是"输出到屏幕 p95 ≤ 100 ms"和"同时 6 个会话"。真实 agent 每秒出的条目是个位数到几十个，离每秒约 380 个还很远，因此算达标。`flood_mixed` 是专门拼出来的压力形态。

要提速，可以在会话 actor 里把同一步里不能合并的事件攒成一批再追加。这条留作改进建议，不在本任务里做。

### 回合指纹的遍历代价（T186 的交接）

合成工作区共 10 万个文件：1 万个已跟踪（`src/`）、9 万个在被忽略的 `node_modules/` 里，另有一个 `.gitattributes`；热缓存，测 7 次。

| 做法 | 时间 |
|---|---|
| 现在的 `Fingerprint::take`（遍历整个工作区） | 中位数 42.9 ms（最小 42.3，最大 48.1） |
| 对照：`git ls-files -co --exclude-standard` 只列 `.gitattributes` | 19.1 ms |
| 对照：同上，列出全部已跟踪和未忽略的文件 | 16.2 ms |

结论：
- 不超预算。快照预算是 9.6 万文件 ≤ 0.5 s，指纹每个回合取两次（开始和结束），合计约 86 ms，在预算里占不到两成。
- 暂不改成"只看已跟踪和未忽略的"。改了每次能省约 25 ms，但要多拉起一次 git 进程，而且会被仓库配置影响（例如 `core.excludesFile`）。
- 遍历时间随被忽略目录的大小线性增长：被忽略的文件到百万级时约 0.4 s，届时再改。

## PERF-bridge-gate 要不要进历史（建议）

建议进。
- **做法**：e2e 作业在夜间跑 `gate.spec.ts` 时，也设置 `CUPPER_PERF_OUT`；用例把每次测得的主进程事件循环延迟写成同样格式的一行（例如 `bridge_loop_delay_p99`，单位 ms）。
- **共用代码**：`perf` 作业里统计、追加历史、判定退化这一段挪成 `xtask` 里的共用函数，e2e 作业调它，指标照样按 1.5 倍历史中位数判定退化。
- **两条判定的关系**：它本身的绝对闸门（p99 < 5 ms）照旧由用例断言，历史只看趋势。这一步要改 e2e 的 TS 用例和 e2e 作业，建议并进 T078 的后续或单开一个小任务。
