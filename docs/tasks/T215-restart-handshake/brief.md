# T215 握手被拒时桌面能弹"重启宿主"，重启后窗口重新连接

- 派发日期：2026-11-02
- 执行者：子 agent（工程师，桌面主进程与宿主网关都可能涉及）
- 分支：`fix/T215-restart-handshake`
- 依赖：无（T214 发现）。T099 依赖本任务

## 背景

T214 测"重启宿主"时发现两处问题（见 T214 的 report.md 第"遗留问题"1、2 条和 notes.md）：

1. **握手被拒时，桌面有时只看到连接关闭**。
   - 现象：第二个 app（key 不同）去连前一个 app 拉起的宿主，控制连接的失败原因 3 次里有 2 次是 `closed`，不是 `unauthenticated`；窗口连接也见过。
   - 后果：`apps/desktop/src/main/index.ts` 只在 `unauthenticated`、`host_unverified` 时弹"需要重启宿主"。报 `closed` 时不弹，也不再重试，新的 app 一直连不上。这正是升级 App 或换了 key 之后第一次打开时会遇到的情形。
   - 推测（没有核实）：宿主回完握手错误就关掉连接，原生扩展在宿主关闭之后读到的字节按 5.8.1 被拒收（每次读取都比对令牌，`PeerExited` 时不交付）。和 T213 是同一类事，发生在桌面这一侧。
2. **重启宿主之后，窗口不再连接**。
   - 现象：重启前窗口的第一次 `open` 已经失败；重启后控制连接回到 `ready`，但没有人再为窗口发起 `open`。20 s 内 `host/status.clients` 里一直没有 `window`。

## 范围

**做**：
1. **核实第 1 条的原因**：在本机单份复现，确认被拒收的是不是握手的错误应答（看原生扩展和主进程的日志，必要时临时加日志，不提交）。给出证据。
2. **修第 1 条**：桌面要能可靠地得到握手被拒的原因，弹出"需要重启宿主"。
   - **5.8.1 不放宽**：在 `PeerExited` 之后交付已读到的字节，这条路不能走（T196、T213 的裁定）。
   - 可以考虑的方向（由你实测后选，汇报里说明理由）：
     - 宿主在握手失败时先送出错误、半关闭写端，等客户端读完关掉或等到一个短的上限再关连接，让客户端读的时候令牌比对还能通过；
     - 或者其他不放宽 5.8.1 的办法。
   - 如果要改宿主的行为或协议的约定，先用 SendMessage 把方案和要改的设计章节发给 `main`，编排者同意后再写。
3. **修第 2 条**：重启宿主、控制连接回到 `ready` 之后，已经打开的窗口重新连接。
4. **用例**：
   - 第 1 条：确定性的用例（宿主或网关一侧的集成测试，或者桌面一侧的单元测试），守着"握手被拒时客户端拿到的是拒绝原因"；能稳定复现的话做修前修后对照。
   - 第 2 条：e2e 覆盖"key 不同的 app 连上旧宿主 → 弹重启 → 重启后窗口连上"。看有没有现成的编号可挂（T007 的 E2E 用例）；需要新编号时先告诉 `main`。
5. 在 runner 上用 `e2e-repeat` 把新的 e2e 用例连跑 100 次以上；要触发时把参数和提交发给 `main`。

**不做**：
- 不放宽 5.8.1 的逐次比对令牌。
- 不改退出流程（T214 刚改过）。
