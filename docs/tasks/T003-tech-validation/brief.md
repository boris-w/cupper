# T003 技术验证：Q8（Claude）、Q9、SP-4b 遗留第 7 条与版本复核

- 派发日期：2026-10-19
- 执行者：子 agent（原型实测工程师）
- 分支：`spike/T003-tech-validation`
- 依赖：无（M1a 第 0 波，结论即检查点 K1，决定驱动层的写法）

## 背景

驱动层（T050–T055）依赖几个还没实测的前提：
- **Q8**：同一个 claude-agent-acp 进程上，多个会话同时发 prompt 是否可靠。这是 ADR-09"每种 agent 共用一个适配器进程"的前提。SP-1 只测过同一会话内的并发。
- **Q9**：ACP Rust SDK `=3.3.0` 能否发送 `_session/steering` 这类扩展请求，能否收到 `_auth/status_update` 和 `$/cancel_request`。
- **SP-4b 遗留第 7 条**：真实适配器拉起工具命令时，会不会调用 setsid。这关系到提权申请的血缘检查（5.8.4）。
- **版本复核**：锁定的适配器、Electron 等版本，以及测量闸门的负载数字（5.7.1），在开工当天是否需要调整。

用户已许可用真实的 Claude CLI 跑这些剧本，会消耗少量额度（U-R5）。

## 目标

给出 K1 的判定，以及 Q9、SP-4b 遗留第 7 条和版本复核的结论，供驱动层的任务使用。

## 范围

**做**：
1. **Q8（Claude）**：用 SP-1 的 TS 客户端（`spikes/SP-1-adapter-behavior/`）编写并发剧本。通过条件见设计 5.9.5：两个会话同时各发 3 个 prompt，全部在 5 分钟内返回，输出没有串到另一个会话，重复 3 轮。记录每一轮的数据。
2. **Q9**：用 `agent-client-protocol = "=3.3.0"` 写一个最小的 Rust 探针，作为 ACP 客户端连接 claude-agent-acp，逐项确认：
   - 能否发送 `_session/steering`；
   - 能否收到 `_auth/status_update`；
   - 能否收到 `$/cancel_request`。

   不支持的项，说明需要线路分接层（5.6.10）在 stdio 上处理什么。
3. **SP-4b 遗留第 7 条**：让真实 agent 执行一条会持续几秒的命令，观察进程树，看命令的会话 ID、进程组是否与适配器相同，即是否调用了 setsid。
4. **版本复核**：
   - 查询 claude-agent-acp、codex-acp、Electron 当天的最新版本，与设计锁定的版本对比；
   - 按 SP-1 录制里的最高输出速率，复核测量闸门的负载数字（每条会话流每秒 25 帧，每帧约 2 KB）；
   - 给出版本建议。

**约束**（安全评审的要求，必须遵守）：
- 临时 git 仓库放在每个用户自己的临时目录下，不用作者的任何真实项目。
- 剧本固定，不让模型联网取内容。
- 权限模式显式设为 `default`；只选不持久的选项（`allow_once`、`reject_once`），不选任何"总是允许"类选项。
- 用最便宜的模型，例如 haiku。
- **运行前后做哈希对比**：`~/.claude/settings.json`，以及 `~/.claude.json` 中与权限有关的字段。报告里只写字段名和"是否变化"，不写内容。
- **不修改任何用户配置**。Claude CLI 运行时自己写入的会话记录、项目目录，列成清单写进 `.private/cleanup/T003-leftovers.md`（不入库），由编排者请用户确认后再清理。子 agent 不删除这些内容。
- 外发请求不带个人信息，需要时用 `cupper-research` 作占位。录制或日志里如果出现用户名、本机路径、会话 ID，入库前先脱敏，脱敏方法同 SP-1。

**不做**：
- 产品代码。原型代码放在 `spikes/T003-tech-validation/`，产品代码不依赖它。
- Codex 的部分：Q8 的 Codex 部分在 M1b 的 T102 里做。
