## 逐项意见

1. **用真实界面持有 4 条会话流**：界面的订阅策略正好是"索引流 + 当前会话 + 最近 3 个"，不在主进程打桩、不另做负载页面，测的就是真实路径。
2. **5,000 个事件的重新同步**由测量钩子以游标 0 订阅灌好的会话来模拟：宿主只对带游标的订阅重放、新订阅一律拿快照，界面自己的订阅产生不出这种负载。编排者事先认可。
3. **遮挡的局限**：Playwright 下被盖住、最小化、`hide()` 之后页面仍是 `visible`、动画帧照常，所以"遮挡"一份是盖住窗口再停掉动画帧来模拟。对 store 来说隐藏页面唯一要紧的变化是动画帧停止（设计 5.7.1：只有通知重渲染合并到动画帧，应用与确认不依赖它），实测停帧时应用与确认照常、没有积压。Chromium 自己对隐藏页面的计时器节流在 e2e 里复现不了，如实列为局限。
4. **钩子只在 e2e 构建**：`window.__cupperGate`，`flavors.test.ts` 加进检查。
5. **T077 的多一次复制**：判定负载下约 0.09 ms/s，5 MB blob 一次约 3.2 ms，不需要处理。

## 记下的点

- **偶发的长延迟**：9 次里有 5 次 max 在 34–55 ms，p99 不受影响。来源没查（可能是 GC 或 blob 集中到达）；以后要看尾部延迟时可给主进程加时间线采样。
- **真正的隐藏状态没测到**：要在不连 DevTools 的情况下启动 App、只经主进程 inspector 测量，另写脚本。记交接。
- **判定负载的表述**：宿主 40 ms 合并后，会话流实际约 20 帧/s、每帧约 2.6 KB，字节数与设计相当。设计 5.7.1 已补按字节率的说明（编排者）。
