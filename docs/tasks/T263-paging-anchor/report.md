## 做了什么

**原因有两条路径**。两条的位移都是新插入的 3 行"实测 − 估算"的差，没人补上。

- **26 px 是哪来的**：sp1 种子每翻一页插 3 行：用户消息、回合头、最终回答。本机 headless 实测 79 + 40 + 39 = 158，估算 3 × 44 = 132，差正好 26。虚拟器自己补偿的那次滚动也是 132 → 158。
- **路径 1：页在用户滚动 150 ms 之后才到**。
  - 这时虚拟器在提交阶段同步量新行；列表还停在顶部，新行不在视口上方，虚拟器不补偿。
  - 复原读的 `measurementsCache` 是渲染时的旧视图，锚点还按 44 估算。
- **路径 2：页在用户滚动 150 ms 之内就到**。
  - 新行在复原之后才由 ResizeObserver 测量。那一刻虚拟器还没收到复原产生的滚动事件，scrollOffset 仍是 0，于是不补偿。
  - jsdom 能稳定复现这个顺序。headless Chromium 里滚动事件总先于 ResizeObserver 到达，复现不了。
  - 真实 App 里插入新行的那次渲染可能落在动画帧里（流的视图按帧 flush），是推断，没有直接观察到。

**修复（最终形态）**：只改了 `ScrollKeeper`。
- 复原后不再立刻放开锚点，而是继续守住；锚点行的位置一变（行量完后重新渲染时），就放回 start − delta。
- 放开的时机：用户滚动（`intend()`：滚轮、触摸、按键、按住滚动条）、`leave()`、`follow()`，或者来了一次不是我们写入的滚动。
- 锚点只在用户离开底部、点了翻页之后才存在，流式增长和贴底不受影响。
- 和虚拟器自己的补偿不会叠加：两边求的都是锚点行该在的绝对位置。
- 行的新位置和放回去的 scrollTop 在同一次提交里落地，不会画出一帧错位。
- 第一轮加的 `takeSnapshot()` 在新机制下不再需要，已经去掉（经你确认）。StreamList.tsx 与 main 相同，只留一套机制。

**测试**：UNIT-stream-anchor 新增 3 个用例。
- ScrollKeeper 用例：锚点行每次移动都放回去；四种情况都会放开锚点。
- DOM 用例 A：新行在渲染时量（路径 1）。
- DOM 用例 B：新行在复原之后、虚拟器看到那次滚动之前量（路径 2）。

**范围外**：`leave()` 的注释挪回原处（T256 时我放错的），单独一个提交。

## 关键取舍

- **第一轮只修了路径 1**（`takeSnapshot` 读当前测量），runner 复测还有 16 页位移。改成守住锚点后两条路径都覆盖，也覆盖其他"复原后行又变高"的情况。
- **放开锚点的条件**：用户操作、程序跳转，以及不是我们写入的滚动（例如浏览器因焦点或查找而滚动）。这样守住锚点不会和用户或浏览器的滚动抢位置。
- **runner 诊断没加**：你同意先带修复复测，复测已经全为 0。
- **规模**：`cargo xtask size` 为 +129 −11，停止线 150，比开工前估的 50–100 多。主要是 scroll.ts 的注释和两个 DOM 用例。
