# T223 迁移样例库与已发布脚本的锁定（P-4）

- 派发日期：2026-11-03
- 执行者：子 agent（Rust 工程师，宿主存储）
- 分支：`test/T223-migration-samples`
- 依赖：T160（自用构建）。**用户安装 Cupper Local 之前合并**

## 背景

计划 P-4：T160 之前表结构只改 `0001`，T160 之后每次改表结构都附样例数据库和迁移用例。T160 核对时发现（`docs/tasks/T160-selfuse-build/report-r1.md` 遗留第 5 条），迁移框架本身够用，但 P-4 要的基础设施还没有：
- 没有按版本存放的样例数据库；
- 没有"把每个样例库迁到最新"的通用用例；
- 没有防止原地修改已发布脚本的检查。`0001_initial.sql` 至今被原地改过很多次。用户开始用 Cupper Local 之后，真实数据停在那时的 `0001`，再原地改就会破坏它。
- `migrate.rs` 的注释还写着"Until T160 … changes in place"。

## 范围

**做**（计划 T223 一行，P-4，设计 5.4.6）：
1. **锁定已发布的脚本**：对已发布的迁移脚本固定哈希，从 T160 合并时的 `0001` 起；改动已发布脚本的提交在 CI 上失败，提示改表结构只能加新脚本。锁放在哪里、怎么更新"已发布"的集合由你提议，写进汇报。
2. **样例数据库**：按版本存放（例如 `testdata/` 下 v1 的 SQL 转储，由宿主在测试里生成，不是手写），覆盖每张表至少几行有代表性的数据。不能含个人信息（`testdata-scan` 会扫）。
3. **通用用例 IT-migrations-samples**（已登记，挂在 T223 下）：把每个样例库迁到最新，检查 `schema_version`、`PRAGMA integrity_check`、`foreign_key_check`、数据保留，再让宿主在上面启动。以后每个改表结构的任务只需加一个样例库。
4. 改 `migrate.rs` 的注释；在 `docs/` 里合适的位置（例如 5.4.6 的建议，写进汇报）说明以后改表结构的步骤。

**不做**：改表结构本身；事件升级器（`view_v`）的样例。

## 验收标准

- [ ] 原地改 `0001` 的变异检查在 CI 上失败（在汇报里给出验证方法，例如本机临时改一行跑检查）。

- [ ] PR 上 GitHub CI 的 8 个检查都通过，汇报里写上 PR 和运行的链接（守则第 9 条）。
