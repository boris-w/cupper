# P01 起草任务拆分（docs/03-plan.md）

- 派发日期：2026-10-16
- 执行者：子 agent（架构师，兼任规划）
- 分支：`docs/P01-task-plan`
- 依赖：`gate/design`（技术设计 v1.0，ADR-01 至 ADR-11 已采纳）

## 背景

技术设计已于 2026-10-16 确认（tag `gate/design`）。阶段 ③ 的产出是 `docs/03-plan.md`：把 M1a 和 M1b 拆成一个个开发任务，交给子 agent 在独立 worktree 里逐个完成。用户在 `gate/plan` 时确认"任务顺序和粒度"。

任务的执行方式（见 `docs/00-process.md`"任务生命周期"）：
- 编排者从 `03-plan.md` 里挑出依赖已满足的任务，写好 brief 后派给子 agent；
- 互不依赖的任务可以并行；
- 每个任务单独一条分支，通过 review 和 CI 后用 `--no-ff` 合并。

所以拆分的质量，直接决定开发阶段能不能平稳推进、可以并行到什么程度。

## 目标

起草 `docs/03-plan.md`，要求做到：编排者照着它就能逐个写 brief、派发任务；每个任务都能独立完成、独立验证，合并后 main 始终可用。

## 范围

`03-plan.md` 应包含以下内容。

1. **拆分原则**
   - 粒度：一个任务交给一个子 agent 一次完成。建议上限为改动约 1,500 行（含测试），太大的要拆开。
   - 每个任务合并后，main 能构建、测试全绿。
   - 契约先行：类型、接口先于实现。
   - 测试基础设施先行。
   - 哪些情况可以并行。
2. **任务清单**：分 M1a、M1b 两部分。每个任务写明：
   - 编号：`T` 加三位数字，例如 M1a 用 T001–T099，M1b 用 T101 起；技术验证类任务也编进去，用名称标明。
   - 名称、分支类型（feat、test、build、ci、chore 等）。
   - 对应的设计小节。
   - 前置依赖。
   - 做什么、不做什么：一两句，指出边界。
   - 验收标准：引用 5.9.10 的用例编号；如果用例是新任务自己引入的，写明会新增哪些编号。
   - 规模估计：S、M、L，L 的要说明为什么不能再拆。
   - 是否需要用户参与：用真实 CLI 时会消耗额度、会弹系统授权框、需要签名证书或 Apple Developer 账号等。
   - 涉及哪些 CODEOWNERS 式的区域：Rust 宿主、协议、TS、桌面主进程、CI，用来判断哪些任务可以并行而不冲突。
3. **依赖图**：用 mermaid 画出任务之间的依赖，标出关键路径。
4. **派发波次**：按依赖把任务排成若干波，每波内可以并行。标出关键的检查点，例如：
   - 协议契约冻结；
   - windowBridge 测量闸门，不通过时要改方案，写明影响哪些后续任务；
   - Q8 的技术验证，不通过时要启用后备方案，写明影响哪些任务；
   - M1a 的退出；
   - SP-6；
   - Q29。
5. **覆盖核对**：
   - 5.12.2、5.12.3 的每一项落到哪个任务；
   - 5.12.4 追溯矩阵里每条 P0 需求的验证用例由哪个任务产出；
   - 5.13 里定为"M1a、M1b 实现时验证"的待定问题，由哪个任务负责。

   保证没有遗漏。
6. **需要用户参与或提供的事项**：按时间顺序列出。例如：
   - U-R5 的真实 CLI 并发剧本；
   - SP-10 的通知部分（会弹系统授权框）；
   - M1b 发布所需的 Developer ID 证书和公证凭据，也就是是否已有付费的 Apple Developer Program 账号（PRD 的 U7 原定在 M3 前核实，但 M1b 的签名公证就需要）；
   - 人工验证清单里需要作者亲自做的项。
7. **风险与应对**：拆分层面的风险，例如关键路径上的大任务、需要外部条件的任务、后备方案触发后的返工范围。

不做：
- 不写产品代码；
- 不写每个任务的 brief（brief 由编排者在派发时写）；
- 不修改设计、ADR、PRD。

发现设计里有遗漏或矛盾时，记进 `03-plan.md` 的"待处理"一节，并在汇报中提出。

## 要求

- 用中文写，先给结论，表格和列表优先。文风参照 `docs/02-design.md`。
- 任务清单用表格，每个任务一行；超出表格能装下的说明，放到表后的注释。
- `03-plan.md` 开头写版本和状态（v0.1，草案，待计划评审）。
- 按主题拆成几个提交，提交信息带 `Refs: P01` 和 `Co-Authored-By`，不出现任何 claude.ai 链接。
- 遵守 `CLAUDE.md` 的子 agent 守则：
  - 只在指定的 worktree 里工作；
  - 不修改用户配置；
  - 不运行真实的 Claude 或 Codex CLI；
  - 外发请求不带个人信息。

## 验收标准

- [ ] 5.12.2、5.12.3 的每一项，都能在覆盖核对里找到负责的任务。
- [ ] 5.12.4 里每条 P0 需求的验证用例，都有产出它的任务。
- [ ] 每个任务都有依赖、验收标准（用例编号）、规模、区域。
- [ ] 依赖图里没有环；关键路径和波次都标出来了。
- [ ] 需要用户参与的事项按时间顺序列出。
- [ ] mermaid 图能通过解析，链接和锚点没有失效。
- [ ] 文档里没有个人信息。

## 汇报要求

`03-plan.md` 和工作笔记 `notes.md`（可选）提交在任务分支上。完成后按 `docs/templates/task-report.md` 的结构，把汇报全文作为最终回复返回，由编排者存档为本目录下的 `report.md`。不要自己创建 `report.md`。
