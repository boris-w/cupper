## 逐项意见

1. **原始客户端与假宿主只在测试里**：原始客户端自己分帧、自己给 `auth`；假宿主先发 `host/hello`，对 `initialize` 回金样例结果、`host_proof` 是随机值，记下对方发来的一切。
2. **E2E-SEC-fake-host 改测"接管"**：App 连上真宿主后由假宿主占住套接字、再杀真宿主。假宿主只收到带证明的 `initialize`，没有 `harness_key`、没有命令，App 弹出"需要重启会话宿主"。"启动时套接字就被占住"测不了，原因是对话框替身在 `launch` 之后才装，见"记下的点"。
3. **握手拒绝的实测与设计对照**：表格清楚。设计没写的三点（`dev_key` 先核对拉起宿主的进程再核对证明、构建不提供的认证方式、非桌面身份带 `role`）编排者已补进 5.8.1（`3dd28f0`）。
4. **上传缓冲就地修**（单独提交，+37 −1，不改接口）：每条连接最多 64 个未决 blob，零长度分片和乱序、超限后的空条目都算在内。修之前 50 万个分片让宿主 RSS 涨约 122 MB 且断开后不还，修之后约 12.6 MB。被攻破的渲染进程原本能用这个办法耗尽宿主内存，这是一处真实的加固。只读的 cli 本来就填不了缓冲。
5. **Q27 的结论**：可行但有局限。正对照（`nc -u` 连文档地址、`connect` 不发包）保证"什么都没采到"不会被当成通过；10 次都在第 2 个样本抓到。局限（快照采样漏掉短连接、代理的 fake-IP）写清了。编排者据此关闭 Q27、更新 5.9.4（`3dd28f0`）。

## 记下的点

1. **所有 e2e 用例启动的宿主都会连公网的 npm 仓库**：夹具没设 `runtime.registry_url`，宿主按运行时安装对 registry.npmjs.org 建 8 条 HTTPS 连接，尽管用的是假 agent。测试不应联网，要在夹具里默认指向回环上关着的端口（或本地夹具仓库），并确认安装失败的状态不影响别的用例的界面。另开小任务尽快修。
2. **启动时弹出的对话框接不住**：替身在 `launch` 之后才装，App 启动时就弹的对话框在 e2e 里是真的原生对话框。可以在 e2e 构建的主进程里提前装替身，与上一条并成一个小任务。
3. **e2e 构建的 CLI 不带密钥时是弱校验**（只按 `peer`），会连上假宿主；本任务只测了带 `harness` 密钥的情形（退出码 4）。
4. **T093 的锁测试偶发失败**（"the lock outlived its command"，负载下 12 s）：执行者推测同一测试进程里别的测试 fork 出的子进程在 exec 之前短暂持有锁文件的描述符。交 T093 的执行者修。
