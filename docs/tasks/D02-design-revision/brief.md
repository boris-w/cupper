# D02 按设计评审结论修订详细设计

- 派发日期：2026-10-16
- 执行者：子 agent（架构师）
- 分支：`docs/D02-design-revision`
- 依赖：D01（已合并，`3a8da30`）；设计评审会（`docs/meetings/2026-10-16-design-review/`）

## 背景

D01 的详细设计草案已经过设计评审会。三位评审者共提出 4 条阻断、45 条重要意见。架构师逐条回应后，评审者又做了确认，编排者对剩下的分歧做了裁定。现在按这些结论修订设计，修订合并后交用户确认，再打 `gate/design`。

## 目标

修订 `docs/02-design.md` 第 5 节和 `docs/design/` 下的文件，使全部阻断和重要意见，以及评审者确认时提出的附加条件，都在设计里有明确的落点，而且彼此不矛盾。修订后的设计应能直接用于阶段 ③ 拆任务。

## 必读材料（依据的优先级从高到低）

1. `docs/meetings/2026-10-16-design-review/minutes.md`：编排者的裁定 D1–D16，以及待用户决定的事项。出现冲突时以它为准。
2. 三份第二轮确认：同目录下的 `desktop-engineer-confirm.md`、`security-engineer-confirm.md`、`test-engineer-confirm.md`。其中"附条件关闭"所列的条件都要落实。
3. `architect-response.md`：逐条回应、统一方案 (a)–(e)、建议级意见的处理、修订工作量、契约冻结检查。
4. 第一轮的三份评审原文：`desktop-engineer.md`、`security-engineer.md`、`test-engineer.md`。
5. 被修订的对象：`docs/02-design.md`、`docs/design/*.md`；D01 的 `notes.md`、`review.md`。
6. 按需查阅：ADR-01 至 ADR-11、`docs/01-prd.md`、实测报告（SP-1、2、4a、4b、5），以及 `spikes/` 下的代码与录制。

## 范围

1. 按 `architect-response.md` 中"修订工作量"一节，逐个文件修改，并加上纪要和三份确认里新增的内容。
2. **待用户决定的事项**（Q5、Q6、Q12、Q13、Q22、U-R1 至 U-R5）一律按纪要中的"建议"来写，并在正文中标注"待用户确认（U-Rn）"。注意 U-R4 用的是编排者调整后的建议。
3. **评估纪要 D8 中的独立 GIT_DIR 快照方案**：快照改用 cupper 自己的 GIT_DIR，用 alternates 指向仓库的对象，只拷贝白名单里的配置和 `info/exclude`。
   - 可以在 `$TMPDIR` 下自建目录，只用 git 做小实验，结束后删除。
   - 判断它和 SP-5 的快照方案（临时索引、私有对象目录）能否兼容、对 `.gitattributes` 和 LFS 有什么影响、性能是否可以接受。
   - 可行就写进 5.2.10 作为快照路径的方案；不可行就写明原因，保留"每次调用前读配置并覆盖"的方案。
   - 实验过程和结论记在 `notes.md`。
4. **契约冻结清单**：在 5.12 中新增一个小节，列出 M1a 冻结前必须定下来的协议和 ShellAPI 改动，即纪要 D16 中的第 1、2 组，以及冻结机制。
5. **更新 5.13**：
   - 关闭 Q1、Q4、Q11、Q14、Q15；更新其余待定问题；新增 Q26–Q33；
   - 改写 5.13.2"对 ADR 的修订建议"，作为编排者修订 ADR 的依据；
   - 改写 5.13.3"对 PRD 的影响"，加入 PS-2 的信任步骤（U-R1）和 SEC-9 的解释（U-R2）。
6. `docs/02-design.md`：版本改为 v0.7，更新第 5 节的"主要结论"；如果第 1 节的组件图受影响（例如审查文档、项目信任），一并更新。
7. **新建核对表** `docs/tasks/D02-design-revision/checklist.md`：每条阻断意见、重要意见、确认中的附加条件、纪要的 D1–D16 各占一行，写明修订后的落点（文件 + 小节）。编排者会按这张表逐条审阅。

- 按主题拆成 8–10 个提交，参考 `architect-response.md` 里建议的分组。提交信息带 `Refs: D02` 和 `Co-Authored-By`，不出现任何 claude.ai 链接。
