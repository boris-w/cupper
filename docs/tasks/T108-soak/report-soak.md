## 怎么测的

- 用 `tools/e2e` 的夹具启动打包的 e2e App，用 CLI 新建一个假 agent 会话，打开后一直显示在窗口里。
- 每 5 分钟经 CLI 给这个会话发一个回合，内容固定：
  - 一个 `execute` 类的工具调用，完成时带 4 KB 输出；
  - 每秒 20 段、每段 80 字符的流式输出，持续 10 秒；
  - 最后一句结束语。
- 第一个回合之前采一次样，之后每个回合结束后采一次：
  - **主进程**：Electron `getAppMetrics` 的 working set，以及 `process.memoryUsage().heapUsed`；
  - **主文档的渲染进程、审查文档的渲染进程**：分开采。按 `webContents.getOSProcessId()` 和审查 iframe 的 `osProcessId` 对应到各自的 working set；JS 堆用各自页面的 `performance.memory.usedJSHeapSize`；
  - **宿主**：`ps` 的 RSS；
  - **`host.db`**：会话数、事件数。
- 单位都是 MB（2^20 字节），取整。

## 实际浸泡了多久

- **300 分钟**，即汇总里的 `soaked_minutes`。
- 时长由 `run.sh` 按构建用时倒推：330 − 6 = 324 分钟，封顶取 300。

## 有没有持续增长的进程

- **主进程、审查文档渲染进程**：平稳。主进程从第 25 分钟起一直在 121–126 MB；审查文档在 76–77 MB；两者的 JS 堆不涨。
- **宿主**：前三个小时从 33 MB 涨到 44 MB，从第 185 分钟起一直是 44 MB，**已经停止增长**。这时事件数约 6,500，之后涨到约 10,300，宿主的内存不再跟着涨。
- **主文档渲染进程**：一直在缓慢上升，但**增速在放慢**：每小时中位数分别多出 7.5、5.5、2.5、1.5 MB。5 小时结束时还没有完全停下。它的 JS 堆只在 13–20 MB 之间随 GC 起伏，没有同步上涨。

## 可疑的地方

1. **主文档渲染进程的 working set 在涨，JS 堆不涨**：
   - 增长不在 JS 对象上。可能是 Blink 的渲染缓存、样式和布局数据、图层或字形缓存，也可能是一个会话的条目越积越多（60 个回合约 1 万个事件，都在同一个开着的会话里）。
   - 增速逐小时放慢，更像是在接近一个上限，而不是线性泄漏。但 5 小时内没有完全停下，结论只能到这一步。
   - 要确认的话，可以：
     - 跑更长（受 6 小时作业上限所限，要拆成几次）；
     - 每小时切换一次会话，或关掉再打开会话，看能否回落；
     - 用 `contentTracing` 或渲染进程的 `memory-infra` 看增长落在哪一类。
2. **宿主在前三个小时涨了约 11 MB 后停住**：
   - 时间上与 `host.db` 里的数据增长对得上，推测是 SQLite 的页缓存逐渐填满（每个连接的缓存上限固定，填满后不再涨）。没有验证。
   - 增长量 +11 MB，低于上限 20 MB，但占了一半以上。浸泡更久、事件更多时，可能需要再看一次。
3. **开头的回落**：
   - 起点的主进程 171 MB、审查文档 113 MB，到第 25 分钟分别降到 122 MB、76 MB，是启动后的释放。
   - 第 1 个回合后主文档冲到 212 MB，随后回落到约 160 MB。
   - 这也说明 5.9.6 用"预热 30 分钟之后"来算增长是对的。

## 局限

- **只测了一个会话的稳态**：一直是同一个会话，没有新建、切换、归档会话，没有打开审查面板做 diff。审查文档的渲染进程常驻但一直隐藏。
- **假 agent 的回合内容固定**，比真实回合短，事件数（每回合约 170 个）也更少。
- **runner 是 3 核的虚拟机**，与参考机型不同；这些数字只用于看趋势，不能和参考机型直接比较。
- **口径**：
  - "working set" 是 Electron 报告的 `workingSetSize`；宿主用的是 `ps` 的 RSS。两者口径接近，但不完全相同。
  - Playwright 下窗口一直是可见状态（T103 已记）。
