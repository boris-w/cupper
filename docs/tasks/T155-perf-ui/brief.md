## 背景

设计 5.9.7 的产出要求把 SP-6 的场景 2、3、4、7、8 改写成每晚运行的性能回归。T103 在 `spikes/T103-sp6-render/` 里写了这些场景的测量脚本并在 runner 上跑过；T262 给渲染进程加了启动标记，并查明计时要用标记，不能用 Playwright 的启动返回或页面内轮询。PERF 用例只记录、不卡闸门（M1a 同步会 D1，T219）。

## 范围

**做**（计划 T155 一行；设计 5.9.6、5.9.7）：
1. 新增四个 PERF 用例，进 nightly 的 e2e 或 perf 作业（跟 PERF-bridge-gate 的放法一致），只记录：
   - PERF-ui-stream：场景 2（单会话洪流 + 打字：帧时间、输入延迟、输出到屏幕的延迟）和场景 3（4 路流 + blob + 重新同步：帧时间、流重置；6 路作为压力报告）；
   - PERF-ui-long-session：场景 4（1,000、5,000 条和单回合 2,000 条：首屏、滚动帧时间、内存、翻页锚点位移）；
   - PERF-ui-switch：场景 7（LRU 内外的切换、"从通知跳过去"，到首屏可见）；
   - PERF-ui-occluded：场景 8（遮挡下持续流式输出，不应有 `stream/reset`，切回后的首帧）。
2. 夹具覆盖代码高亮（T143）和回合折叠（T146）：长会话和流式消息里要有代码块、折叠的回合。
3. 测量方法以 T103 的脚本为准，助手用 `tools/e2e/src/perf.ts`；时刻用渲染进程的标记和事件的 `ts`。脚本里踩过的坑见交接事项（seed 的请求 id、程序滚动先发 wheel、`fs_usage` 的停法）。
4. 场景 8：T078、T103 都测到在 Playwright 下遮住窗口后页面仍是 `visible`。先查有没有让遮挡生效的办法（例如不同的窗口显示方式），在估算里提出；没有就让用例记"环境不合格"、不计结果，并在汇报里说明。
5. 每个用例的记录格式与已有 PERF 用例一致，能被 trace-ids 认作执行过；超出预算的项可以顺带录 Chromium trace（主进程 `contentTracing`）作为附件。

**不做**：热启动（要等 Q35）；"下一个需要处理的会话"（`next_needs_action` 还没有处理方，归 T153）；任何产品代码的优化（T159）。
