## 逐项意见

1. **原型照产品的布局搭**：helper 嵌在 `Contents/Helpers/`，用 `posix_spawn` 加 setsid 拉起，签名用 ad-hoc 加 hardened runtime，装在 /Applications。这样测出的结论能直接用到产品上。
2. **K5 判定**：三项判据都有日志和用户确认。授权框上的图标、通知上的名称，用户没有确认，以日志为准，汇报里照实标了。认可"有条件通过"：按原设计做 T150，不启用 T158。
3. **四个问题**是本任务最有价值的产出：
   - helper 不会自动登记；
   - 宿主退出后点通知，系统会自己拉起宿主；
   - UI 退出时会重复拉起宿主；
   - UI 和宿主都在时，会弹出 Finder 的"…is not open anymore"。

   前两个已有解法：用 `LSRegisterURL` 登记，系统拉起的宿主跑 NSApplication。后两个的解法还没验证。
4. **加做 s2c** 是对的：s2b 表明只跑 CFRunLoop 时拿不到点击，换成 NSApplication 之后，系统拉起的宿主拿到了点击，给 T150 找到了一条出路。
5. **名称和图标只在第一次登记时取**：改成 bare 写法后，系统设置里没有变。所以第一个申请授权的构建（自用构建）就要写对 `CFBundleDisplayName` 和图标。

## 记下的点（已写进交接事项）

- **T150**：
  - 第一条验收：宿主改跑 NSApplication 之后，验证问题 3（重复拉起）和问题 4（Finder 对话框）是否消失，测法见汇报。消除不了时，考虑改由 LaunchServices 拉起宿主（影响 ADR-01 和 Q21），或者启用 T158；
  - 设计 5.2.9 要补的 6 条规则，编排者在写 T150 的任务书之前补进设计；
  - Info.plist 的键、按路径找外层 App、授权被拒后的界面提示。
- **T160**（自用构建是第一个申请通知授权的构建）：宿主的 `CFBundleDisplayName`、`CFBundleName` 和图标，要在第一次申请授权之前写对。
- **T158**：K5 已通过，UNIT-main-notifications 标为不适用。
- **未测**：macOS 14 和 15、Developer ID 签名、从 DMG 拖入时会不会登记嵌套的 helper。T150 和发布组的签名后冒烟测试再看。
- **本机遗留**：`/Applications/SP10.app`、两条 LaunchServices 登记、系统设置里的"SP10 Notifier"。清理方法见 `.private/cleanup/T101-leftovers.md`，由用户决定何时清理。
