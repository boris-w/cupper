## 逐项意见

1. **原因经实验证实**：主线程循环"拿锁、立刻放开"，另一线程持续拉子进程。
   - 不拉进程时 0 次失败；用 `cupper_sys::spawn` 约 200/3,000 次失败；用 `std::process::Command` 约 170/3,000 次失败。
   - 子进程 exec 之前持有本进程 fd 的副本，`flock` 随副本留着；锁文件带 `O_CLOEXEC` 也一样。
   - 生产里宿主不会在同一进程里放开后再拿这把锁，所以只是测试的问题。结论可靠。
2. **修法**：
   - 照 `cupper-sys` 的 `testutil::alone`，把这条用例放进单独的测试进程，并核对子进程恰好跑了这一条、并且通过；
   - 用一条必定失败的临时断言验证过用例体确实在子进程里执行；
   - 没有用重试掩盖。
3. **`alone` 复制一份、不共用**：理由成立。共用要在唯一允许 `unsafe` 的 crate 上开公开的测试特性，为 20 行不值得。
4. **同类排查**：只有这一条需要改，排查的范围和理由写清楚了。
5. **效果**：修复后在并行负载下全部 lib 测试连跑 200 次 0 失败；同进程加拉进程负载连跑 1,000 次 0 失败。
