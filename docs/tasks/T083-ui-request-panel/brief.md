## 背景

请求面板是 agent 向用户要批准、要回答、要确认计划的地方，出现在输入框原来的位置。它是一条安全路径：设计 5.7.8 的 RP-1 至 RP-12 规定了待命期、焦点、按键、编号和回答的映射，防止用户正在打字或正要点发送时，输入落到面板上（安全工程师"附条件可以"，v1.5）。

主进程一侧的真实输入规则（T077）和原生确认框（T134）已经就位；输入框（T086）也已在 `ComposerArea` 里给面板留了位置。

## 范围

**做**（计划 T083 一行；设计 5.7.4 的请求面板、5.7.5、5.7.8 的"请求面板的落点"与真实输入规则）：
1. **请求面板**：
   - 在 `ComposerArea`（`composer/QueueList.tsx`）里，有待处理的请求时替换 `Composer`，排队消息保持在上方；草稿和附件留在 `useUi()`，切回来原样还在（T086 的交接）；
   - 三类请求（权限、提问、计划确认）；未知类型显示占位，提示"请在桌面端处理"或"此版本不支持"；
   - 多个请求时显示"1 / 3"；别处处理后收起并提示。
2. **RP-1 至 RP-12**（5.7.8 的表，逐条照做）：
   - RP-1 待命期 500 ms（期间按键、点击都吞掉，有按键就重新计时；结束后设 `data-ready`）；
   - RP-2 点击只认 `mousedown` 在"可以操作"之后；
   - RP-3 焦点：自动获得焦点的三个条件（`data-activation="auto"`）；否则显示"按 Tab 或点击以处理请求"（`data-activation="manual"`）；打字键撤销键盘可操作状态；第一下 ⌘Enter 不提交；不抢焦点；
   - RP-4 初始选中；
   - RP-5 按键（数字键选中即提交、↑↓、←→、Enter、⌘Enter、Esc）；
   - RP-6 编号等于 `options` 的序号、不重新排序；效果未知的选项只能点击并走原生确认；
   - RP-7 特权选项只经 `requestPrivileged`，Esc 永远不会触发；
   - RP-8 连续的请求重新待命；
   - RP-9 有弹出层时不响应按键；
   - RP-11 只涉及主文档的还原确认，M1a 没有审查面板，本任务不做；
   - RP-12 "拒绝并附一条消息"：拒绝成功后才发跟进消息（带 `reply_to`）；`already_resolved`、`expired` 时文字留在输入框并提示"已在别处处理"；M1a 没有 Steer，跟进消息一律排队。
   - "请再按一次"只用于窗口激活后的冷却期（5.7.8 第 7 条）：按 `window.onFocusChange` 的时间区分。
3. **标注与显示**："效果未知"、持久选项、"拒绝将结束本回合"；不可见字符转义（用 i18n 包的 `escapeInvisible`）；"已截断"。
4. **"跳过""提交""关闭"到回答的映射**（5.7.4）。
5. **消息流里的请求记录行**："已批准""已询问 n 个问题""未回答"，用 T128 的行类型注册表登记。
6. **DOM 标记**：`data-ready`、`data-activation` 等，供 e2e（T091–T093）使用。

**不做**：输入框本身（T086）；e2e 用例（T092、T093）；审查面板与还原确认（M1b）。
